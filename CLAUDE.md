# CLAUDE.md — backend-adapter

> Локальный проектный контекст для Claude Code. Входит в состав репозитория —
> обновляется вместе с кодом (см. changelog.md).

## Цели проекта

**backend-adapter** — HTTP-прокси, позволяющий работать **Claude Code** (CLI) с
бэкендом LLM, который реализует **OpenAI-совместимый API**
(`/v1/chat/completions`), но некорректно обрабатывает протокол
Anthropic Messages API.

```
Claude Code  <--Anthropic API-->  adapter (localhost:9999)  <--OpenAI API-->  LLM Backend
```

Адаптер решает четыре проблемы:
1. **System messages** — бэкенд кластеризует их в конец диалога; адаптер
   собирает их в одно сообщение в начале, как требует спецификация OpenAI.
2. **Format mismatch** — двунаправленная конвертация сообщений, инструментов
   и tool choice между Anthropic Messages API и OpenAI Chat Completions.
3. **Model compatibility** — использование моделей Qwen через Claude Code.
4. **Qwen tool_calls fallback** — парсинг вызовов инструментов, которые
   модели Qwen иногда возвращают текстом в XML-подобных тегах.

Приоритеты: **надёжность и наблюдаемость** (retry/timeout/trace-логирование),
**минимум зависимостей**, **простая конфигурация через переменные окружения**.

## Ключевые факты

- Точка входа: `backend-adapter.py`; доменный пакет `backend_adapter/`
  (23 модуля, включая `__init__.py`; генератор дерева артефактов —
  группа модулей `artifact_tree*.py` из 8 файлов, публичный API —
  `artifact_tree.generate()`; см. `docs/architecture.md`).
- **Python 3.10+** (аннотации `X | Y`).
- Единственная внешняя зависимость — **PyYAML** (`requirements.txt`);
  всё остальное — стандартная библиотека.
- Полная документация: `docs/install.md`, `docs/environment.md`,
  `docs/logging.md`, `docs/sanitizing.md`, `docs/architecture.md`,
  `docs/webui.md`.
- Версия объявляется в `backend-adapter.py` (`__version__`), история — в `changelog.md`.
- **WEBUI** (`ADAPTER_WEBUI_ENABLE=1`): общее ядро `webserver.py` (роутинг эндпойнтов,
  `serve()`, CLI `python -m backend_adapter.webserver`) + эндпойнт-модули: `/` =
  `webui_status.py` (версия, LLM-эндпойнты, модели; секция «Использованные модели» —
  таблица `model_usage.py` персистентна: YAML `model-usage.yaml` в корне WEBUI,
  сброс строки — кнопка/POST `/api/model-usage/reset`; проверка бэкендов —
  фоновая: при старте адаптера, на первом GET `/` и по кнопке
  «⟳ Проверить сейчас» (POST `/`) → `config.start_refresh()`; POST отвечает
  303 See Other на GET `/` (PRG — нет диалога «повторить действие»);
  пока проверка идёт, страница показывает баннер
  «Проверка выполняется…» и авто-обновляется по завершении через
  `/api/refresh-state`), `/session` = `session_viewer.py` (вкладки + раздача файлов + hash8-алиасы
  `/session/<hash8>/...` и png/puml-шорткаты; корень — директория
  `ADAPTER_DEBUG_LOGPATH`, порт `ADAPTER_WEBUI_PORT`, адрес `ADAPTER_WEBUI_HOST`,
  daemon-поток в процессе адаптера), `/config` = `webui_config_api.py`
  (runtime-пул из 12 переменных — объём debug-записи, санитайзер, рубильники
  стриминга/usage и строгой валидации моделей; см. `RUNTIME_CONFIG_POOL`
  в `config.py`; сеть/бэкенды/порты/`ADAPTER_DEBUG_LOGPATH` на лету не меняются).
  Адрес прослушивания самого адаптера — `ADAPTER_ENDPOINT_HOST`
  (обе по умолчанию `127.0.0.1`);
  `artifact_tree.py` — генерация дерева артефактов (`artefacts/tree.html`)
  на лету; повторные генерации инкрементальны: чекпоинт
  `artefacts/.build_state.json` ограничивает пересборку новыми `*.parts`
  файлами сессии; большие сессии разбиваются на страницы пагинации
  `artefacts/pages/<N>/`.
  Новый эндпойнт = модуль с `@webserver.register` + импорт в `webserver.serve()`.
  Per-session дампы частей протокола включаются флагом `ADAPTER_DEBUG_TAGS_OUT=1`
  (парные `.json`+`.yaml`, фиксированный список тегов), требуют
  `ADAPTER_DEBUG_ENABLE=1` и директорию `ADAPTER_DEBUG_LOGPATH`.
- Служебные файлы продакшена: `backend-adapter.service` (systemd),
  `com.user.backend-adapter.plist` (launchd).

## Принципы

- Не ломать «нулевую настройку»: минимальный запуск — `ADAPTER_BACKEND_CONFIG`
  (путь к YAML-файлу `backend:`) + env-переменная токена, на которую ссылается
  поле `key`.
- Все секреты в логах маскируются (`redact.py`); санитайзер включён по умолчанию.
- Новые возможности покрываются флагами окружения (см. `docs/environment.md`),
  дефолты выбирают безопасное поведение.
- Документация обновляется вместе с кодом, а не после.

## Проверка перед коммитом — обязательна

Перед каждым коммитом гонять в `venv/` все четыре команды (в этом порядке);
зелёные все четыре — только тогда коммит:

```bash
# Linting and formatting
ruff check backend_adapter/ backend-adapter.py
ruff format --check backend_adapter/ backend-adapter.py
# Type checking
mypy --strict --ignore-missing-imports backend_adapter/ backend-adapter.py
# Tests
pytest
```

Контекст: lint/typecheck идут по `backend_adapter/ backend-adapter.py`
(тесты не покрываются), mypy — в strict-режиме, несмотря на не-strict
конфиг `pyproject.toml` (disable_error_code там всё ещё действует;
strict-ошибки в пакете починены и регрессий быть не должно).

### 2026-09-06 — Токены usage + таймаут пробы 10 с + перепроверка строки модели (v0.8.4)

**Контекст:** после группы коммитов персистентной таблицы (см. записи ниже)
наблюдение за работой выявило: (1) проба эндпоинтов падала с
`failed: timed out` на живых completions — таймаут 5 с на эндпоинт был мал
для пограничных таймингов pvapi; (2) колонки «Отправлено/Получено» учитывали
байты тел обмена, а диагностика в ответах приходит в токенах — байты не
отражают фактический расход; (3) результаты проб эндпоинтов строки снимались
при первом обращении и «освежались» только сбросом строки (с потерей
счётчиков).

**Решение:**
- **таймаут пробы 5 → 10 с**: две константы-дефолта (`webui_status.
  PROBE_TIMEOUT`, `model_usage.MODEL_USAGE_PROBE_TIMEOUT`) и формулировки
  «до 4×5 с» → «до 4×10 с»; общий модуль-константа НЕ вводился (цикл
  импорта config ↔ webui_status ↔ model_usage; дубликаты-дефолты — паттерн
  проекта);
- **учёт переведён на usage-токены ответов**: поля строки
  `bytes_sent`/`bytes_recv` → `input_tokens`/`output_tokens` (из
  `usage.prompt_tokens`/`completion_tokens`; не-stream — тело ответа,
  stream — последний chunk.usage; эвристика `chars/4` остаётся только для
  trace-поля `input_tokens_estimated`, в учёт не попадает). Ответы без usage /
  error-тела / пробы токенов не дают. `add_usage_bytes` → `add_usage_tokens`
  (гейт по сумме); `bytes_sink`/`sent`-байты удалены. YAML-файл —
  `version: 2` + **миграция v1 при загрузке**: v1-файл читается,
  calls/backend/endpoints/errors/first_seen сохраняются, байтовые поля
  отбрасываются, токены стартуют с 0; следующие сохранения пишут v2.
  Колонки страницы — «Input»/«Output», точные токены с разделителем тысяч
  (`_fmt_tokens`; «0» — usage не было);
- **перепроверка строки** — `POST /api/model-usage/reprobe?model=<имя>` +
  кнопка «Перепроверить» в колонке «Действия» (рядом со «Сбросить»):
  фоновая перепроба 4 эндпоинтов **именно этой моделью** для строк с
  колонками «—» (отдельный снимок `_REPROBE` в model_usage под
  `_REPROBE_LOCK`, НЕ `probing`-флаг строки; обновляет только
  backend/endpoints/errors; calls/токены не трогает); PRG 303 для кнопки,
  202/404/400 для JSON-клиента; баннер «Перепроверка…» + JS-поллинг лёгкого
  GET `/api/model-usage/reprobe-state` по образцу проверки бэкендов
  (состояние живёт в model_usage, не в config.refresh_state).

**Следствия:** первый запрос новой модели ждёт до 4×10 = 40 с (осознанно),
проба не срывается на живых эндпоинтах; колонки показывают фактический
расход токенов по модели; бэкенды без usage дают «0»; старые v1-файлы не
теряют строки при апгрейде; строка перепроверяется по кнопке без потери
счётчиков и без рестарта; поведение проксирования не меняется. Ветка
`feature/v0.8.4` готова к PR после завершения группы коммитов.

### 2026-09-06 — Персистентная таблица использованных моделей + API сброса + docs/webui.md (v0.8.4)

**Контекст:** таблица использованных моделей (`model_usage.py`, см. запись
ниже) жила только в памяти процесса — счётчики вызовов и трафика терялись
при каждом рестарте адаптера. Задача группы коммитов v0.8.4 — сделать учёт
перманентным (YAML в корне WEBUI), добавить сброс строки модели через API и
кнопку на странице, составить руководство по WEBUI и API.

**Решение:**
- **персистентность** — YAML-файл `model-usage.yaml` в корне WEBUI (формула
  `ADAPTER_DEBUG_LOGPATH or "./tmp/webui"`, та же, что у корня веб-сервера;
  синхронизация пути в `webserver.serve()` — и встроенный запуск, и
  standalone кладут файл в корень). Файл несёт **версию формата**
  (`version: 1`); незнакомая версия/битый файл игнорируются. Загрузка —
  ленивая, при первом обращении к пустой таблице; строки нормализуются,
  загруженные строки не перепроверяются (fast-path; «освежить» = сброс +
  новое обращение);
- **период сохранения** — новый env-параметр `ADAPTER_MODEL_USAGE_SAVE_INTERVAL`
  (сек, дефолт **300**): «грязная» таблица пишется не чаще раза в период;
  создание строки модели, сброс строки и завершение работы адаптера (в т.ч.
  Ctrl-C — `flush_table`) сохраняют сразу. Строки с `probing: True` на диск
  не попадают; потеря хвоста ≤ периода при жёстком kill;
- **API сброса** — `POST /api/model-usage/reset?model=<имя>` (новый эндпоинт
  `ModelUsageResetEndpoint` в `webui_status.py`): JSON-клиент — 200/404/400
  (`{"ok"|"error": ...}`); кнопка «Сбросить» в строке таблицы — HTML-форма по
  PRG (303 See Other на GET `/`). Сброс — только по одной модели, полный
  сброс таблицы НЕ добавлялся;
- **заголовки страниц** `/` и `/config` — `[CC]-adapter` → `Backend-Adapter`;
  внизу страницы `/` — ссылка на GitHub-репозиторий проекта
  (`https://github.com/alekseybb197/backend-adapter`);
- **docs/webui.md** — руководство по WEBUI и API (страницы `/`, `/session`,
  `/config`, JSON-эндпоинты, файл `model-usage.yaml`), ссылки из README/
  install.md/logging.md/CLAUDE.md; синхронизированы environment.md и
  architecture.md.

**Следствия:** счётчики переживают перезапуски адаптера (страница `/` после
рестарта сразу показывает прошлые строки); строка модели сбрасывается с
веб-страницы и curl-ом без рестарта и правки файла; поведение проксирования
не меняется; таблица по-прежнему не влияет на запросы (учёт не бросает
исключений наружу). Ветка `feature/v0.8.4` готова к PR после завершения
группы коммитов.

### 2026-09-06 — Таблица использованных моделей (v0.8.4)

**Контекст:** статус-страница WEBUI показывает модели бэкендов (что
адаптер *принимает*), но не фактическое использование (какие модели агент
реально зовёт) и не доступность API-эндпоинтов *по каждой модели* —
колонка «Доступные API» проверяет бэкенд в целом probe-моделью, а у
бэкендов с несколькими моделями доступность эндпоинтов может различаться
от модели к модели.

**Решение:**
- **новый модуль `backend_adapter/model_usage.py`** — лист DAG (импортирует
  только `config`; его импортируют `server.py` и `webui_status.py`). Таблица
  `_TABLE` (client_model → строка: backend/calls/endpoints/errors/
  first_seen/probing), короткий `_TABLE_LOCK` — только мутация таблицы
  (поиск/создание/инкремент), сетевая проба — вне лока; персистентность
  (YAML в корне WEBUI) — см. ADR «Персистентная таблица использованных
  моделей + API сброса + docs/webui.md» выше; в runtime-пул `/config` не входит;
- **точка учёта — одна строка в `server.do_POST`** сразу после strict-проверки
  модели и ДО маппинга: `model_usage.record_model_usage(client_model)`.
  Недопустимая модель (HTTP 400) в таблицу не попадает; провал резолва/пробы
  никогда не роняет запрос;
- **синхронная проба при ПЕРВОМ обращении** к модели: та же низкоуровневая
  `config._probe_backend_endpoints`, что у фоновой проверки бэкендов, но
  resolved-именем модели ЗАПРОСА и без TTL-кэша; повторные обращения никогда
  не перепроверяют (только инкремент счётчика). Первый запрос новой модели
  ждёт до 4×5 с (осознанно — синхронно в потоке запроса);
- **мастер-флаг `ADAPTER_MODEL_USAGE_ENABLE`** (дефолт `1`): `0` — пробы
  и накопление трафика отключены, учёт остаётся. Пробы по модели НЕ зависят
  от `ADAPTER_ENDPOINT_PROBE` (тот управляет только фоновой проверкой
  бэкендов);
- **счётчики трафика** — строка дополнительно накапливает байты обмена
  адаптер ↔ бэкенд: `bytes_sent` (тела [OI]-запросов, **каждая** попытка)
  и `bytes_recv` (тела ответов, включая ответы ошибок; для стрима — сырые
  SSE-строки через `bytes_sink` в `stream_openai_to_anthropic`). Накопление —
  в локальных переменных `do_POST`, фиксация ОДИН раз в существующем
  `finally` через `model_usage.add_usage_bytes(client_model, sent, recv)`
  (единая точка на любой исход: успех, ошибка бэкенда, исчерпание ретраев,
  исключение). Запросы без strict-проверки и служебные дымовые пробы в
  счётчики не попадают;
- **вывод** — секция «Использованные модели» статус-страницы `/`
  (`webui_status._usage_rows_html`): Модель | Бэкенд | Вызовов | Отправлено
  | Получено | completions | messages | responses | embeddings
  (✓ ⇔ HTTP 200; байтовые колонки — `_fmt_bytes`, 1024-единицы).

**Следствия:** видно фактическое использование моделей, реальную доступность
эндпоинтов по каждой модели и объёмы обмена с бэкендом (включая повторные
попытки при сбоях); повторные запросы без накладных расходов (никаких
перепроверок); таблица не влияет на проксирование. Персистентность, API
сброса и руководство WEBUI — отдельной записью ниже (см. ADR 2026-09-06
«Персистентная таблица …»). Ветка `feature/v0.8.4` готова к PR после
завершения группы коммитов.

### 2026-09-06 — WEBUI статус-страница: HTTP-200-only колонка, PRG, автопроверка (v0.8.3)

**Контекст:** после внедрения фоновой проверки по кнопке (v0.8.2) на
статус-странице накопились дефекты: (1) колонка Endpoints рисовала зелёным ✓
эндпоинты, ответившие любым кодом, кроме 404 (включая `501 Not Implemented`);
(2) авто-обновление страницы (`location.reload()`) повторяло POST кнопки —
браузер показывал диалог «повторить действие», закрывающийся только отменой,
а при отмене зависал баннер «Проверка выполняется…» (его снимал только тот
же reload); (3) проверки не вызывались при первом старте: стартовая
инициализация делала только модельный опрос, а GET «/» проверку не запускал —
колонка Endpoints была пустой до клика по кнопке.

**Решение:**
- **колонка Endpoints — только HTTP 200**: классификация дымовой пробы в
  `config._probe_backend_endpoints` (единое место правды): `found=True` ⇔
  HTTP 200; любой другой код — `found=False`. Рендер `_api_html` показывает
  зелёный `✓` только для `found`, непрошедшие/пропущенные пути скрывает;
  проба была, но ни одного 200 — серая `—`;
- **PRG (Post/Redirect/Get)**: POST «/» (кнопка) запускает фоновую проверку
  и отвечает **303 See Other** на GET «/» (новый сервис `Handler._redirect`);
  авто-релоад происходит на GET-документе — диалог «повторить действие»
  исчезает, баннер корректно снимается;
- **автопроверка**: `config.start_refresh(timeout=PROBE_TIMEOUT)` зовётся при
  старте адаптера (блок WEBUI в `backend-adapter.py`, после поднятия сервера)
  и на первом GET «/» (`webui_status._autostart_first_check`: есть что
  проверять И проверка не идёт И ещё ни разу не завершалась — `done_at`
  пуст). Повторные проверки — только по кнопке; периодического refresh
  по-прежнему нет.

**Следствия:** колонка Endpoints = «что реально работает», а не «что ответило
не 404»; повторные GET не порождают сетевых запросов (контракт v0.8.2
«GET проверку не запускает» заменён на «первый GET запускает первую
проверку, повторные — только по кнопке»); результат виден сразу после
старта без кликов; диалога браузера нет. Поведение проксирования не меняется.
Ветка `fix/v0.8.3` готова к PR.

### 2026-09-05 — WEBUI: фоновая проверка бэкендов по кнопке (v0.8.2)

**Контекст:** статус-страница `/` при каждой загрузке (GET) и по кнопке
«⟳ Проверить сейчас» (POST) **синхронно** вызывала `config.refresh_models`
(опрос `/v1/models` всех бэкендов + дымовая проба API-эндпойнтов) — при
недоступном/медленном бэкенде HTTP-ответ висел (N бэкендов × 5 с на
эндпоинт), а повторный GET даже при живом бэкенде давал лишнюю пачку
сетевых запросов.

**Решение:**
- **фоновая проверка — только по кнопке** (POST `/`, кнопка «⟳ Проверить
  сейчас»): `config.start_refresh(timeout)` публикует снимок-состояние
  `_REFRESH_JOB` (`running`/`started_at`/`done_at`/`ok`/`count`/`errors`/
  `checked_at`) под `_REFRESH_LOCK` и запускает daemon-поток `_refresh_worker`
  (`refresh_models` + публикация финального снимка в `finally`); повторный
  вызов во время идущей проверки возвращает `False` — второй поток не
  создаётся. Загрузка страницы (GET `/`) проверку **не запускает**: рендерит
  текущее состояние (`config.refresh_state()`) — результат стартового опроса
  или последней проверки;
- **индикатор «проверка идёт» — баннер + авто-обновление**: пока проверка
  выполняется, страница показывает баннер «Проверка выполняется…» и JS
  `status_poll` каждые ~2 с опрашивает лёгкий JSON-эндпоинт
  `/api/refresh-state` (`RefreshStateEndpoint`, тот же модуль); по завершении
  — `location.reload()` рендерит свежий результат (авто-релоад безопасен:
  GET проверку не запускает, зацикливания нет);
- состояние проверки живёт в `config.py` рядом с мутируемыми
  `refresh_models` глобалами; снимок иммутабелен (замена ссылки целиком) —
  читателям лок не нужен; `refresh_models` по-прежнему мутирует кэши из
  фонового потока, отдельный Lock вокруг внутренностей не добавлялся
  (существующий компромисс чтения словарей при clear+update).

**Следствия:** статус-страница отвечает мгновенно при любом состоянии
бэкендов; повторные GET не порождают сетевых запросов; результат проверки
виден без ручного обновления; поведение проксирования не меняется.
Новый эндпоинт `/api/refresh-state` — чисто наблюдательный. Ветка
`feature/v0.8.2` готова к PR (детекция API-эндпойнтов v0.8.0 → фоновая
проверка по кнопке).

### 2026-09-04 — WEBUI: инкрементальное дерево артефактов, пагинация, hash8-алиасы, runtime-конфиг `/config` (v0.8.0)

**Контекст:** повторные заходы в WEBUI полностью пересобирали дерево
сессии (дорого на больших сессиях), просмотр длинных диалогов требовал
прокрутки огромной страницы, а объём debug-записи менялся только
перезапуском адаптера.

**Решение:**
- **инкрементальная генерация** в `artifact_tree.py`: чекпоинт
  `artefacts/.build_state.json` (последняя обработанная часть); при следующем
  заходе пересобираются только новые `*.parts`, разметка (Finish/Superseded/
  Title, ответы на запросы, границы страниц) пересчитывается по полному
  состоянию. Чекпоинт битый/отсутствует — холодный полный пересбор с warning;
- **пагинация**: `generate()` дополнительно считает границы страниц по
  реальным пользовательским запросам и пишет `artefacts/pages/<N>/tree.{html,puml,png}`
  + сводный `artefacts/pages/index.html` («по страницам»);
- **короткие адреса**: hash8 из имени папки сессии — `/session/<hash8>/<rel_path>`,
  дерево как картинка/PlantUML-исходник — `/session/<session_id|hash8>/png` и
  `/puml` (`?page=N` — страницу пагинации);
- **runtime-конфиг**: эндпойнт `/config` (`webui_config_api.py`) переключает
  на лету узкий пул debug-переменных (`RUNTIME_CONFIG_POOL` в `config.py`:
  4 bool — `ADAPTER_DEBUG`, `ADAPTER_DEBUG_TAGS_OUT`, `ADAPTER_DEBUG_TOOLS`,
  `ADAPTER_DEBUG_TOOLS_ERROR`; 3 int — `ADAPTER_TRACE_REASONING_MAX_CHARS`,
  `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS`, `ADAPTER_DEBUG_TRIM`); чтение пула
  кодом переведено на живые `config.ADAPTER_X` (не снимок на импорте);
  `set_runtime_config()` молча игнорирует неверные типы/неизвестные ключи.

**Следствия:** повторные заходы в `/session` — быстрые; большие сессии
читаются постранично; ссылки на сессии/артефакты стали короткими;
объём debug-записи переключается с веб-страницы без рестарта.
Сеть/бэкенды/модели/порты/`ADAPTER_DEBUG_LOGPATH` на лету не меняются.
`__version__` поднята до 0.8.0.

### 2026-09-04 — Zero-config: консоль-логи по умолчанию, WEBUI включён, дефолты минимальных ресурсов (v0.7.2)

**Контекст:** дефолты требовали ресурсов, которые нужны только при
целенаправленном включении: при стандартном запуске создавалась папка
`./tmp/logs` (файловая запись при пустом LOGPATH), ошибки инструментов
обрабатывались по умолчанию (`ADAPTER_DEBUG_TOOLS_ERROR=1`), а WEBUI —
единственный способ увидеть состояние адаптера — был выключен
(`ADAPTER_WEBUI_ENABLE=0`), и его корень жёстко зависел от лог-директории.

**Решение:**
- **консоль ↔ диск развязаны** в `logger.py`: `_d()` печатает в stdout,
  гейтится только `ADAPTER_DEBUG_ENABLE`; файловая запись — только при
  явно заданном `ADAPTER_DEBUG_LOGPATH` (`_DEBUG_IS_DIR`/`_DEBUG_PATH`
  falsy на импорте при пустом LOGPATH). Убрано `os.makedirs("./tmp/logs")`
  из стартового блока — при пустом LOGPATH папка не создаётся вообще;
- **`ADAPTER_DEBUG_TOOLS_ERROR` default `"1"` → `"0"`** — zero-config не
  обрабатывает собранные логи (`[TOOL_RESULT_ERROR]` по умолчанию не пишется);
- **`ADAPTER_WEBUI_ENABLE` default `"0"` → `"1"`** — статус-страница `/`
  поднимается по умолчанию на `127.0.0.1:8765` (zero-config: состояние
  видно сразу). Корень WEBUI больше НЕ обязан быть лог-директорией:
  `ADAPTER_DEBUG_LOGPATH`, если задан; иначе — независимая `./tmp/webui`
  (создаётся при старте WEBUI; вкладка `/session` пуста, т.к. логов нет).

**Следствия:** минимальный запуск — только `ADAPTER_BACKEND_CONFIG`:
консольные debug-блоки видны, на диск ничего не пишется, статус доступен
на дефолтном порту. Полное логирование/просмотр сессий — одним
`ADAPTER_DEBUG_LOGPATH` (+ мастер-выключатель `ADAPTER_DEBUG_ENABLE`).

### 2026-09-03 — Настраиваемые адреса прослушивания ADAPTER_ENDPOINT_HOST / ADAPTER_WEBUI_HOST

**Контекст:** адаптер слушал все интерфейсы (bind `("", PROXY_PORT)` → INADDR_ANY),
а WEBUI был жёстко привязан к `127.0.0.1`. Для запуска в сети/контейнерах
нужно было управлять адресами обоих HTTP-серверов, и дефолт «все интерфейсы»
для адаптера — небезопасен по умолчанию.

**Решение:**
- две env-переменные: `ADAPTER_ENDPOINT_HOST` (HTTP-эндпоинт адаптера) и
  `ADAPTER_WEBUI_HOST` (веб-интерфейс); дефолт обеих — `127.0.0.1` (localhost);
- идиом `os.environ.get(name, "") or "127.0.0.1"`: и незаданная, и **пустая**
  env-переменная дают безопасный localhost (в bind-кортеже socketserver пустая
  строка означала бы INADDR_ANY — все интерфейсы);
- `0.0.0.0` — осознанный выбор для доступа из сети (прежнее поведение адаптера);
  баннеры при старте показывают реальный адрес прослушивания.

**Следствия:** безопасный дефолт — оба сервера слушают только localhost, пока
адрес не задан явно; WEBUI из сети — только через осознанный `ADAPTER_WEBUI_HOST=0.0.0.0`
(в содержимом сессий — git log, файлы, reasoning).

### 2026-09-03 — Единая директория логов ADAPTER_DEBUG_LOGPATH

**Контекст:** два механизма сессионного логирования настраивались раздельно
(переменная debug-блоков и отдельная переменная structured trace) и
поддерживали дуальность «файл или директория», а WEBUI как корень
использовал ту же переменную debug-лога. Это усложняло документацию
и запуск («куда писать?»).

**Решение:**
- две переменные заменены одной — `ADAPTER_DEBUG_LOGPATH`, указывающей на
  **директорию** логов сессий: debug-логи (`session-*.log`), trace-логи
  (`session-*.jsonl`), `*.parts` дампы и корень WEBUI лежат в ней плоско;
- пусто → дефолт `./tmp/logs` относительно папки запуска (применяется
  лениво — на старте/при записи, не на импорте);
- `ADAPTER_DEBUG_ENABLE` — мастер-выключатель: при `0` ничего не пишется
  и папка НЕ создаётся; при `1` папка создаётся при необходимости (на
  старте и/или при первой записи);
- LOGPATH указывает на существующий **файл** → `[FATAL]` на старте +
  подсказка + `sys.exit(1)`;
- single-file режим удалён полностью — запись всегда через per-session
  файлы в директории.

**Следствия:** настройка логирования — одна переменная; debug, trace,
дампы и WEBUI всегда делят одну директорию; включение/выключение — одним
рубильником `ADAPTER_DEBUG_ENABLE`.

### 2026-09-03 — Удалён legacy-режим конфигурации бэкенда

**Контекст:** поддерживались два способа указания подключения к бэкенду —
legacy-пара `ADAPTER_BACKEND_BASE` + `ADAPTER_BACKEND_KEY` и YAML через
`ADAPTER_BACKEND_CONFIG`. Двойной путь усложнял код (ветки в
`refresh_models`/`_resolve_backend`/стартовом блоке и webui_status) и
документацию («нулевая настройка» из двух env-переменных).

**Решение:**
- конфигурация бэкенда — **только** YAML через `ADAPTER_BACKEND_CONFIG`
  (структура `backend:`: список `name`/`base`/`key`, где `key` — имя
  env-переменной токена, раскрываемое при старте);
- удалены legacy-глобалы (`BACKEND_BASE`/`BACKEND_KEY`/`_BACKEND_LEGACY`),
  `_probe_models()` и все legacy-ветки;
- пустой `ADAPTER_BACKEND_CONFIG` на старте → `[FATAL]` + подсказка
  (пример — `sample.adapter.yaml` в корне) + `sys.exit(1)`;
- финальный «недостижимый» return в `_resolve_backend` → `RuntimeError`;
- в корень репозитория добавлен пример `sample.adapter.yaml`, на него
  ссылаются env-файлы, plist и README.

**Следствия:** минимальный запуск — `ADAPTER_BACKEND_CONFIG` (путь к YAML)
+ env-переменная токена из поля `key`; «нулевая настройка» сохраняется:
без YAML адаптер не стартует и объясняет, что задать.
