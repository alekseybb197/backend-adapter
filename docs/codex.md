# Настройка Codex CLI для работы через backend-adapter

> Руководство по настройке клиента **Codex CLI** ([OI]) на работу через
> backend-adapter. Типовые файлы — в `docs/codex/`: `sample.config.toml`
> (профиль пользователя) и `sample.local.config.toml` (минимальный локальный
> профиль). Установка и настройка самого адаптера — [`docs/install.md`](install.md).
> Настройка двух других клиентов — [CC] ([`docs/claude_code.md`](claude_code.md))
> и QwenCode ([`docs/qwen-code.md`](qwen-code.md)); сравнение подходов к
> моделям — раздел 9 ниже.

---

## 1. Установка Codex CLI

Официальная инструкция: <https://learn.chatgpt.com/docs/codex/cli#getting-started>.

**Standalone-инсталлятор (macOS/Linux).** Основной способ — установочный
скрипт; он же служит командой обновления (повторный запуск ставит свежую
версию):

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

На странице установки есть и другие способы (Windows, npm, Homebrew) — они
переключаются вкладками; актуальные команды смотрите на самой странице.

**Проверка.** Отдельной команды проверки версии страница не документирует:
установка считается успешной, если `codex` запускается и открывает интерфейс.

**Вход.** Запустите `codex` в каталоге проекта — при первом запуске клиент
предложит выбрать способ входа (подробности — в разделе `/codex/auth` на том
же сайте). Для работы через локальный адаптер аутентификация [OI] не нужна:
адаптер сам авторизуется на бэкенде, а клиенту достаточно непустого ключа-
заглушки (см. `env_key` в разделе 6).

**Первые шаги.** Задача описывается естественным языком. В интерфейсе
доступны слэш-команды `/init`, `/status`, `/permissions`, `/model`, `/review`;
в терминале — `codex` (интерактивно), `codex exec` (неинтерактивно),
`codex resume` (возобновить сессию), `codex mcp` (MCP-серверы),
`codex --search`, `codex --image`.

> **Про `/model`.** У Codex есть собственный пикер моделей, но на кастомном
> `model_provider` (как в этом руководстве) он ненадёжен — известны баги
> перезаписи профиля и клонирования контекста при смене модели без
> перезапуска сессии. Поэтому адаптер держит **собственный канал**
> переключения: вы пишете `/model <имя>` обычным сообщением (раздел 7).

## 2. Как Codex подключается к адаптеру

Codex CLI говорит на **Responses API**: клиент отправляет `POST` на
`<base_url>/responses`. Адаптер поднимает локальный HTTP-эндпоинт (по
умолчанию `http://127.0.0.1:9999`), принимающий Responses API на входе
`/v1/responses` (см. [`docs/routing.md`](routing.md)).

| Параметр | Значение | Назначение |
|---|---|---|
| `base_url` | `http://127.0.0.1:9999/v1` | Адрес адаптера **с суффиксом `/v1`** — клиент дописывает `/responses` |
| `env_key` | `LOCAL_API_KEY` | Имя переменной окружения с ключом; значение — заглушка `dummy` |
| `wire_api` | `"responses"` | Протокол обмена; для Responses API — единственное поддерживаемое значение |

> **Важно про `base_url`.** Адрес указывается **с суффиксом `/v1`**
> (`http://127.0.0.1:9999/v1`) — клиент сам дописывает `/responses`. Так же
> устроен `openai`-провайдер QwenCode (`.../v1` + `/chat/completions`); а вот
> [CC] задаёт адрес **без** `/v1` в `ANTHROPIC_BASE_URL`, потому что клиент
> дописывает `/v1/messages`. Если перепутать, запрос уйдёт на несуществующий
> путь.

В отличие от [CC], который читает адрес адаптера из переменных окружения
(`ANTHROPIC_BASE_URL`), и от QwenCode, который задаёт его в `settings.json`
(поле `baseUrl`), Codex берёт адрес из **файла `config.toml`** (раздел 4).
Адаптер настройки клиента не читает — ему нужны только собственные `ADAPTER_*`
(см. [`docs/environment.md`](environment.md)).

## 3. Что нужно включить в адаптере

Прежде чем настраивать клиент, проверьте вход адаптера: у каждого из трёх
входов есть TARGET-переменная (`ADAPTER_*_TARGET`, см.
[`docs/routing.md`](routing.md)), и **вход Responses по умолчанию выключен**:

| Значение `ADAPTER_RESPONSES_TARGET` | Что происходит |
|---|---|
| `none` (**дефолт**) | Вход выключен: на любой запрос Codex придёт `404 "endpoint is disabled (ADAPTER_RESPONSES_TARGET=none)"` |
| `responses` | Внутренний конвертер `responses→responses`: тело уходит бэкенду в формате Responses; адаптер принудительно ставит `store: false` и **поддерживает команду `/model`** (раздел 7) |
| `completions` | Кросс-форматная конвертация `responses→completions`: запрос переводится в Chat Completions для [OI]-совместимого бэкенда, ответ — обратно в Responses; команда `/model` **поддерживается** |
| `passthrough` | Тело уходит бэкенду **дословно**, без вмешательств; команда `/model` **не работает** (адаптер не разбирает тело) |

Включение — переменной окружения адаптера:

```bash
# Бэкенд умеет Responses API — отдаём тело как есть (плюс store:false)
export ADAPTER_RESPONSES_TARGET=responses

# Бэкенд умеет только Chat Completions — конвертируем
export ADAPTER_RESPONSES_TARGET=completions
```

> **`passthrough` и `/model` несовместимы.** В режиме `passthrough` адаптер
> не заглядывает в тело запроса — служебная команда `/model` дойдёт до
> бэкенда как обычный текст пользователя и будет проигнорирована. Нужно
> переключение модели на лету — выбирайте `responses` или `completions`.

## 4. Файлы настроек: расположение и приоритет

Codex CLI читает настройки из файлов `config.toml`:

| Файл | Уровень | Назначение |
|---|---|---|
| `~/.codex/config.toml` | Пользовательский | Основное место настройки: провайдер, модель, окно контекста |
| `<project>/.codex/config.toml` | Проектный | Настройки конкретного проекта; применяется **только для доверенных проектов** |
| `$CODEX_HOME/<профиль>.config.toml` | Именованный профиль | Альтернативный профиль; выбирается флагом `codex --profile <профиль>` |

Правила:

- **проектный файл ограничен в правах**: в `.codex/config.toml` нельзя
  задавать `model_provider`, `model_providers`, `profile`/`profiles`,
  `openai_base_url`, `chatgpt_base_url`, `notify` и ряд других ключей —
  провайдера и модель для проекта берут только из пользовательского файла
  или из именованного профиля. Это защита от подмены адреса API
  содержимым чужого репозитория;
- в репозиторий backend-adapter каталог `.codex/` не коммитится, поэтому
  типовые файлы лежат в `docs/codex/` и копируются вручную (раздел 10);
- **встроенные идентификаторы провайдеров зарезервированы**: `openai`,
  `ollama`, `lmstudio`. Свой провайдер называйте любым другим именем — в
  типовом файле это `local`.

## 5. Типовой профиль — `~/.codex/config.toml`

Типовой файл — [`docs/codex/sample.config.toml`](codex/sample.config.toml).
Скопируйте в `~/.codex/config.toml` и при необходимости поправьте адрес,
имя модели и размер окна:

```toml
model = "local"
model_provider = "local"

[model_providers.local]
name = "Local gateway"
base_url = "http://127.0.0.1:9999/v1"
env_key = "LOCAL_API_KEY"
wire_api = "responses"
requires_openai_auth = false
stream_idle_timeout_ms = 600000
request_max_retries = 2
model_context_window = 262144
```

---

## 6. Комментарии по ключам

### 6.1 Верхний уровень

| Ключ | Значение | Назначение |
|---|---|---|
| `model` | `"local"` | Имя модели, активной при старте. Должно приниматься бэкендом — напрямую или через маппинг моделей адаптера (`ADAPTER_MODELS_MAPPING`) |
| `model_provider` | `"local"` | Какой провайдер использовать; должен совпадать с именем секции `[model_providers.<имя>]` |

### 6.2 Секция `[model_providers.local]`

| Ключ | Значение | Назначение |
|---|---|---|
| `name` | `"Local gateway"` | Отображаемое имя провайдера в интерфейсе |
| `base_url` | `"http://127.0.0.1:9999/v1"` | Адрес адаптера **с `/v1`** (см. раздел 2) |
| `env_key` | `"LOCAL_API_KEY"` | Имя переменной окружения с API-ключом. Ключ должен быть **непустым** — впишите заглушку `dummy`; реальную авторизацию на бэкенде выполняет адаптер |
| `wire_api` | `"responses"` | Протокол обмена. `"responses"` — единственное поддерживаемое значение и значение по умолчанию |
| `requires_openai_auth` | `false` | Не требовать аутентификации [OI] — для локального адаптера выключено |
| `stream_idle_timeout_ms` | `600000` | Таймаут простоя SSE-потока (мс). 10 минут — с запасом на медленный локальный бэкенд и «размышления» |
| `request_max_retries` | `2` | Повторы при сбое запроса. Адаптер **сам** делает ретраи (`ADAPTER_RETRY`), поэтому клиентские повторы держат минимальными, чтобы не умножать нагрузку |
| `model_context_window` | `262144` | **Размер контекстного окна (клиентский ключ).** Адаптер его **не читает** — это представление клиента о ёмкости модели, от него Codex считает компактизацию и обрезку истории |

> **`model_context_window` — одно значение на все модели.** Как и у [CC],
> у Codex нет способа задать разное окно для разных моделей: переключение
> `/model` меняет модель, но не окно. Подробности — в разделе 7.

**Заглушка ключа.** Значение переменной `LOCAL_API_KEY` адаптеру безразлично
(он игнорирует входящую авторизацию и подставляет свой ключ бэкенда) — важен
лишь непустой ключ для клиента. Задайте его в окружении shell:

```bash
export LOCAL_API_KEY=dummy
```

## 7. Переключение модели на лету — `/model <имя>`

Нативный пикер `/model` самого Codex на кастомном `model_provider` ненадёжен
(баги пикера и клонирования контекста предыдущего провайдера при смене модели
без перезапуска сессии). Поэтому адаптер держит **собственный, полностью
предсказуемый канал**: вы отправляете `/model <имя>` **обычным сообщением**,
и адаптер перехватывает его до похода к бэкенду
(`convert.detect_model_switch_command` → `session_settings.set_model_override`).

Как это выглядит в работе:

1. команда распознаётся, только если **последнее** сообщение `role="user"`
   целиком состоит из одного текстового блока и совпадает с шаблоном
   `/model <имя>` (регистр не важен) — обычный текст, лишь упоминающий
   `/model`, не перехватывается;
2. выбранное имя сохраняется для **всей** сессии и применяется ко всем
   последующим запросам, пока не будет переключено снова;
3. реальная модель на команду **не вызывается**: клиент получает
   синтетическое подтверждение `Model switched to \`<имя>\`.` — SSE-потоком
   (`streaming.emit_responses_control_message`) или обычным JSON-ответом
   (`streaming.build_responses_control_response`) в зависимости от `stream`;
4. в консоли адаптера видны строки `[MODEL_SWITCH] session=… -> <имя>` (сам
   момент переключения) и `[MODEL_OVERRIDE] session=…` (применение оверрайда
   к последующим запросам, где клиент всё ещё присылает старое `model`).

Пример:

```
/model qwen3.6-35b-a3b
```

### 7.1 Ограничения

**1. Только внутренние конвертеры.** Команда работает, когда
`ADAPTER_RESPONSES_TARGET` равен `responses` или `completions`. В режиме
`passthrough` тело запроса уходит дословно — адаптер в него не заглядывает, и
команда доходит до бэкенда как обычный текст (раздел 3).

**2. Сохранение диалога на стороне сервера принудительно отключено.**
Адаптер принудительно выставляет `store: false` в каждом запросе, чей
исходящий формат — Responses (`convert.force_store_false`; в консоли —
`[STORE_ENFORCED] responses: store forced to false`). Причина:
`previous_response_id` может разрешить только тот бэкенд, который сам создал
предыдущий `response`, а сторонний бэкенд за адаптером чужих ответов не
хранит. На практике Codex и сам пересобирает контекст целиком на своей
стороне, но адаптер не полагается на добросовестность клиента: `store: false`
— это инвариант эндпоинта. При `ADAPTER_RESPONSES_TARGET=completions` поля
`store` в запросе нет вовсе — в Chat Completions такого поля не существует.

> Формулировка «сохранение отключается автоматически для не-[OI] моделей»
> неверна: триггер — **исходящий формат запроса** (`responses`), а не
> модель и не её вендор.

**3. Одно контекстное окно на все модели.** `model_context_window` задаётся
**одним числом** на профиль, и клиент считает компактизацию и обрезку истории
именно от него — какую бы модель вы ни выбрали командой `/model`. Практическое
следствие: переключились на модель с реальным окном меньше заявленного —
рискуете переполнить контекст и получить ошибку от бэкенда; заявили меньше
реального — Codex будет компактизировать раньше времени, теряя историю без
нужды. Держите значение по самой «узкой» из используемых моделей либо
используйте модели сопоставимого класса.

## 8. Передача id сессии

Codex CLI шлёт id сессии внутри заголовка `x-codex-turn-metadata` (поле
`session_id` JSON-объекта). Это имя **уже входит** в дефолтный список
`ADAPTER_SESSION_HEADER`
(`X-Claude-Code-Session-Id,x-opencode-session,x-codex-turn-metadata:session_id`)
— править ничего не нужно: адаптер подхватит id, и сессия получит честное имя
в таблице `/sessions`, а не `unknown`.

Синтаксис `Имя-заголовка:ключ` означает «разобрать значение заголовка как
JSON-объект и взять строковое поле `ключ`» — именно так читается
`x-codex-turn-metadata:session_id`. Битый JSON или отсутствие ключа — кандидат
молча пропускается.

`x-client-request-id` — **opt-in**: Codex дублирует в нём тот же uuid, но имя
у заголовка generic (у части клиентов это per-request id, а не id сессии),
поэтому в дефолт он не входит. Нужен — добавьте его в `ADAPTER_SESSION_HEADER`
(см. [`docs/environment.md`](environment.md)).

## 9. Отличия от [CC] и QwenCode

Все три клиента работают через один и тот же адаптер, но по-разному
подключаются и распоряжаются моделями.

| Аспект | Codex CLI | [CC] ([`docs/claude_code.md`](claude_code.md)) | QwenCode ([`docs/qwen-code.md`](qwen-code.md)) |
|---|---|---|---|
| **Протокол** | Responses API (`/v1/responses`) | Anthropic Messages (`/v1/messages`) | Anthropic Messages **или** Chat Completions |
| **Где задаётся адрес** | `base_url` в `~/.codex/config.toml` (с `/v1`) | `ANTHROPIC_BASE_URL` (без `/v1`) | `baseUrl` записи в `modelProviders` (`openai` — с `/v1`, `anthropic` — без) |
| **Как объявляются модели** | Одна активная модель (`model`) + переключение командой `/model <имя>` в сессии | Не фиксированы: имя приходит в запросе, проверяется адаптером | **Фиксированы заранее**: каждая модель — запись в `modelProviders` |
| **Размер контекста** | **Одно значение на все модели** (`model_context_window`) | **Одно значение на все модели** (`CLAUDE_CODE_AUTO_COMPACT_WINDOW`) | **Своё у каждой модели** (`contextWindowSize`) |
| **Роли и субагенты** | Ролевых переменных нет | Отдельные переменные на роли и субагентов | Ролевых переменных нет |
| **Переключение модели** | `/model <имя>` сообщением — канал адаптера (раздел 7) | Любая поддержанная модель сразу доступна; правка конфига не нужна | Сначала описать модель, затем выбрать `/model` |

**Практический вывод.** Codex CLI — единственный из трёх клиентов, говорящий
на Responses API, поэтому ему нужен включённый вход
`ADAPTER_RESPONSES_TARGET` (раздел 3). Модель переключается командой-сообщением
`/model <имя>` — это канал адаптера, а не нативный пикер клиента, и работает
он только при `responses`/`completions` (не `passthrough`). Как и у [CC], окно
контекста задаётся одним числом на все модели.

## 10. Установка типового файла

```bash
# Пользовательский профиль (каталог создаётся при необходимости)
mkdir -p ~/.codex
cp docs/codex/sample.config.toml ~/.codex/config.toml
#    поправьте base_url, model и model_context_window (разделы 5–6)

# Ключ-заглушка (значение адаптеру безразлично, важен непустой ключ)
export LOCAL_API_KEY=dummy

# Минимальный локальный профиль — если нужен только адрес и окно
# cp docs/codex/sample.local.config.toml ~/.codex/config.toml

# И не забудьте включить вход Responses в окружении адаптера (раздел 3):
# export ADAPTER_RESPONSES_TARGET=responses   # или completions
```

## 11. Проверка

```bash
# 1. Адаптер слушает и отвечает
curl -s http://127.0.0.1:9999/v1/models | head

# 2. Вход Responses включён: запрос доходит до бэкенда, а не отдаёт 404
curl -s http://127.0.0.1:9999/v1/responses \
  -H 'Content-Type: application/json' \
  -d '{"model":"local","input":"ping","stream":false}' | head

# 3. Клиент запускается в каталоге проекта
codex

# 4. Сессия протоколируется честным id: в консоли адаптера
#    [REQ] ... session=<uuid>, а не session=unknown; строка видна на /sessions

# 5. Переключение модели на лету (раздел 7): в интерфейсе Codex отправьте
#    сообщением "/model <имя>" — в ответ придёт "Model switched to `<имя>`.",
#    а в консоли адаптера появится строка [MODEL_SWITCH]
```

Если на запрос Codex приходит
`404 "endpoint is disabled (ADAPTER_RESPONSES_TARGET=none)"` — не включён вход
`/v1/responses` (раздел 3).
