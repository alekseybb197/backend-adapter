# Маршрутизация входных эндпоинтов (TARGET) — backend-adapter

> Настройка того, какие POST-эндпоинты принимает адаптер и что делает с
> запросом на каждом из них: конвертация форматов, passthrough E→E или
> запрет. Справочник env-переменных — [`docs/environment.md`](environment.md);
> внутреннее устройство (`routing.py`, поток запроса) —
> [`docs/architecture.md`](architecture.md), §4.2.

---

## 1. Принципы настройки

1. **Один вход — одна TARGET-переменная.** У адаптера три входных
   POST-эндпоинта: `/v1/messages` (Anthropic Messages), `/v1/chat/completions`
   ([OI] Chat Completions), `/v1/responses` (Responses). Чем управляется вход —
   видно из имени переменной: **префикс = входной эндпоинт**
   (`ADAPTER_MESSAGES_TARGET`, `ADAPTER_COMPLETIONS_TARGET`,
   `ADAPTER_RESPONSES_TARGET`).
2. **`none` — вход выключен.** Значение `none` (безопасный дефолт) запрещает
   вход: запросы на него не принимаются, ответ — HTTP **404** «endpoint is
   disabled (ADAPTER_*_TARGET=none)». Единственный способ закрыть вход.
3. **`auto` — не эвристика.** Автовыбор маршрута идёт **только по кэшу
   результатов проб** (какие эндпоинты бэкенд подтверждённо поддерживает);
   сети во время запроса адаптер не делает — никакой живой проверки
   доступности в момент выбора пути.
4. **Работает то, что реализовано.** Разрешённые преобразования перечислены в
   реестре `IMPLEMENTED_CONVERSIONS` (`backend_adapter/routing.py`).
   Нереализованная директива даёт **явную ошибку агенту** (HTTP 400/404), а не
   молчаливую подмену маршрута.
5. **Passthrough E→E — особый случай.** Когда целевой формат == входному,
   запрос уходит бэкенду **как пришёл** (адаптер подставляет только
   резолвнутую модель), ответ и SSE-поток возвращаются дословно. Это не
   «конвертация сама в себя», а режим прозрачной передачи на бэкенд, который
   сам говорит на языке входа.
6. **Доступность бэкенда на маршрут не влияет** (кроме `auto`): в явном
   режиме решение принимается по значению TARGET-переменной, а не по тому,
   какие эндпоинты бэкенд «раздаёт».

---

## 2. Что реализовано сейчас (v0.9.x)

### 2.1 Матрица «вход × значение TARGET»

Что произойдёт с запросом при каждом допустимом значении TARGET-переменной
входа (значение ∈ `messages | completions | responses | auto | none`):

| Вход | `messages` | `completions` | `responses` | `auto` | `none` (дефолт для 2 входов) |
|---|---|---|---|---|---|
| **`/v1/messages`** | passthrough E→E `messages→messages` | **конверсия `messages→completions`** *(дефолт)* | не реализовано → 400 | auto-выбор | вход выключен → 404 |
| **`/v1/chat/completions`** | не реализовано → 400 | **passthrough E→E `completions→completions`** | не реализовано → 400 | auto-выбор | **вход выключен → 404** *(дефолт)* |
| **`/v1/responses`** | не реализовано → 400 | не реализовано → 400 | **passthrough E→E `responses→responses`** | auto-выбор | **вход выключен → 404** *(дефолт)* |

Реализованные маршруты выделены жирным. Не-реализованные ячейки принимают
директиву, но отвергают запрос HTTP **400** «conversion … is not implemented» —
см. §2.2.

### 2.2 Сводка реализованного

- **Конверсия `messages → completions`** (единственная реализованная пара
  конвертеров; реестр `IMPLEMENTED_CONVERSIONS` в `routing.py`): запрос
  `convert_messages_anthropic_to_openai`, ответ `convert_openai_to_anthropic`,
  стрим `stream_openai_to_anthropic` (`convert.py`/`streaming.py`). Это
  дефолт для `/v1/messages` — «нулевая настройка» сохраняет прежнее
  поведение 100%.
- **Passthrough E→E** — целевой формат == входному: `completions→completions`,
  `responses→responses` (и `messages→messages` — по явной директиве
  `ADAPTER_MESSAGES_TARGET=messages`). Тело передаётся дословно.
- **`auto`** — автовыбор по кэшу проб (см. §1.3): passthrough E→E, если
  бэкенд подтверждённо поддерживает входной формат (для `messages` — в т.ч.
  `messages→messages`); иначе — реализованная конверсия из входа; иначе —
  HTTP 400 «no route». В нулевой настройке не участвует (входы с `none` до
  него не доходят).
- **Запрет входа** — `none` → HTTP **404**.

**Коды ответов при отказе:** нереализованное преобразование → 400
(«conversion … is not implemented»); `auto` без подходящего маршрута → 400
(«no route»); вход `none` → 404 («endpoint is disabled (ADAPTER_*_TARGET=none)»);
явный маршрут (passthrough/convert) при подтверждённо не поддерживающем
целевой формат бэкенде → 502 (до отправки запроса, `.err` не пишется).
Решение принимается **только по кэшу проб** (`config.endpoint_support` —
геттер `_ENDPOINT_STATE`); в явном режиме отсутствие данных (None) не
блокирует — маршрут выбирается оптимистично.

### 2.3 Примеры конфигураций

```bash
# Нулевая настройка (дефолты, можно ничего не задавать): принимается только
# /v1/messages, конвертируется в chat.completions; остальные входы закрыты (404).
export ADAPTER_MESSAGES_TARGET=completions      # = дефолт
# export ADAPTER_COMPLETIONS_TARGET=none        # = дефолт (вход закрыт)
# export ADAPTER_RESPONSES_TARGET=none          # = дефолт (вход закрыт)

# Открыть вход /v1/chat/completions для [OI]-клиента: passthrough E→E на бэкенд.
# export ADAPTER_COMPLETIONS_TARGET=completions

# Открыть вход /v1/responses: passthrough E→E на бэкенд, говорящий на Responses.
# export ADAPTER_RESPONSES_TARGET=responses

# Автовыбор маршрута по кэшу проб (без сети в запросе) — например для messages.
# export ADAPTER_MESSAGES_TARGET=auto
```

Полный env-файл с комментариями всех переменных — `docs/samples/sample.adapter.env`.

## 3. Варианты настроек следующих версий (не реализовано сегодня)

> Ниже — **направления развития**, а не текущее поведение. Пока конвертер не
> реализован, соответствующая директива в текущих версиях даёт HTTP 400/404
> (см. §2.2); матрица в §2.1 актуализируется в той же версии, где пара
> появляется.

1. **Дополнительные пары конверсий** — `completions → messages`,
   `messages → responses`, `completions → responses` и обратные. Станут
   доступны с реализацией соответствующих конвертеров; появятся в реестре
   `IMPLEMENTED_CONVERSIONS` (`routing.py`) и в матрице §2.1.
2. **`auto` для всех входов как основной режим** — сегодня `auto` уже умеет
   выбирать между passthrough E→E и реализованной конверсией по кэшу проб
   (§2.2), но выбор ограничен реализованными парами; с новыми парами
   конверсий (п. 1) `auto` сможет маршрутизировать шире.
3. **Отбор маршрута по доступности эндпоинтов** — сознательно **не**
   реализуется в явном режиме (принцип §1.6): маршрут задаётся директивой, а
   не живой проверкой. В `auto` доступность учитывается только через кэш проб,
   без сети.
4. **Проксирование/балансировка между несколькими бэкендами** — вне
   маршрутизации входов: выбор бэкенда под модель делает
   `config._resolve_backend` (см. `docs/architecture.md` §6.3), а TARGET-
   маршрутизация решает только про формат.

---

## 4. Поведение, общее для всех входов

Учёт «Models in use» (таблица использованных моделей), strict-проверка
модели (`ADAPTER_STRICT_MODELS`), маппинг моделей, извлечение токенов usage и
`.err`-протокол инцидентов работают на всех трёх входах **одинаково** — после
того как маршрут принят (disabled/reject до учёта и `.err` не доходят).
