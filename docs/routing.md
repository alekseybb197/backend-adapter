# Маршрутизация входных эндпоинтов (TARGET) — backend-adapter

> Настройка того, какие POST-эндпоинты принимает адаптер и что делает с
> запросом на каждом из них: **прямое преобразование** формата, **дословная
> передача** (passthrough) или запрет. Значения задаются env-переменными при
> старте, а на работающем адаптере меняются на лету на странице `/config`
> WEBUI (выпадающие списки, runtime-пул — см. [`docs/webui.md`](webui.md) §6).
> Справочник env-переменных — [`docs/environment.md`](environment.md);
> внутреннее устройство (`routing.py`, поток запроса) —
> [`docs/architecture.md`](architecture.md), §4.2.

---

## 1. Принципы настройки

1. **Один вход — одна TARGET-переменная.** У адаптера три входных
   POST-эндпоинта: `/v1/messages` (Anthropic Messages), `/v1/chat/completions`
   ([OI] Chat Completions), `/v1/responses` (Responses). Чем управляется вход —
   видно из имени переменной: **префикс = входной эндпоинт**
   (`ADAPTER_MESSAGES_TARGET`, `ADAPTER_COMPLETIONS_TARGET`,
   `ADAPTER_RESPONSES_TARGET`).
2. **Конкретный формат = прямое преобразование.** Значение
   `messages | completions | responses` задаёт **целевой формат**: вход
   преобразуется в него и уходит на соответствующий эндпойнт бэкенда. Это
   преобразование, даже когда целевой формат совпадает с входным: например
   `ADAPTER_MESSAGES_TARGET=messages` — это `convert messages→messages`
   (сортировка system-полей, см. §2.2), а **не** дословная передача.
3. **`passthrough` = дословно.** Отдельное значение `passthrough` передаёт
   запрос на эндпойнт **входного** формата **без преобразования**: тело и
   SSE-поток уходят бэкенду как пришли (адаптер подставляет только
   резолвнутую модель). Это способ «ничего не менять».
4. **`none` — вход выключен.** Значение `none` (безопасный дефолт) запрещает
   вход: запросы на него не принимаются, ответ — HTTP **404** «endpoint is
   disabled (ADAPTER_*_TARGET=none)». Единственный способ закрыть вход.
5. **`auto` удалён (v0.9.4).** Прежнее значение `auto` (автовыбор маршрута по
   кэшу проб) убрано — для него нет приемлемой логики. Встретив `auto` в env
   (как и любое невалидное значение), адаптер печатает `[WARN]` в консоль и
   трактует вход как `none` (вход выключен); старт не падает.
6. **Работает то, что реализовано.** Разрешённые преобразования перечислены в
   реестре `IMPLEMENTED_CONVERSIONS` (`backend_adapter/routing.py`).
   Нереализованная директива даёт **явную ошибку агенту** (HTTP 400/404), а не
   молчаливую подмену маршрута.
7. **Доступность бэкенда влияет только на отказ.** Решение принимается по
   значению TARGET-переменной, а не по тому, какие эндпоинты бэкенд «раздаёт»;
   поддержка целевого формата проверяется лишь для того, чтобы при
   **подтверждённом** отказе (проба была и дала found=False) вернуть HTTP 502
   до отправки запроса. Нет данных (проба не проводилась / выключена) — маршрут
   выбирается оптимистично.
8. **Сессия может переопределить TARGET (v0.9.5).** Значение общей переменной —
   дефолт для всех сессий; для отдельного `session_id` его можно переопределить
   (или вернуть к общему значением `inherit`) через WEBUI, не затрагивая
   остальных — см. §2.4.

## 2. Что реализовано сейчас (v0.9.x)

### 2.1 Матрица «вход × значение TARGET»

Что произойдёт с запросом при каждом допустимом значении TARGET-переменной
входа (значение ∈ `messages | completions | responses | passthrough | none`):

| Вход | `messages` | `completions` | `responses` | `passthrough` | `none` (дефолт для 2 входов) |
|---|---|---|---|---|---|
| **`/v1/messages`** | **convert `messages→messages`** (сортировка system) | **convert `messages→completions`** *(дефолт)* | не реализовано → 400 | **дословно `messages→messages`** | вход выключен → 404 |
| **`/v1/chat/completions`** | не реализовано → 400 | не реализовано → 400 | не реализовано → 400 | **дословно `completions→completions`** | **вход выключен → 404** *(дефолт)* |
| **`/v1/responses`** | не реализовано → 400 | не реализовано → 400 | **convert `responses→responses`** (внутренний конвертер, `store:false`) | **дословно `responses→responses`** | **вход выключен → 404** *(дефолт)* |

Реализованные маршруты выделены жирным. Не-реализованные ячейки принимают
директиву, но отвергают запрос HTTP **400** «conversion … is not implemented» —
см. §2.2. Дословная передача входа, формат которого совпадает с целевым
(`completions→completions`), достигается **только** значением `passthrough`:
self-пара `completions→completions` конвертером не реализована. Пара
`responses→responses` (v0.9.6) — исключение: она **реализована** (внутренний
конвертер, см. §2.2) и вдобавок поддерживает команду `/model` (см. §2.5).

### 2.2 Сводка реализованного

- **Конверсия `messages → completions`** — полный конвертер (реестр
  `IMPLEMENTED_CONVERSIONS` в `routing.py`): запрос
  `convert_messages_anthropic_to_openai`, ответ `convert_openai_to_anthropic`,
  стрим `stream_openai_to_anthropic` (`convert.py`/`streaming.py`). Это
  дефолт для `/v1/messages` — «нулевая настройка» сохраняет прежнее
  поведение 100%.
- **Конверсия `messages → messages`** — сортировка полей: все `role=system`
  переносятся в начало диалога (`normalize_messages_system_first`,
  `convert.py` — перенос без склейки, относительный порядок остальных ролей
  сохраняется), т.к. часть бэкендов (vLLM-шаблон чата) падает 400
  `Jinja Exception: System message must be at the beginning`, когда
  [CC]-сессия несёт system-сообщения по ходу диалога. Включается значением
  `ADAPTER_MESSAGES_TARGET=messages`.
- **Конверсия `responses → responses`** (v0.9.6) — внутренний конвертер
  Responses API: тело проходит через нормализацию (в частности,
  `store` принудительно выставляется в `false` — `force_store_false`,
  `convert.py`; факт правки отмечается в логе строкой `[STORE_ENFORCED]`),
  затем уходит на эндпойнт `responses` бэкенда. Включается значением
  `ADAPTER_RESPONSES_TARGET=responses`. От `passthrough` отличается тем, что
  тело преобразуется (а не идёт дословно) и поддерживает команду `/model`
  (см. §2.5).
- **Passthrough E→E** (`passthrough`) — дословная передача на эндпойнт
  входного формата: `messages→messages`, `completions→completions`,
  `responses→responses`. Тело уходит **без единого преобразования** — в
  частности, для `/v1/messages` с `passthrough` system-сообщения **не**
  переставляются (в отличие от `TARGET=messages`). Ответ и SSE-поток
  возвращаются дословно (`relay_sse`).
- **Запрет входа** — `none` → HTTP **404**.

**Коды ответов при отказе:** нереализованное преобразование → 400
(«conversion … is not implemented»); вход `none` → 404 («endpoint is disabled
(ADAPTER_*_TARGET=none)»); маршрут (passthrough/convert) при подтверждённо не
поддерживающем целевой формат бэкенде → 502 (до отправки запроса; в `.err`
строки Sessions попадает — v0.9.5). Решение принимается **только по кэшу проб**
(`config.endpoint_support` — геттер `_ENDPOINT_STATE`); отсутствие данных
(None) не блокирует — маршрут выбирается оптимистично.

### 2.3 Примеры конфигураций

```bash
# Нулевая настройка (дефолты, можно ничего не задавать): принимается только
# /v1/messages, конвертируется в chat.completions; остальные входы закрыты (404).
export ADAPTER_MESSAGES_TARGET=completions      # = дефолт
# export ADAPTER_COMPLETIONS_TARGET=none        # = дефолт (вход закрыт)
# export ADAPTER_RESPONSES_TARGET=none          # = дефолт (вход закрыт)

# Открыть вход /v1/chat/completions для [OI]-клиента: дословно (passthrough)
# на бэкенд, говорящий на chat.completions.
# export ADAPTER_COMPLETIONS_TARGET=passthrough

# Открыть вход /v1/responses: дословно (passthrough) на бэкенд, говорящий
# на Responses.
# export ADAPTER_RESPONSES_TARGET=passthrough

# /v1/messages: дословно, без сортировки system (в отличие от =messages).
# export ADAPTER_MESSAGES_TARGET=passthrough
```

> **Миграция с версий < 0.9.4.** Раньше целевой формат, равный входу, означал
> passthrough E→E. Теперь это преобразование: `ADAPTER_COMPLETIONS_TARGET=completions`
> и `ADAPTER_RESPONSES_TARGET=responses` дают **400** «not implemented» — замените
> их на `passthrough`. Прежнее `auto` замените на конкретное значение
> (`passthrough` или формат-цель). Дефолт `/v1/messages=completions` не менялся.

Полный env-файл с комментариями всех переменных — `docs/samples/sample.adapter.env`.

### 2.4 Пер-сессионный TARGET (v0.9.5)

TARGET-переменную можно переопределить **для отдельной сессии агента**, не
трогая общую настройку приложения: сессия — единица управления, а не только
наблюдения. Механизм — `session_settings.py` (хранение в памяти процесса,
ключ — `session_id` из колонки «Сессия» таблицы Sessions, т.е. значение
заголовка `ADAPTER_SESSION_HEADER`); потребитель — `routing.decide` /
`routing.target_for_input` при непустом `session_id`.

Настройка живёт в одном из трёх состояний:

| Состояние | Что действует |
|---|---|
| **не задана** (записи нет) | общая настройка приложения `config.ADAPTER_*_TARGET` — сессия «наследует» её, включая последующие изменения через `/config` |
| **`inherit`** | то же самое (взять общее), но запись существует и видна в WEBUI как явное значение |
| **конкретное значение** | собственно переопределение сессии |

Домен значения сессии шире общего: `config.SESSION_TARGET_VALUES =
("inherit", *TARGET_ALLOWED_VALUES)` — те же
`messages | completions | responses | passthrough | none` плюс `inherit`.
Отдельный домен нужен потому, что у сессии «не задано» — это не «`none`»
(выключено), а именно «наследовать»: выпадающий список WEBUI имеет три
положения `inherit | passthrough | none` (или формат-цель).

Переопределения задаются через WEBUI — выпадающий список в колонке «Target»
таблицы Sessions (задача 6) либо POST `/api/sessions/settings`; значения
переживают вытеснение строки из таблицы Sessions (настройка адресуется
сессии, а не строке-кортежу), но не переживают перезапуск адаптера — как и
сама таблица. Селект адресует **ту** переменную, что управляет входом строки
(`routing.target_env_name`), поэтому переопределение `completions`-строки
меняет `ADAPTER_COMPLETIONS_TARGET`, а не `messages`-вход.

Пример: общая настройка `ADAPTER_MESSAGES_TARGET=completions` (дефолт), а
одной сессии нужно дословно — `inherit` остаётся у всех, у неё ставится
`passthrough`; остальные сессии продолжают конвертировать.

### 2.5 Команда `/model` (v0.9.6)

Внутренний конвертер `responses→responses` (значение
`ADAPTER_RESPONSES_TARGET=responses`) добавляет **внутриполосную команду
переключения модели**. Пользователь отправляет обычным сообщением строку
`/model <имя>`; если тело запроса `responses` состоит ровно из этой команды,
адаптер:

1. перехватывает её **до** похода к бэкенду (`convert.detect_model_switch_command`);
2. сохраняет выбранную модель как оверрайд сессии
   (`session_settings.set_model_override(session_id, имя)`) — служебный ключ
   вне `SESSION_CONFIG_POOL`, живёт в памяти процесса и не переживает
   перезапуск (как и остальные пер-сессионные настройки);
3. возвращает **синтетический ack** (не обращаясь к бэкенду): при
   `stream:true` — SSE-поток минимальной формы (`streaming.emit_responses_control_message`),
   иначе — JSON-объект Responses (`streaming.build_responses_control_response`).

Все **последующие** запросы сессии получают оверрайд: если клиент прислал
`model=...`, адаптер подменяет его на сохранённое значение (строка
`[MODEL_OVERRIDE]` в логе). Команда действует, пока её не переключат снова.

Почему свой канал, а не нативный `/model` клиента: на кастомном
`model_provider` Codex CLI нативное переключение модели ненадёжно (баги пикера
моделей и клонирования контекста провайдера при смене модели без рестарта
сессии), поэтому адаптер держит собственный перехватчик.

> **Только для `TARGET=responses`, не для `passthrough`.** Команда работает,
> когда вход `/v1/responses` идёт через **внутренний конвертер**
> (`ADAPTER_RESPONSES_TARGET=responses`). При `passthrough` тело уходит
> дословно — перехвата нет по определению.

Дополнительно конвертер `responses→responses` принудительно выставляет
`store:false` в теле (`convert.force_store_false`; факт правки — строка
`[STORE_ENFORCED]` в логе): Responses API по умолчанию сохраняет ответы на
стороне бэкенда, что для прокси-режима нежелательно.

## 3. Варианты настроек следующих версий (не реализовано сегодня)

> Ниже — **направления развития**, а не текущее поведение. Пока конвертер не
> реализован, соответствующая директива в текущих версиях даёт HTTP 400
> (см. §2.2); матрица в §2.1 актуализируется в той же версии, где пара
> появляется.

1. **Дополнительные пары конверсий** — `completions → messages`,
   `messages → responses`, `completions → responses` и обратные (включая
   оставшуюся self-пару `completions→completions`). Станут доступны с
   реализацией соответствующих конвертеров; появятся в реестре
   `IMPLEMENTED_CONVERSIONS` (`routing.py`) и в матрице §2.1.
   (`responses→responses` реализована в v0.9.6 — см. §2.2 и §2.5.)
2. **Отбор маршрута по доступности эндпоинтов** — сознательно **не**
   реализуется (принцип §1.7): маршрут задаётся директивой, а не живой
   проверкой. Доступность учитывается только через кэш проб — и лишь для
   отказа 502, без сети во время запроса.
3. **Проксирование/балансировка между несколькими бэкендами** — вне
   маршрутизации входов: выбор бэкенда под модель делает
   `config._resolve_backend` (см. `docs/architecture.md` §6.3), а TARGET-
   маршрутизация решает только про формат.

## 4. Поведение, общее для всех входов

Учёт «Models in use» (таблица использованных моделей), strict-проверка
модели (`ADAPTER_STRICT_MODELS`), маппинг моделей, извлечение токенов usage и
`.err`-протокол инцидентов работают на всех трёх входах **одинаково** — после
того как маршрут принят. Отказы маршрутизации (disabled/reject) до учёта
«Models in use» не доходят, но **в счётчик ошибок и `.err` строки таблицы
Sessions попадают** (v0.9.5, задача 7 — см. `docs/logging.md`).
