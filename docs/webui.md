# WEBUI и API — backend-adapter

> Руководство по веб-интерфейсу адаптера: страницы `/` (статус), `/session`
> (просмотр сессий), `/config` (runtime-конфиг), health-эндпоинты
> `/healthz` `/health` `/live` `/ready` и JSON-эндпоинты
> `/api/refresh-state`, `/api/model-usage/reset`, `/api/model-usage/reprobe`,
> `/api/model-usage/delete`, `/api/model-usage/reprobe-state`,
> `/api/model-usage/snapshot`, `/api/sessions/snapshot`. Общее ядро —
> `backend_adapter/webserver.py`; эндпойнт-модули — `webui_status.py`,
> `session_viewer.py`, `webui_config_api.py`, `webui_ops.py`.
> Prometheus-метрики — на отдельном слушателе `prometheus_exporter.py`
> (см. §10). Архитектура — `docs/architecture.md`;
> env-переменные — `docs/environment.md`; конфигурация логирования и `*.parts`
> дампы — `docs/logging.md`.

## 1. Что такое WEBUI

WEBUI — локальный веб-интерфейс адаптера: общее ядро
`backend_adapter/webserver.py` (реестр эндпойнтов, единый HTTP-диспетчер,
`serve()`, CLI) плюс модули-эндпойнты:

| Путь | Модуль | Что показывает |
|---|---|---|
| `/` | `webui_status.py` | Статус: версия кода, режим работы, LLM-бэкенды (доступность, модели, «Доступные API»), секция «Models in use» (live-счётчики), секция «Sessions» (активные сессии агентов, live-счётчики) |
| `/healthz`, `/health` | `webui_ops.py` | Health-check: 200 JSON — процесс жив, сервер отвечает (версия, uptime, pid) |
| `/live` | `webui_ops.py` | liveness (k8s): 200 — процесс жив |
| `/ready` | `webui_ops.py` | readiness (k8s): 200 — бэкенды настроены и кэш моделей непуст; иначе 503 |
| `/session` | `session_viewer.py` | Просмотр `*.parts` сессий: дерево артефактов, вкладки, hash8-адреса, png/puml |
| `/config` | `webui_config_api.py` | Runtime-переключение объёма debug-записи, рубильников и TARGET-маршрутизации входов (форма) |
| `/api/refresh-state` | `webui_status.py` | JSON-состояние фоновой проверки бэкендов (для JS страницы `/`) |
| `/api/model-usage/reset` | `webui_status.py` | Обнуление счётчиков строки таблицы использованных моделей (POST) |
| `/api/model-usage/reprobe` | `webui_status.py` | Фоновая перепроба эндпоинтов строки модели (POST) |
| `/api/model-usage/delete` | `webui_status.py` | Удаление строки модели из таблицы и YAML-файла (POST) |
| `/api/model-usage/reprobe-state` | `webui_status.py` | JSON-состояние перепроверки строки (для JS страницы `/`) |
| `/api/model-usage/snapshot` | `webui_status.py` | JSON-снимок таблицы Models in use (для live-счётчиков страницы `/`) |
| `/api/sessions/snapshot` | `webui_status.py` | JSON-снимок таблицы Sessions — активные сессии агентов (для live-счётчиков страницы `/`) |

Запускается двумя способами:

- **Встроенный запуск** — всегда, в процессе адаптера (v0.8.6; флага
  `ADAPTER_WEBUI_ENABLE` больше нет): `backend-adapter.py` поднимает сервер
  в daemon-потоке через `webserver.serve(root_dir, __version__)`.
  Статус-страница доступна сразу после старта (zero-config), без
  дополнительных действий.
- **Standalone** — отдельный процесс вне адаптера:

  ```bash
  python3 -m backend_adapter.webserver [ROOT_DIR] [--port 8765] [--host 127.0.0.1]
  ```

  Корень по умолчанию — текущая папка. В standalone режиме конфиг-глобалы
  адаптера пусты (адаптер в этом процессе не стартовал) — статус-страница
  показывает режим standalone и подсказку; чтобы получить живые данные,
  задайте `ADAPTER_BACKEND_CONFIG` (путь к YAML) и перезапустите сервер.

Отключить WEBUI нельзя — он поднимается всегда (управляются только порт
`ADAPTER_WEBUI_PORT` и адрес `ADAPTER_WEBUI_HOST`).

### Health-эндпоинты `/healthz` `/health` `/live` `/ready`

На том же слушателе WEBUI живут health-эндпоинты для оркестрации
(k8s probes, скрипты мониторинга) — модуль `webui_ops.py`:

| Эндпоинт | Назначение | Ответ |
|---|---|---|
| `/healthz` (+ алиас `/health`) | Проверка здоровья процесса | 200 `application/json`: `{"status": "ok", "version": "...", "uptime": <сек>, "pid": <pid>}` |
| `/live` | liveness: процесс жив и сервер отвечает | 200, тот же JSON |
| `/ready` | readiness: готов принимать трафик | 200 `{"status": "ready", ...}` если бэкенды настроены (`_BACKENDS` непуст) И кэш моделей непуст (стартовый/последний опрос прошёл — «прогрет»); иначе **503** `{"status": "not_ready", "reason": "..."}` |

Все — только GET; непустой хвост пути (`/healthz/x`) — 404; не-GET метод —
405. `uptime` — секунды с момента импорта модуля. Пример:

```bash
curl -s http://127.0.0.1:8765/healthz
# → 200 {"status": "ok", "version": "0.9.0", "uptime": 1234.5, "pid": 4242}
curl -s http://127.0.0.1:8765/ready
# → 200 {"status": "ready", ...}  — бэкенды настроены и прогреты
# → 503 {"status": "not_ready", ...} — конфиг пуст / кэш моделей пуст
```

Prometheus-метрики — НЕ на WEBUI-порту, а на отдельном слушателе экспортёра
(см. §10).

## 2. Доступ

- Адрес по умолчанию: **`http://127.0.0.1:8765/`**.
- Порт — `ADAPTER_WEBUI_PORT` (по умолчанию `8765`); адрес прослушивания —
  `ADAPTER_WEBUI_HOST` (по умолчанию `127.0.0.1` — только локально).
- **Корень веб-сервера** — директория `ADAPTER_DEBUG_LOGPATH` (по умолчанию
  `./tmp/logs`; там лежат `*.parts` папки сессий и файл `model-usage.yaml`).
  Директория создаётся при старте всегда; вкладка `/session` пуста, пока
  файловая запись выключена (`ADAPTER_DEBUG_ENABLE=0`, per-session логов нет).
- `ADAPTER_WEBUI_HOST=0.0.0.0` открывает доступ из сети — в содержимом сессий
  и логов могут быть чувствительные данные (git log, файлы, reasoning, секреты
  при отключённом санитайзере). Не включайте удалённый доступ без необходимости.

## 3. Страница `/` (статус)

Заголовок страницы — **«Backend-Adapter Version <x.x.x>»** (версия кода из
`context.version` — в адаптере `__version__`). Второй строкой — иконки-
навигация: 🔃 (кнопка POST `/` — проверка бэкендов с перечитыванием
`ADAPTER_BACKEND_CONFIG`, прежняя «⟳ Перепроверить», PRG/303; подпись
«Перепроверить бэкенды» в `title`/`aria-label`), 📋 → `/session`
(Обзор сессий), 🔧 → `/config` (Runtime config). Ниже — таблица бэкендов и
секция «Models in use». В самом низу страницы — ссылка на
GitHub-репозиторий проекта.

### Таблица бэкендов

Колонки: **Backend | Base URL | Status | Endpoints | Models**.

- **Status** — `ok` (на старте опрошен, есть модели) или «не опрошен»; при
  ошибке последней проверки — «недоступен» с текстом ошибки.
- **Endpoints («Доступные API»)** — результат дымовой пробы API-эндпоинтов
  бэкенда по **политике «только явно указанные»**: пробуются только
  эндпоинты, перечисленные в ключе `probe` YAML-записи бэкенда **с непустой
  моделью** (короткие POST `max_tokens:1`; модель пробы — из значения
  `probe.<эндпоинт>`). Неперечисленные эндпоинты, пустое значение (`probe`
  есть, а эндпоинта/модели нет) и бэкенд без ключа `probe` **не пробуются
  вовсе** (см. `docs/environment.md`, §1). Зелёным `✓` показываются
  **только** пути, ответившие HTTP 200; непрошедшие/пропущенные пути на
  странице не показываются. Проба кэшируется ~60 с
  (`ENDPOINT_PROBE_TTL`), отключается `ADAPTER_ENDPOINT_PROBE=0`.
  Помимо фоновой проверки, в кэш `_ENDPOINT_STATE` синхронизируются
  found-эндпоинты дымовых проб **моделей** (первое обращение к модели,
  «Перепроверить» строки, загрузка `model-usage.yaml`, см. §3 «Models in
  use» и §6) — колонка видит и их.
- **Models** — список моделей бэкенда, которые адаптер реально принимает в
  запросах. Если моделей больше 4 — остальные прячутся под кнопку
  «Показать ещё (N)».

Проверка бэкендов (опрос `GET /v1/models` + дымовая проба) — **фоновая**:

- запускается **при старте адаптера**, на **первом** заходе на страницу
  (GET `/`, если проверок ещё не было) и по кнопке-иконке **🔃** (POST `/`,
  подпись «Перепроверить бэкенды» в `title`/`aria-label`);
- кнопка 🔃 не только перепроверяет все настроенные
  бэкенды, но и **перечитывает** файл `ADAPTER_BACKEND_CONFIG` — бэкенды
  добавляются/удаляются в работающем адаптере без рестарта (см.
  `docs/environment.md`, §5). Битый/недоступный YAML — прежние бэкенды
  остаются, в консоль пишется `[WARN]`, фоновая проверка всё равно
  перепроверяет прежних;
- кнопка 🔃 работает по **PRG**: POST отвечает **303 See Other** на GET `/` —
  браузер переходит GET-навигацией, обновление страницы никогда не повторяет
  POST (нет диалога «повторить действие?»);
- пока проверка идёт, страница показывает баннер «Проверка выполняется…» и
  авто-обновляется по завершении: JS опрашивает JSON-эндпоинт
  `/api/refresh-state` каждые ~2 с и делает `location.reload()`;
- футер после проверки — **«Список провайдеров обновлён в HH:MM:SS (N
  провайдеров, M моделей).»** (N — число бэкендов после перечитывания, M —
  моделей в кэше); при провале — «Не удалось обновить список провайдеров…»;
- повторные загрузки страницы (GET) проверку **не запускают** — показывают
  последний результат. Периодического фонового refresh нет.

Провал опроса не роняет страницу: показывается прежний список моделей и текст
ошибки (при полном провале), либо честно без моделей упавшего бэкенда (при
частичном успехе).

### Секция «Models in use»

Секция идёт сразу после футера проверки бэкендов (под таблицей бэкендов),
подписи-комментария перед ней нет. Показывает модели, к которым агент **реально
обращался** (после прохождения строгой проверки), и доступность API-эндпоинтов
бэкенда **именно этой моделью**:

| Модель | Бэкенд | Вызовов | Input | Output | Cost | Endpoints | Actions |
|---|---|---|---|---|---|---|---|

- **Вызовов** — счётчик обращений агента к модели (каждый успешный запрос
  после strict-проверки; недопустимая модель с HTTP 400 не попадает).
- **Input / Output** — токены из usage-блока ответов бэкенда: `Input` —
  сумма `usage.prompt_tokens`, `Output` — сумма `usage.completion_tokens` по
  всем успешным попыткам (включая повторные при сбоях). Ответы **без usage**
  (ошибки 4xx/5xx, обрывы, бэкенд не отдаёт usage) в учёт не попадают.
  Формат — точное число с разделителем тысяч («12 345»); «0» — usage в
  ответе не было. Служебные дымовые пробы эндпоинтов токенов не дают.
- **Cost** — стоимость накопленных токенов строки по тарифу модели на
  **момент отображения** (`ADAPTER_MODELS_TARIFFS`, см. §6 и
  `docs/environment.md`): `Input×цена_входных + Output×цена_выходных`,
  формат «0,25 USD» (запятая — десятичный разделитель). Модели нет в
  тарифах / нулевая цена / токенов ещё нет — серая «—».
- **Endpoints** — одна колонка вместо прежних четырёх: перечисляет **только
  доступные** эндпоинты (ответившие HTTP 200 при дымовой пробе **этой
  моделью**) короткими именами через запятую — например «completions,
  responses». Порядок — как в `config.ENDPOINT_PROBES`. Ничего доступного /
  не пробовано / `ADAPTER_MODEL_USAGE_ENABLE=0` — серая «—». Повторные
  обращения никогда не перепроверяют (только инкремент счётчика); обновить
  результат строки без сброса — кнопка ⟳ (см. §6, `/api/model-usage/reprobe`).
- **Actions** — кнопки-иконки строки модели (символьные, с подписью-подсказкой
  в `title`/`aria-label` при наведении):
  - **⟳ Перепроверить** — фоновая перепроба эндпоинтов этой моделью;
  - **↺ Сбросить** — обнуление счётчиков строки: Вызовов/Input/Output → 0
    (строка с моделью, бэкендом и результатами пробы эндпоинтов остаётся —
    см. §6);
  - **✕ Удалить** — удаление строки модели: модель исчезает из рабочей
    таблицы **и из YAML-файла** (`model-usage.yaml` перезаписывается без
    строки; счётчики строки при этом теряются — действие необратимо,
    кнопка красная — см. §6).

  Пока перепроверка строки идёт, вместо кнопок — серый текст «проверяется…».

**Live-счётчики.** Колонки «Вызовов/Input/Output» обновляются **без
перезагрузки страницы**: пока вкладка открыта, JS `usage_poll` каждые ~5 с
опрашивает лёгкий JSON-эндпоинт `/api/model-usage/snapshot` (см. §6) и
обновляет только ячейки счётчиков. Строки сопоставляются по порядку
(рендер и снимок идут в порядке первого обращения); строка удалена / новая
модель появилась — страница перезагрузится сама (редкое событие).
Колонка **Cost** ставится тем же поллингом через `innerHTML` (`setHtml`):
значение приходит со снимком как готовый HTML (`cost_html` — серверный
рендер `_cost_cell_html`, единый для страницы и снимка), чтобы «—»
отображалась серой разметкой, а не буквальным текстом; счётчики —
через `textContent` (см. §1, фикс v0.9.0). Если значение ячейки не
изменилось, DOM не трогается. Оверхед поллинга — один маленький JSON-ответ
раз в 5 с на открытую вкладку; сеть к бэкендам счётчики не гоняют; при
скрытой вкладке браузер сам замедляет таймеры (трафика почти нет).

Таблица **персистентна**: сохраняется между запусками адаптера в файле
`model-usage.yaml` в корне WEBUI (см. §7) и переживает перезапуски — после
рестарта страница сразу показывает прошлые строки без новых запросов.
`ADAPTER_MODEL_USAGE_ENABLE=0` — пробы и накопление токенов отключены, учёт
обращений остаётся (колонка Endpoints «—», Input/Output «0»);
персистентность работает независимо от мастер-флага.

### Секция «Sessions»

Секция идёт ниже таблицы «Models in use». **Строка = кортеж** значений
первых пяти колонок — `(session, agent, model, backend, route)` — то есть
закреплённое соответствие «кто (агент) чем (модель) через какого
обработчика (бэкенд + маршрут) пользуется в рамках сессии». Смена любого
элемента кортежа — **новое событие** и **новая строка**; три последние
колонки не порождают строк, а лишь сопровождают уже описанный кортеж:

| Сессия | Агент | Модель | Бэкенд | Маршрут | Последнее обращение | Вызовов | Ошибок |
|---|---|---|---|---|---|---|---|

- **Сессия** — идентификатор клиентской сессии (заголовок
  `X-Claude-Code-Session-Id`): первые 8 символов в `<code>`, полный id — в
  подсказке (`title`) и в атрибуте `data-session` строки.
- **Агент** — заголовок `User-Agent` до первого пробела ([CC] CLI шлёт
  `claude-cli/2.1.236 (external, cli)` → в колонке `claude-cli/2.1.236`).
- **Модель / Бэкенд / Маршрут** — клиентское имя модели (до маппинга, как в
  «Models in use»), имя бэкенда и выбранное правило TARGET-маршрутизации
  (`passthrough messages→messages`, `convert messages→completions`,
  `reject`, `disabled` — см. `docs/routing.md`). Фиксируются в момент
  запроса; показываются и при `reject`/`disabled` — видно, куда агент
  пытался попасть. Запрос, отвергнутый **до** `routing.decide` (400
  валидации тела), даёт строку с пустыми этими тремя полями.
- **Последнее обращение** — дата-время последнего запроса этого кортежа
  (`YYYY-MM-DD HH:MM:SS`).
- **Вызовов** — счётчик обращений этого кортежа (растёт на каждый запрос,
  включая не дошедшие до бэкенда: 400 валидации тела тоже учтены).
- **Ошибок** — счётчик финальных HTTP-ответов **≥ 400** по этому кортежу
  (400 валидации, 404/400 `disabled`/`reject`, 4xx/5xx бэкенда после
  ретраев).

**Пример.** Сессия начала работу на модели `m1`, затем агент переключился на
`m2`, потом вернулся на `m1`: в таблице **две** строки — `m1` (Вызовов 2) и
`m2` (Вызовов 1). Смена настроек входного эндпойнта (правило TARGET),
изменившая обработчика трафика, тоже даёт новую строку, даже если модель та
же. Возврат к уже встречавшемуся кортежу новую строку **не** создаёт —
инкрементится `calls` той же строки.

Строки сортируются по времени последнего обращения — **новые сверху**, при
новом обращении строка всплывает наверх. Глубина таблицы ограничена
`ADAPTER_SESSIONS_TABLE` (дефолт 10; `0` — таблица отключена): лимит считает
**строки** (кортежи), а не сессии, — при регистрации обращения самая старая
строка вытесняется. Таблица живёт **только в памяти процесса** — каждый
запуск адаптера начинает её заново (персистентности нет, в отличие от
`model-usage.yaml`); модуль — `backend_adapter/session_registry.py`.

**Live-обновление.** Колонки обновляются **без перезагрузки страницы**:
JS `sessions_poll` каждые ~5 с опрашивает `/api/sessions/snapshot` (см. §6)
и обновляет текстовые ячейки. Одна сессия может занимать несколько строк,
поэтому строки сопоставляются **по `data-key`** — компактной JSON-строке
кортежа (та же строка приходит в поле `key` снимка), а не по `data-session`:
`session` не уникален, а позиционное сопоставление сломалось бы при всплытии
строки. Если состав строк не совпал (новая строка или эвикция по глубине) —
страница перезагружается сама (заодно перерисовывается корректный порядок).
Сеть к бэкендам поллинг не гоняет; скрытую вкладку браузер троттлит.

## 4. Страница `/session` (просмотр сессий)

Дерево артефактов по `*.parts`-дампам каждой сессии (`artefacts/tree.html`),
вкладки по сессиям, раздача файлов. Детали — в `docs/logging.md`, секция
«Просмотр сессий в браузере», и `docs/architecture.md`:

- дерево генерируется **на лету** и инкрементально (чекпоинт
  `artefacts/.build_state.json` — пересобираются только новые `*.parts`);
- большие сессии разбиваются на страницы пагинации —
  `artefacts/pages/<N>/tree.{html,puml,png}` + сводный `artefacts/pages/index.html`;
- короткие адреса: hash8 из имени папки сессии —
  `/session/<hash8>/<rel_path>`; дерево как картинка/PlantUML-исходник —
  `/session/<session_id|hash8>/png` и `/puml` (с `?page=N` — страницу пагинации);
- активная вкладка запоминается в `location.hash` — после обновления страницы
  открывается та же вкладка.

В левом краю панели вкладок — обратная ссылка **«Статус 📊»** на корень
сервера (статус-страницу `/`) и **«Runtime config 🔧»** на `/config` — чтобы
после просмотра сессий возвращаться к списку бэкендов и моделей одним
кликом.

`/session` доступен только когда задан `ADAPTER_DEBUG_LOGPATH` (есть что
показывать); при zero-config вкладка пуста.

## 5. Страница `/config` (runtime-конфиг)

Форма переключения на **работающем** адаптере узкого пула переменных
(`RUNTIME_CONFIG_POOL` в `config.py`) — без перезапуска. GET `/config` —
форма с текущими значениями; POST применяет валидные значения через
`config.set_runtime_config()` и показывает, что применилось (неверные типы и
неизвестные ключи игнорируются).

Пул — 12 переменных:

- **bool (6)** — файловая запись и per-session дампы: `ADAPTER_DEBUG`
  (файл `session-*.log` — полные строки, без обрезки; консоль — всегда,
  с обрезкой `ADAPTER_DEBUG_TRIM`), `ADAPTER_DEBUG_PARTS` (дампы `.json`+
  `.yaml` всех логгируемых частей); рубильники поведения новых запросов и
  логов: `ADAPTER_SENSITIVE_LOGGING_ENABLE` (отключение санитайзера —
  секреты в открытом виде), `ADAPTER_STREAMING_ENABLE`,
  `ADAPTER_STREAM_INCLUDE_USAGE`, `ADAPTER_STRICT_MODELS`;
- **int (3)** — лимиты обрезки: `ADAPTER_DEBUG_TRIM` (консоль; `0` — без
  обрезки), `ADAPTER_TRACE_REASONING_MAX_CHARS`,
  `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS`;
- **enum (3)** — TARGET-маршрутизация входов (v0.9.1): `ADAPTER_MESSAGES_TARGET`,
  `ADAPTER_COMPLETIONS_TARGET`, `ADAPTER_RESPONSES_TARGET` — выпадающие списки
  из домена `messages | completions | responses | auto | none` (какой формат
  отдавать бэкенду для запросов соответствующего входа; полная семантика
  значений — [`docs/routing.md`](routing.md)). Текущее значение подсвечено
  в списке.

Читатели пула обращаются к `config.ADAPTER_X` «на лету» — изменения видны на
следующем же запросе/вызове (маршрут каждого запроса решается по актуальному
TARGET). На лету **нельзя** менять: сеть и адреса
прослушивания, бэкенды (`ADAPTER_BACKEND_CONFIG`, `ADAPTER_MODELS_MAPPING`),
таймауты/ретраи, `ADAPTER_DEBUG_LOGPATH`, `ADAPTER_MODEL_USAGE_ENABLE`,
порты и `ADAPTER_WEBUI_*` — они влияют на активные соединения, раскладку
файлов или структуру конфигурации.

В шапке страницы `/config` — обратные ссылки **«Статус 📊»** (на `/`) и
**«Обзор сессий 📋»** (на `/session`).

## 6. JSON-эндпоинты

### `/api/refresh-state` — состояние фоновой проверки (GET)

Лёгкий JSON-ответ для JS `status_poll` на статус-странице. GET проверку не
запускает и ничего не мутирует — безопасно опрашивать каждые 2 с:

```json
{
  "running": false,
  "started_at": 1725600000.0,
  "done_at": 1725600005.0,
  "ok": true,
  "count": 3,
  "errors": {},
  "checked_at": "14:32:05"
}
```

Поля: `running` (идёт ли проверка), `started_at`/`done_at` (time.time),
`ok`/`count`/`errors` (итог последней `refresh_models`), `checked_at`
(«HH:MM:SS» завершения). До первой проверки — дефолт-словарь (все None/False).

### `/api/model-usage/reset` — обнуление счётчиков строки (POST)

**`POST /api/model-usage/reset?model=<имя>`** обнуляет счётчики строки модели
в таблице использованных моделей: `calls`/`input_tokens`/`output_tokens` →
0. Строка (модель, бэкенд, результаты пробы эндпоинтов) **остаётся** в
таблице и в YAML-файле — «Сбросить» очищает накопленные счётчики, а не
удаляет модель (полного сброса таблицы не предусмотрено — только по одной
модели; повторные обращения к модели после сброса не делают новую пробу —
строка существует, fast-path).

JSON-клиент (`Content-Type: application/json`):

```bash
# Обнулить счётчики модели (200 — сброшено)
curl -X POST -H 'Content-Type: application/json' \
  'http://127.0.0.1:8765/api/model-usage/reset?model=qwen3.6-35b-a3b'
# → 200 {"ok": true, "model": "qwen3.6-35b-a3b"}

# Повторный сброс той же модели — 200 (строка жива, счётчики уже 0);
# модели нет в таблице — 404 {"error": "model 'ghost' not in usage table"}

# Без query-параметра model (400)
curl -X POST -H 'Content-Type: application/json' \
  'http://127.0.0.1:8765/api/model-usage/reset'
# → 400 {"error": "missing 'model' query parameter"}
```

Кнопка **«Сбросить» (↺)** в строке таблицы на странице `/` — HTML-форма без JSON
Content-Type: обнуление + **303 See Other** на GET `/` (PRG, как у кнопки
🔃 проверки бэкендов). После обнуления файл `model-usage.yaml`
перезаписывается сразу.

GET на префикс — 404. Формат ошибки — единый `{"error": ...}` (как в
`server.py`).

### `/api/model-usage/reprobe` — фоновая перепроба строки модели (POST)

**`POST /api/model-usage/reprobe?model=<имя>`** повторяет дымовую пробу
эндпоинтов бэкенда **именно этой моделью** по политике «только явно
указанные» (пробуются только эндпоинты из ключа `probe` YAML-записи бэкенда
с непустой моделью — см. §3 и `docs/environment.md` §1) для строки таблицы
использованных моделей — для строк с колонками «—» (первый запрос был давно
/ бэкенд ожил / модель появилась в `/v1/models`). Обновляет только
`endpoints`/`errors` строки (и имя бэкенда, если резолв сменился); счётчик
`calls` и токены **не сбрасываются и не растут** (проба — служебный запрос,
не обращение агента). Найденные перепробой эндпоинты (HTTP 200)
синхронизируются в кэш `config._ENDPOINT_STATE` бэкенда — их видит колонка
«Доступные API» бэкенда и экспортёр. Перепроверка выполняется **в фоновом
потоке** — ответ приходит сразу, строка на это время показывает
«проверяется…».

JSON-клиент (`Content-Type: application/json`):

```bash
# Запустить перепроверку строки модели (202 — запущено в фоне)
curl -X POST -H 'Content-Type: application/json' \
  'http://127.0.0.1:8765/api/model-usage/reprobe?model=qwen3.6-35b-a3b'
# → 202 {"ok": true, "model": "qwen3.6-35b-a3b"}

# Строки нет в таблице или перепроверка этой модели уже идёт (404)
curl -X POST -H 'Content-Type: application/json' \
  'http://127.0.0.1:8765/api/model-usage/reprobe?model=ghost'
# → 404 {"error": "model 'ghost' not in usage table or already reprobing"}

# Без query-параметра model (400)
curl -X POST -H 'Content-Type: application/json' \
  'http://127.0.0.1:8765/api/model-usage/reprobe'
# → 400 {"error": "missing 'model' query parameter"}
```

Кнопка **⟳ («Перепроверить»)** в колонке Actions строки таблицы — HTML-форма
без JSON Content-Type: старт + **303 See Other** на GET `/` (PRG). Пока
перепроверка идёт, страница показывает баннер «⟳ Перепроверка модели X…» и
авто-обновляется по завершении (JS опрашивает `/api/model-usage/reprobe-state`
каждые ~2 с — как у проверки бэкендов, см. §3). Результат пробы сохраняется
в `model-usage.yaml` сразу по завершении.

### `/api/model-usage/delete` — удаление строки модели (POST)

**`POST /api/model-usage/delete?model=<имя>`** удаляет строку модели из
таблицы использованных моделей и **из YAML-файла**: `model-usage.yaml`
перезаписывается сразу обновлённой таблицей без указанной строки. Действие
необратимо — накопленные счётчики/токены строки и результаты пробы
эндпоинтов теряются (удалить счётчики, сохранив строку, — кнопка ↺
«Сбросить»; обновить пробу без потери счётчиков — ⟳ «Перепроверить»).
Бэкенд в таблице бэкендов и его модели при этом не трогаются; кэш
доступности эндпоинтов (`config._ENDPOINT_STATE`) — общий на бэкенд, не по
моделям — не чистится.

JSON-клиент (`Content-Type: application/json`):

```bash
# Удалить строку модели (200 — удалено; строки больше нет ни в памяти, ни в файле)
curl -X POST -H 'Content-Type: application/json' \
  'http://127.0.0.1:8765/api/model-usage/delete?model=qwen3.6-35b-a3b'
# → 200 {"ok": true, "model": "qwen3.6-35b-a3b"}

# Повторное удаление той же модели — 404 (строки уже нет; в отличие от reset,
# delete НЕ идемпотентен); модели нет в таблице — 404
#   → 404 {"error": "model 'ghost' not in usage table"}

# Без query-параметра model (400)
curl -X POST -H 'Content-Type: application/json' \
  'http://127.0.0.1:8765/api/model-usage/delete'
# → 400 {"error": "missing 'model' query parameter"}
```

Кнопка **✕ («Удалить»)** в колонке Actions строки таблицы на странице `/` —
HTML-форма без JSON Content-Type: удаление + **303 See Other** на GET `/`
(PRG; после перехода строка исчезает со страницы — повторный клик
невозможен). Файл перезаписывается сразу. Кнопка красная — деструктивное
действие.

GET на префикс — 404. Формат ошибки — единый `{"error": ...}` (как в
`server.py`).

### `/api/model-usage/reprobe-state` — состояние перепроверки (GET)

Лёгкий JSON-ответ для JS `reprobe_poll` на статус-странице (аналог
`/api/refresh-state`, но состояние живёт в `model_usage`, а не в
`config.refresh_state`). GET ничего не мутирует — безопасно опрашивать
каждые 2 с:

```json
{
  "running": true,
  "model": "qwen3.6-35b-a3b",
  "started_at": 1725600000.0
}
```

Поля: `running` (идёт ли перепроверка), `model` (имя перепроверяемой строки),
`started_at` (time.time запуска). В покое — `{"running": false, "model": null,
"started_at": null}`.

### `/api/model-usage/snapshot` — снимок таблицы Models in use (GET)

Лёгкий JSON-ответ для JS `usage_poll` на статус-странице (live-счётчики, §3):
`model_usage.usage_snapshot()` — список строк таблицы в порядке первого
обращения. GET ничего не мутирует (кроме ленивой загрузки таблицы при первом
обращении) и **не ходит в сеть к бэкендам** — безопасно опрашивать каждые 5 с:

```bash
curl 'http://127.0.0.1:8765/api/model-usage/snapshot'
```

```json
[
  {
    "model": "qwen3.6-35b-a3b",
    "backend": "home",
    "calls": 42,
    "input_tokens": 1523400,
    "output_tokens": 812345,
    "endpoints": {
      "completions": {"status": 200, "found": true},
      "messages": {"status": 200, "found": true}
    },
    "errors": {},
    "first_seen": "14:32:05",
    "probing": false,
    "cost_html": "<span style=\"color:#aaa\">—</span>"
  }
]
```

Токены в ответе — точные числа (без разделителя тысяч; форматирование — на
стороне JS, как в ячейках страницы). `cost_html` — **готовый HTML** ячейки
Cost на текущий момент (`_cost_cell_html`: серая «—» для 0 токенов/модели
без тарифа, «0,25 USD»-строка для суммы — единый источник с серверным
рендером); JS `usage_poll` ставит его в ячейку через `innerHTML` (`setHtml`),
а не `textContent` — чтобы «—» отображалась серой разметкой, а не
буквальным текстом. Пустая таблица — `[]`.

### `/api/sessions/snapshot` — снимок таблицы Sessions (GET)

## 7. Файл `model-usage.yaml`

Персистентное хранилище таблицы использованных моделей.

**Расположение** — корень WEBUI: `ADAPTER_DEBUG_LOGPATH` (дефолт `./tmp/logs`).
Встроенный запуск кладёт файл в корень автоматически
(синхронизация в `webserver.serve()`); standalone
(`python -m backend_adapter.webserver [ROOT]`) — в явно указанный корень.

**Формат** — YAML с **версией формата** (`version: 2` в корне) и строками под
ключом `models`:

```yaml
version: 2
models:
  qwen3.6-35b-a3b:
    model: qwen3.6-35b-a3b
    backend: home
    calls: 42
    input_tokens: 1523400
    output_tokens: 812345
    endpoints:
      completions: {status: 200, found: true}
      messages: {status: 200, found: true}
    errors: {}
    first_seen: "14:32:05"
    probing: false
```

Семантика:

- **версия формата** — обязательное поле `version` в корне; при изменении
  формата версия повышается. Читатель принимает только известные версии:
  файл с незнакомой версией (> 2) игнорируется (таблица стартует пустой) и
  будет перезаписан первым сохранением. Плоский формат без `version`/`models`
  читается как легаси;
- **миграция v1** — файл формата `version: 1` (учёт в байтах: поля
  `bytes_sent`/`bytes_recv`) при загрузке НЕ игнорируется: строки читаются,
  `calls`/`endpoints`/`errors`/`first_seen` сохраняются, байтовые поля
  отбрасываются, токены `input_tokens`/`output_tokens` стартуют с 0;
  следующее сохранение переписывает файл в `version: 2`;
- **автосброса нет** — счётчики и токены накапливаются от запуска к запуску;
  очистить накопленное по строке можно кнопкой «Сбросить» (↺) или
  `POST /api/model-usage/reset` (обнуляет счётчики, строку не удаляет);
  обновить результаты проб без сброса — кнопкой «Перепроверить» (⟳) или
  `POST /api/model-usage/reprobe`; убрать строку из таблицы и файла целиком —
  кнопкой «Удалить» (✕) или `POST /api/model-usage/delete`;
- **загрузка при старте** — ленивая, при первом обращении к таблице: файл
  читается один раз, строки нормализуются (`probing` всегда False, счётчики —
  неотрицательные int, незнакомые имена эндпоинтов/ключи отбрасываются).
  Повреждённый/битый YAML игнорируется (лог `ignoring unreadable file`,
  таблица пуста, файл перезапишется первым сохранением);
- **загруженные строки не перепроверяются** — повторное обращение к известной
  модели идёт по fast-path (инкремент счётчика), результаты проб эндпоинтов
  из файла могут устареть (осознанно). «Освежить» результаты пробы: кнопка
  «Перепроверить» (перепроба без потери счётчиков). При загрузке found-
  эндпоинты строк (для бэкендов из текущего `ADAPTER_BACKEND_CONFIG`)
  синхронизируются в кэш `config._ENDPOINT_STATE` — колонка «Доступные API»
  бэкенда и экспортёр видят их сразу, без сети (перепробы при загрузке нет);
- **период сохранения** — `ADAPTER_MODEL_USAGE_SAVE_INTERVAL` (сек, дефолт
  **300**): «грязная» таблица сохраняется не чаще раза в период. Создание
  новой строки модели, обнуление счётчиков строки (кнопка «Сбросить» /
  `POST /api/model-usage/reset`) и завершение работы адаптера (в т.ч.
  Ctrl-C — `flush_table`) сохраняют сразу. При жёстком kill (kill -9) потеря
  хвоста ≤ периода; при штатном завершении таблица сохраняется всегда;
- **строки с `probing: True` на диск не попадают** — крах во время первой
  синхронной пробы новой модели теряет только саму новую строку;
- запись атомарная: временный файл в той же директории + `os.replace`.

## 8. Советы

- **Мониторинг фактического использования** — секция «Models in use»
  показывает, какие модели агент реально зовёт (а не какие бэкенд
  *принимает*), сколько раз и сколько токенов usage (Input/Output) по каждой.
  Счётчики переживают рестарты — таблицу удобно проверять периодически,
  накопленные токены — фон для оценки расходов; при открытой странице
  счётчики обновляются сами (live, §3).
- **Диагностика доступности эндпоинтов по модели** — колонка Endpoints
  отвечает на вопрос «какие из `/v1/chat/completions`, `/v1/messages`,
  `/v1/responses`, `/v1/embeddings` работают именно для этой модели?»
  (у бэкенда с несколькими моделями доступность может различаться; в строке —
  только доступные). Первый запрос новой модели делает синхронную пробу
  (до 4×10 с) — строка появляется с результатом; повторные запросы накладных
  расходов не несут.
- **Когда жать «Перепроверить»** — строка с устаревшими колонками «—»
  (бэкенд был недоступен при первом обращении / ожил / модель появилась в
  `/v1/models`): перепроба эндпоинтов (по probe-перечню бэкенда) именно этой
  моделью в фоне, без потери счётчиков и без рестарта. Пока перепроверка
  идёт, строка показывает «проверяется…» и страница обновится сама.
- **Когда жать «Сбросить»** — очистить накопленные счётчики/токены одной
  модели (Вызовов/Input/Output → 0), чтобы считать расход заново. Строка с
  моделью, бэкендом и результатами пробы эндпоинтов остаётся (полного
  сброса таблицы не предусмотрено).
- **Когда жать «Удалить»** — строка модели больше не нужна (модель
  выведена из эксплуатации, строка-«мусор»): убрать её из таблицы и из
  `model-usage.yaml`. Действие необратимо — счётчики и результаты пробы
  строки теряются; сам бэкенд и его модели в таблице бэкендов не
  затрагиваются. Повторное обращение к удалённой модели создаст строку
  заново (с новой пробой эндпоинтов).
- **Сочетание с `ADAPTER_MODEL_USAGE_ENABLE`** — `0` отключает пробы и
  накопление токенов, но учёт обращений и персистентность остаются; колонки
  эндпоинтов показывают «—». Переменная в runtime-пул `/config` не входит —
  меняется только перезапуском.

## 9. Troubleshooting

| Симптом | Причина и решение |
|---|---|
| Страница не открывается на `8765` | Порт занят. Проверьте занятость (`lsof -i :8765`), смените `ADAPTER_WEBUI_PORT`. WEBUI поднимается всегда — флага отключения нет. |
| Вкладка `/session` пуста | Нет per-session логов: задайте `ADAPTER_DEBUG_LOGPATH` (там лежат `*.parts` папки) и включите файловую запись `ADAPTER_DEBUG_ENABLE=1`, затем перезапустите; при zero-config (`ADAPTER_DEBUG_ENABLE=0`) сессий в корне нет. |
| Статус-страница показывает «standalone» и подсказку | Сервер запущен вне процесса адаптера (`python -m backend_adapter.webserver`) и не видит данные: задайте `ADAPTER_BACKEND_CONFIG` (путь к YAML) и перезапустите, либо используйте встроенный запуск в адаптере. |
| Секция «Models in use» пуста | Модели не проходили strict-проверку (HTTP 400 в таблицу не попадает), либо `ADAPTER_MODEL_USAGE_ENABLE=0`, либо запросов ещё не было. Проверьте, что модель есть в списке бэкенда на странице `/`. |
| `model-usage.yaml` не обновляется | Корень WEBUI недоступен для записи (read-only директория). Путь файла — корень WEBUI (см. §7); при ошибке записи адаптер логирует `failed to save` и продолжает учёт в памяти. |
| Файл `model-usage.yaml` повреждён/битый | Игнорируется при загрузке (таблица стартует пустой, лог `ignoring unreadable file`); будет перезаписан первым сохранением. Удалите файл, чтобы начать с чистой таблицы. |
| После рестарта таблица пуста | Файл лежит не там, где ожидает адаптер (сменился `ADAPTER_DEBUG_LOGPATH`/рабочая папка), либо у файла незнакомая версия формата. Проверьте путь: корень WEBUI (см. §7). |
| После «Сбросить» счётчики строки — 0, но строка осталась | Так и задумано: «Сбросить» обнуляет счётчики (Вызовов/Input/Output), а не удаляет модель. Убрать строку целиком — «Удалить» (✕) / `POST /api/model-usage/delete`. Результаты пробы эндпоинтов строка не теряет (обновить их — «Перепроверить»). Следующее обращение к модели начнёт копить счётчики заново (без новой пробы). |

## 10. Prometheus-экспортёр (`ADAPTER_EXPORTER_ENABLE`)

**Отдельный** лёгкий HTTP-слушатель (модуль `backend_adapter/prometheus_exporter.py`,
stdlib-only) на порту `ADAPTER_EXPORTER_PORT` (дефолт **9100**) и адресе
`ADAPTER_WEBUI_HOST`. Поднимается вместе с WEBUI при
`ADAPTER_EXPORTER_ENABLE=1` (значение по умолчанию). Отдаёт метрики **текстом
text exposition format 0.0.4** — `GET /metrics` (`GET /` — то же самое,
прочие пути — 404), без внешних библиотек и без клиентских библиотек
Prometheus:

```bash
curl -s http://127.0.0.1:9100/metrics
```

Свой слушатель, а не эндпоинт WEBUI: повторный `serve()` общего ядра
перезаписал бы контекст и открыл бы весь WEBUI на порту экспортёра, а
`/metrics` не должен висеть на порту статуса.

Группы метрик (источники — живые конфиг-глобалы, те же, что у страницы `/`):

- **настройки/статус приложения** — `backend_adapter_info{version="..."}`,
  `backend_adapter_build_info`, `backend_adapter_uptime_seconds` (с момента
  импорта модуля экспортёра), `backend_adapter_backends_configured` (число
  бэкендов из `_BACKENDS`), `backend_adapter_models_available` (модели в
  кэше `_AVAILABLE_MODELS`);
- **по бэкенду** (label `name`, `base`): `backend_adapter_backend_up` (1 —
  бэкенда нет в ошибках снимка последней проверки, 0 — не смог отдать
  `/v1/models`), `backend_adapter_backend_models` (число моделей бэкенда в
  `_MODEL_TO_BACKEND`), `backend_adapter_backend_endpoint{endpoint="completions"
  |"messages"|"responses"|"embeddings"} 1/0` — по `config._ENDPOINT_STATE`
  (единый источник, куда синхронизируются и found-эндпоинты проб моделей);
- **по использованной модели** (label `model`, `backend`):
  `backend_adapter_model_calls_total`,
  `backend_adapter_model_input_tokens_total`,
  `backend_adapter_model_output_tokens_total` — счётчики из таблицы Models in
  use (см. §3/§6; чтение — `model_usage.usage_snapshot()`).

Label-значения (имена бэкендов/моделей) экранируются по правилам text format
(`\\`, `"`, перевод строки). Не-GET методы — 501 дефолтом. Отключить —
`ADAPTER_EXPORTER_ENABLE=0` (экспортёр не должен ронять адаптер: занятый порт
→ строка `[EXPORTER] Failed to bind ...` в консоли, остальное работает).
