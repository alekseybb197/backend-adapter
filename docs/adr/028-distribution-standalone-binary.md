# ADR-028: Поставка — standalone-бинарник и один путь установки

| Поле | Значение |
|---|---|
| Статус | Действует (v0.7.3); упрощено в v0.9.2; CLI и шаблоны — v0.9.11–v0.9.13 |
| Тип решения | deliberate (записано) |
| Уверенность | high (что); medium (почему бинарник) |
| Источник рационала | changelog v0.8.0 (сводка), v0.9.11, v0.9.12; сообщение `cd4e15b` |

## Контекст

Пользователь адаптера — разработчик, которому нужен локальный сервис рядом с
агентом, без настройки Python-окружения.

## Решение

- **PyInstaller `--onefile`**: бинарники собираются CI по тегу
  (`release-binaries.yml`): Linux, macOS (arm64), Windows. Сборка macOS x64
  убрана (`e068da2`).
- **Один путь установки** (`cd4e15b`): `install.sh` скачивает только бинарник
  последнего релиза в фиксированный каталог (Linux — `/usr/local/bin`, macOS —
  `~/.local/bin`). Удалены варианты `--pip`, `--prefix`, `INSTALL_DIR`.
  Windows-bash — явный отказ. Опции: `--service` (systemd), `--delete`,
  `--check`; повторная установка — корректное обновление.
- **Шаблоны конфигов встроены в пакет** (`templates.py`, v0.9.12): в
  бинарнике и wheel нет `docs/samples/`. Образцы в `docs/samples/` остаются
  справочными; совпадение байт-в-байт проверяет тест.
- **CLI разбирается до валидации env и импорта `config`** (v0.9.11):
  `--version`/`--help` отвечают при любом окружении; разбор argv ручной, не
  `argparse` (нужен `-?`); неизвестный ключ — `[FATAL]`, код 2 («молча
  проглоченный ключ у сервиса опасен»).
- Запуск из исходников сохраняется (`pip install -r requirements.txt`,
  `scripts/dev-run.sh`).

## Рассмотренные альтернативы

- Установка через pip/venv (`--pip`). Удалена в `cd4e15b` («убраны
  альтернативные сценарии»).
- Контейнерный образ. Не обнаружен в репозитории.

## Следствия

- Код должен работать из PyInstaller: отсюда встроенные шаблоны,
  `--bootloader-ignore-signals` (ADR-026), отсутствие рантайм-чтения
  `docs/`.
- `install.sh` и бинарник — два исполнителя установки, формат YAML бэкенда
  поддерживается в обоих синхронно (`write_backend_yaml` ↔
  `templates.render_adapter_yaml`).
- `install.sh` покрыт molecule-сценариями только для Ubuntu 24.04; macOS-путь
  не тестируется автоматически.

## Обнаруженный дефект (подтверждён на релизе v1.0.0)

Цель `linux-arm64` в `release-binaries.yml` собирается на раннере
`ubuntu-latest` (x86-64) обычным `pyinstaller --onefile`. PyInstaller не
выполняет кросс-сборку, поэтому под именем `backend-adapter-linux-arm64`
публикуется **x86-64**-бинарник. Health check в CI проходит именно потому,
что x86-64 запускается на x86-64-раннере.

Проверка: первые 64 байта опубликованных ассетов v1.0.0 —
`backend-adapter-linux-arm64` и `backend-adapter-linux-x64` оба имеют
`e_machine = 0x3E` (x86-64). `install.sh` отдаёт этот файл хостам
`aarch64|arm64`, где он завершится `exec format error`. Дефект присутствует с
`38e530a` (v0.7.3).

Это пример «accidental»-решения: архитектура заявлена, но фактически не
реализована. Исправление — раннер `ubuntu-24.04-arm` (или эквивалент) для
цели `linux-arm64` и проверка архитектуры (`file`) в health check.

## Ответ автора (2026-10-10)

- macOS x64 убрана из-за проблем с раннерами GitHub и невостребованности.
- Вопрос установки через pip отложен (согласуется с ADR-016: публикация в
  PyPI — задача последнего порядка).

## Уточнение к дефекту arm64 (требует ответа)

В ответе на п. 25 сказано «бинарник x86 для macOS не нужен». Дефект касается
**Linux**, не macOS: файл `backend-adapter-linux-arm64` в релизе — это
x86-64. macOS-сборка (`macos-arm64`, раннер `macos-latest`) корректна.
Варианты:

1. **Linux arm64 нужен** — собирать на раннере `ubuntu-24.04-arm` и
   проверять архитектуру в health check (`file dist/backend-adapter | grep
   -q aarch64`).
2. **Linux arm64 не нужен** — убрать цель из матрицы и строку
   `aarch64|arm64) echo "linux-arm64"` из `install.sh`, чтобы ARM-хост
   получал понятное «Unsupported platform», а не нерабочий бинарник.

В любом варианте уже опубликованный ассет v1.0.0 стоит удалить из релиза.
