# ADR-013: Конвертер Responses API и внутриполосная команда `/model`

| Поле | Значение |
|---|---|
| Статус | Принято (v0.9.6 — `responses→responses`; v0.9.7 — `responses→completions`) |
| Тип решения | deliberate (записано) |
| Уверенность | high |
| Источник рационала | changelog v0.9.6, v0.9.7; комментарии `routing.py`; `docs/routing.md` §2.5, `docs/codex.md` §7 |

## Контекст

Codex CLI говорит только на Responses API. Бэкенд может не иметь
`/v1/responses`. Кроме того, нативный `/model` Codex ненадёжен на
пользовательских `model_provider`.

## Решение

- **`responses→completions`** — отдельный полный конвертер (не общий с
  `messages→completions`: иная входная форма). `instructions` и `developer`
  схлопываются в одно system (ADR-007); `function_call`/`function_call_output`
  ↔ `tool_calls`/`role=tool`; `reasoning`-элементы пропускаются. Ответ и стрим
  пересобираются в Responses-объект и события.
- **`call_id` без реестра на стороне адаптера:** клиент сам эхует его в
  `function_call_output`, поэтому кросс-запросное состояние не нужно.
- **`responses→responses`** — почти дословно, но с двумя вмешательствами:
  принудительный `store:false` и перехват `/model`.
- **`/model <имя>`** перехватывается адаптером **до** обращения к бэкенду:
  выбор сохраняется как переопределение модели сессии, клиенту отдаётся
  синтетическое подтверждение.

## Рассмотренные альтернативы

- Общий конвертер для Messages и Responses. Отвергнут: разная входная форма.
- Полагаться на нативный `/model` клиента. Отвергнуто: ненадёжен.

## Следствия

- Адаптер впервые хранит **состояние диалога** (выбранную модель) между
  запросами — в памяти, без персистентности (ADR-021).
- `/model` работает только на внутренних конвертерах, не в `passthrough`.
- Ограничение из `docs/codex.md`: у всех переключаемых моделей должен быть
  один размер контекста.
- `store:false` отключает серверное хранение ответов: если клиент
  когда-либо опирается на `previous_response_id`, такая цепочка через
  адаптер работать не будет.

## Доказательства

- `backend_adapter/convert.py`: `convert_responses_input_to_openai_messages`,
  `force_store_false`, `detect_model_switch_command`,
  `convert_openai_completions_to_responses`.
- `backend_adapter/streaming.py`: `stream_openai_completions_to_responses`.
- `3e4cef4` (v0.9.6), `735dc5a` (v0.9.7).

## Ответ автора (2026-10-10)

`store:false` — **механизм переключения моделей**, а не приватность. Бэкенд
переводится в строго stateless-режим: каждый запрос несёт всю историю и не
ссылается на ответы, сохранённые на сервере под конкретной моделью.
Поэтому модель можно просто подменить на нужный id в любом запросе.

**Следствие, которое из этого вытекает:** раз клиент в каждом запросе
присылает всю историю, команда `/model <имя>` и ответ-подтверждение уже
содержатся в ней. Привязку «сессия → модель» можно восстанавливать из
истории, а не хранить в памяти адаптера — см.
[ADR-037](037-proposal-model-override-from-history.md).
