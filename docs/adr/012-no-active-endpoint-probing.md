# ADR-012: Отказ от активного зондирования эндпойнтов бэкенда

| Поле | Значение |
|---|---|
| Статус | Действует (v0.9.9); заменяет решения v0.8.2–v0.8.5 о пробах |
| Тип решения | deliberate (записано) |
| Уверенность | high |
| Источник рационала | changelog v0.9.9; журнал ADR 2026-09-05…2026-09-07 (исходные решения) |

## Контекст

С v0.8.2 адаптер активно проверял, какие API (`completions`, `messages`,
`responses`, `embeddings`) поддерживает бэкенд, а с v0.8.4 — и каждая
модель: дымовые POST с `max_tokens:1` на четыре пути. Результат питал
колонку «Доступные API», значение TARGET=`auto` и ветки 502 в маршрутизации.

## Решение

Удалить зондирование целиком. Единственная проверка бэкенда — опрос
`GET /v1/models` (на старте, по кнопке и при перечитывании конфига).
Маршрутизация оптимистична (ADR-011); ошибка неверного маршрута видна по
факту в `.err`.

Удалены: дымовые пробы, кэш `_ENDPOINT_STATE`, YAML-ключ `probe:`,
переменная `ADAPTER_ENDPOINT_PROBE`, колонки и кнопка reprobe в WEBUI,
эндпойнты `/api/model-usage/reprobe*`, метрика
`backend_adapter_backend_endpoint`.

## История (цепочка заменённых решений)

| Версия | Решение | Проблема, обнаруженная потом |
|---|---|---|
| v0.8.2 | пробы всех бэкендов в фоне по кнопке | синхронная проверка на GET вешала страницу |
| v0.8.3 | «доступно» ⇔ HTTP 200 (было «не 404») | 501 показывался как доступность |
| v0.8.4 | синхронная проба **модели** при первом обращении, до 4×5 с | — |
| v0.8.4 | таймаут пробы 5 → 10 с; первый запрос ждёт до 40 с («осознанно») | пробы падали по таймауту на живых эндпойнтах |
| v0.8.5 | пробы только явно перечисленных в `probe:` эндпойнтов | неявная проба «моделью по умолчанию» удивляла |
| **v0.9.9** | **пробы удалены** | сложность при сомнительной ценности; задержка первого запроса |

## Рассмотренные альтернативы

Все промежуточные варианты выше были реализованы и отвергнуты на практике.
Это самая длинная цепочка пересмотров в проекте.

## Следствия

- Первый запрос к новой модели больше не ждёт до 40 с.
- Адаптер не знает заранее, поддерживает ли бэкенд нужный эндпойнт;
  пользователь узнаёт об этом по первой ошибке.
- Ключ `probe:` в старых `adapter.yaml` молча игнорируется.

## Доказательства

- `e96191a` (пробы добавлены), `7583fa6` (фон), `36c64ed` (таймаут 10 с),
  `52800a4` (только явные), `e5c42b6` (удалены).
- Журнал ADR, записи 2026-09-05, 2026-09-06, 2026-09-07
  (`docs/adr/archive/`).
- `backend_adapter/routing.py`, `decide` — нет сетевых вызовов.

## Ответ автора (2026-10-10) — решающая причина

**Пробы давали ложноположительный результат:** бэкенды отвечали HTTP 200 на
дымовой запрос даже к эндпойнтам, которые фактически не поддерживали.
Измерение, которое не различает «поддерживается» и «не поддерживается»,
бесполезно — поэтому механизм удалён целиком, а не доработан. Задержка
первого запроса и сложность — вторичные соображения.

Это сильный аргумент и против возврата к пробам в будущем: доступность
эндпойнта у таких бэкендов можно установить только по реальной ошибке на
реальном запросе (что и делает `.err`-канал, ADR-019).
