# ADR-036: Долг keep-alive — сначала измерить, потом решать

| Поле | Значение |
|---|---|
| Статус | Предложено (2026-10-11); продолжение ADR-003 |
| Тип решения | proposal |
| Повод | ответ автора на вопрос 20: «долг актуален, требует исследования» |

## Контекст

Соединения не переиспользуются на двух участках с разной ценой:

| Участок | Цена нового соединения | Вывод |
|---|---|---|
| агент → адаптер (`127.0.0.1`, HTTP) | TCP по loopback, доли миллисекунды | не стоит усилий: HTTP/1.1 потребовал бы chunked-фрейминга SSE в `http.server` |
| адаптер → бэкенд (`urlopen`, обычно HTTPS) | DNS + TCP + TLS: 1–3 RTT до бэкенда на **каждый** ход агента | кандидат на оптимизацию, но только если доля заметна |

Ответ LLM-бэкенда сам по себе занимает секунды (время до первого токена).
Если рукопожатие — малая доля этого времени, keep-alive ничего не даст.

## Решение: измерение (без изменения кода)

1. На машине адаптера против реального бэкенда:

   ```bash
   B=https://llm.example.com; K="$ADAPTER_LLM_KEY"
   for i in 1 2 3 4 5; do
     curl -so /dev/null -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
       -d '{"model":"<модель>","messages":[{"role":"user","content":"hi"}],"max_tokens":16}' \
       -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
       "$B/v1/chat/completions"
   done
   ```

   Доля установки соединения: `time_appconnect / time_starttransfer`.
2. Медиану TTFB реальных ходов агента взять из trace (`session-*.jsonl`).
3. Порог: если `time_appconnect` < 5 % медианного TTFB — долг закрыть как
   «не делаем» с цифрами в ADR-003. Если больше — переходить к пулу.

## Если пул нужен — ограничения дизайна

- **Пул должен быть общим, а не thread-local:** `ThreadingHTTPServer`
  создаёт новый поток на каждое входящее соединение, а агент → адаптер
  соединения не переиспользует (ADR-003). Кэш в `threading.local` будет
  пустым при каждом запросе.
- Структура: `dict[(scheme, host, port)] → deque[HTTPSConnection]` под
  локом, ограничение простаивающих соединений на хост (например, 4) и время
  жизни простоя (меньше idle-таймаута бэкенда/балансировщика, например 30 с).
- **Повтор на «протухшем» соединении** (сервер закрыл его в простое) —
  ровно один, только если ошибка возникла до получения первого байта ответа
  (`RemoteDisconnected`, `BrokenPipeError`, `ConnectionResetError` при
  отправке). POST не идемпотентен: повтор после частично полученного ответа
  недопустим.
- Стрим занимает соединение до конца ответа; в пул оно возвращается только
  после полного чтения тела. Оборванный стрим — соединение закрывается.
- `urllib` пула не даёт: нужен переход на `http.client` в обёртке. Это
  остаётся в рамках stdlib (ADR-002).
