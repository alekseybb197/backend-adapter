# ADR-039: Хранение `log/` — две политики для двух классов данных

| Поле | Значение |
|---|---|
| Статус | Предложено (2026-10-11); дополняет ADR-018, ADR-019 |
| Тип решения | proposal |
| Повод | ответ автора на вопрос 22: ротация нужна; логи ошибок и логи анализа харнесса — разные |

## Контекст

Файлы в `log/` не удаляются никогда (FIFO в `session_log.py` вытесняет
только открытые дескрипторы). Классы данных:

| Класс | Файлы | Природа | Требования |
|---|---|---|---|
| Инциденты | `session-*.err` | эксплуатационные, пишутся безусловно | ротация и удаление по времени (автор) |
| Анализ харнесса | `session-*.log`, `session-*.jsonl`, `session-*.parts/` | сырьё анализатора, дизайн которого не завершён | политика хранения не определена (автор) |

## Решение

### Инциденты — политика сейчас

- `ADAPTER_ERR_RETENTION_DAYS` (int, дефолт `30`, `0` — хранить всегда):
  удаляются `.err`, не изменявшиеся дольше срока (по `mtime`).
- `.err` дописывается на каждую ошибку сессии; ротация по размеру не
  предлагается: WEBUI ссылается на файл по имени (`_ERR_NAME_RE`), а длинная
  сессия с ошибками — это как раз то, что нужно разбирать целиком.

### Анализ харнесса — политика позже, предохранитель сейчас

Политика удаления не вводится, пока не определён анализатор. Чтобы до тех
пор каталог не заполнил диск — только предохранитель:

- `ADAPTER_LOG_MAX_TOTAL_MB` (int, дефолт `0` — выключен): при превышении
  суммарного объёма файлов анализа удаляются **целые сессии** (`.log` +
  `.jsonl` + `.parts/`), от старых к новым, пока объём не станет ниже 90 %
  лимита. `.err` в этот подсчёт не входит — он под своей политикой.
- **Комплект сессии нельзя определять по общему префиксу имени.** Метка
  времени для `.log`/`.jsonl` (`session_log._session_file_ts`) и для
  `.parts` (`_parts_dir_ts`) назначается независимо при первой записи
  каждого вида и может различаться на секунды. Группировать нужно по
  `id8` с учётом близости меток, а надёжнее — завести в `session_log` одну
  метку на сессию для всех видов файлов (небольшая правка, полезная и
  дереву артефактов). `id8` — первые 8 символов id сессии, поэтому
  совпадение `id8` у разных сессий возможно; при группировке по `id8`
  метка времени остаётся вторым ключом.
- Удаление сессии — всегда комплектом: частичная сессия (лог без
  `.parts`) бесполезна для анализатора и сбивает дерево артефактов.

### Исполнитель — «уборщик»

Поток-демон: проход при старте, затем раз в час. Правила безопасности
удаления:

1. Только прямые дети `log_dir()`: `os.scandir`, без рекурсии по путям извне.
2. Только имена по строгому шаблону `^session-\d{8}-\d{6}-[A-Za-z0-9._-]{1,8}(\.log|\.jsonl|\.err|\.parts)$`
   — посторонние файлы не трогаются.
3. Символические ссылки не удаляются и не обходятся
   (`entry.is_symlink()` → пропуск; `is_dir(follow_symlinks=False)`), чтобы
   ссылка из `log/` не привела к удалению чужого каталога. Для `.parts` —
   `shutil.rmtree` только после этой проверки.
4. Сессии с открытыми дескрипторами в `session_log` и сессии, изменённые
   за последние 15 минут, не удаляются — активная сессия не теряет файлы
   посреди записи.
5. Ошибки удаления — одна строка `[WARN]`, без исключения наружу (канал
   наблюдательный).
6. В конце прохода — итог: сколько удалено и сколько освобождено.

`--check` показывает, что **было бы** удалено при текущих настройках (без
удаления) — это даёт проверить политику до включения.

## Следствия

- Ссылки на удалённый `.err` в таблице `/sessions` начнут отвечать 404 —
  это нормально; страница должна показывать «файл удалён по сроку
  хранения», а не ошибку.
- Когда будет определён анализатор, политика для класса «анализ» заменит
  предохранитель отдельным ADR (например, хранение до обработки анализатором
  плюс архивирование результатов).
