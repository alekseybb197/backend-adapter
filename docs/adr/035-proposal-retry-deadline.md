# ADR-035: Ретраи с учётом клиента — проверка разрыва и общий дедлайн

| Поле | Значение |
|---|---|
| Статус | **Предложено** (2026-10-11); уточняет ADR-010 |
| Тип решения | proposal |
| Повод | ответ автора на вопрос 19: «требует исследования, предложения принимаются» |

## Факты

**Адаптер** (`config.py`): `ADAPTER_TIMEOUT=300`, `ADAPTER_RETRY_COUNT=3`,
пауза `2**attempt`. Таймаут передаётся в `urlopen(timeout=…)`, то есть это
**таймаут одной операции сокета**: ожидание первого байта ответа и каждая
пауза между чанками, а не общая длительность. Худший случай без стрима:
`300 + 2 + 300 + 4 + 300 ≈ 906 с`.

**Клиенты:**

| Клиент | Таймаут | Собственные повторы | Источник |
|---|---|---|---|
| [CC] | `API_TIMEOUT_MS` = 600 000 мс (10 мин) по умолчанию | `CLAUDE_CODE_MAX_RETRIES` = 10 по умолчанию | документация Claude Code, env-vars |
| QwenCode | `timeout: 300000` (5 мин) | — | `docs/qwen-code/global.settings.json` проекта |
| Codex CLI | `stream_idle_timeout_ms = 600000` | `request_max_retries = 2` | `docs/codex/sample.config.toml` проекта |

## Проблема

1. **Ретраи для ушедшего клиента.** У QwenCode таймаут равен одной попытке
   адаптера: когда первая попытка истекает по таймауту, клиент уже отключился,
   а адаптер начинает вторую и третью — нагрузка на бэкенд без получателя.
   Для [CC] то же наступает после второй попытки (600 с).
2. **Умножение повторов.** Клиент повторяет запрос сам, адаптер тоже:
   [CC] — до 10 × 3 = 30 обращений к бэкенду на один ход в худшем случае.
   Пока адаптер ретраит «старый» запрос, клиентский повтор уже идёт
   параллельно — бэкенд получает дубли.
3. Адаптер сейчас **никак не узнаёт** об уходе клиента до попытки записать
   ответ (`BrokenPipe` → `[CLIENT_GONE]`).

## Решение

### 1. Проверка разрыва перед каждым повтором (главное, дёшево)

```python
import select
import socket


def client_gone(sock: socket.socket) -> bool:
    """True, если клиент закрыл соединение (EOF) или сокет сломан.
    Не потребляет данные (MSG_PEEK), не блокирует (select с таймаутом 0)."""
    try:
        readable, _, _ = select.select([sock], [], [], 0)
        if not readable:
            return False  # тишина — клиент ждёт ответа
        return sock.recv(1, socket.MSG_PEEK) == b""  # b"" — EOF
    except (OSError, ValueError):
        return True  # RST, закрытый дескриптор
```

Вызывается в петле попыток **до** `time.sleep(delay)` и до следующего
`urlopen`: если клиент ушёл — `[CLIENT_GONE]` в лог, без `.err`-блока
(ошибкой адаптера это не является), выход из петли. Проверено на реальных
сокетах: живой простаивающий клиент → `False`; живой клиент с непрочитанными
данными → `False` (данные не потребляются); закрытие (FIN) → `True`;
сброс (RST) → `True`.

Ограничение: клиент, закрывший только запись (`shutdown(SHUT_WR)`) и
ждущий ответ, будет принят за ушедшего. HTTP-клиенты агентов так не делают.

### 2. Общий дедлайн запроса (опционально)

`ADAPTER_REQUEST_DEADLINE` (сек, `0` — выкл., дефолт `0`): таймаут каждой
попытки — `min(ADAPTER_TIMEOUT, осталось)`; новая попытка не начинается, если
осталось меньше `ADAPTER_TIMEOUT / 10`. Позволяет явно держать худший
случай ниже таймаута клиента (например, 570 с для [CC]). Дефолт `0`
сохраняет текущее поведение.

### 3. Правило в документации

«Худший случай адаптера должен быть меньше таймаута клиента; повторы
клиента — минимальные, потому что повторяет адаптер». Для Codex это уже
записано (`request_max_retries = 2`). Для [CC] стоит рекомендовать
`CLAUDE_CODE_MAX_RETRIES` меньше дефолтных 10.

## Следствия

- Пункт 1 устраняет оба эффекта (лишние попытки и большую часть умножения)
  без новых настроек.
- В trace стоит добавить событие `client_gone_before_retry` (номер попытки,
  прошедшее время) — это даст данные для выбора `ADAPTER_REQUEST_DEADLINE`.
