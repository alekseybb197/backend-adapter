# ADR-041: Ротация лога сервиса — newsyslog + переоткрытие по SIGHUP

| Поле | Значение |
|---|---|
| Статус | Действует (v1.0.3) |
| Тип решения | proposal |
| Связано | ADR-018 (каналы логов), ADR-026 (контракт завершения), ADR-039 (хранение `log/`), ADR-025 (состояние в файлах) |

## Контекст

Лог сервиса — stdout/stderr процесса под launchd — задаётся в plist
(`StandardOutPath`/`StandardErrorPath`) как
`~/Library/Logs/backend-adapter/adapter.log` (путь — единственный источник
`service_log.service_log_path()`). Файл живёт **вне** дома, потому что
`<root>/log` принадлежит работающему адаптеру; это решение принято в v1.0.2
и не меняется.

Проблема: у этого файла нет ни владельца, ни политики. launchd открывает его
один раз при старте агента и сам ничего не ротирует; `--launchd logs`
показывает хвост, `logs-clear` не существует. Измерено на рабочей машине
(2026-11-27): 21 527 612 байт за неполные сутки.

Проверено экспериментально (macOS, `newsyslog` из базовой поставки):

1. **`truncate` не работает.** launchd передаёт агенту fd 1/2, открытые **без**
   `O_APPEND` (в `lsof` — `1u`, `2u`). Писатель со смещением после `os.truncate`
   оставляет NUL-дырку: в замерах 160 байт (launchd-дескрипторы) и 490 байт
   (обычный файл с `O_APPEND`). Поэтому «очистка» файла должна быть его
   **удалением**, а не обнулением.
2. **`newsyslog` умеет всё нужное.** Конфиг
   `<log> 501:20 600 5 1024 * BZ <pidfile> 1` по достижении 1 МБ переименовывает
   лог, создаёт новый с заданными `owner:group`/`mode`, сжимает архив gzip
   (`Z`), не вставляет служебное сообщение (`B`) и шлёт `SIGHUP` PID из
   pid-файла. Демон `com.apple.newsyslog` запускается по
   `StartCalendarInterval Minute 30` — раз в час в :30; при `when = *` решение
   принимается только по размеру.
3. **Переоткрытие по SIGHUP работает,** если писатель его обрабатывает:
   обработчик открывает путь заново (`O_WRONLY|O_APPEND|O_CREAT`) и делает
   `dup2` — дальнейшие строки идут в новый файл, архив остаётся целым.
   `N` (без сигнала) не годится: писатель продолжает писать в переименованный
   файл, и лог теряется в архиве.
4. **`signal_number 0` недопустим** (`illegal signal number in config file`):
   «не сигналить» — только флагом `N`, а сигнал по умолчанию — `SIGHUP`.
5. **Отсутствующий pid-файл ломает ротацию мягко и опасно:** dry-run печатает
   `can't open pid file`, файлы не трогает, но и сигнал не шлёт — в бою это
   означало бы «лог переименован, агент пишет в архив». Поэтому наличие
   pid-файла проверяется при установке конфига.
6. **`SIGHUP` сегодня убивает адаптер:** `shutdown.install_signal_handlers`
   ставит только `SIGINT`/`SIGTERM`, а у `SIGHUP` действие по умолчанию —
   завершение процесса.
7. **`sudo` нужен только на запись конфига:** `/etc/newsyslog.d/` принадлежит
   root; dry-run (`newsyslog -r -n -f <conf>`) проверяется без root и
   возвращает 0 на валидном конфиге и 1 на мусоре.
8. **PID-файл живого сервиса может отсутствовать** (legacy `ADAPTER_DATA_ROOT`
   в `adapter.env`, ручное удаление): путь нельзя угадывать — он резолвится
   через `<root>/adapter.env` теми же правилами, что `daemon._pidfile_path`.

## Решение

### Переоткрытие по SIGHUP — новый модуль `service_log.py`

Модуль — лист DAG (stdlib + `templates`), единственный источник пути лога.

- `service_log_path()` — единственный источник пути
  `~/Library/Logs/backend-adapter/adapter.log`; `cli_args._service_log_path()`
  делегирует сюда, чтобы код и plist не разъехались.
- `install_hup_handler()` — вызывается из `backend-adapter.py` перед
  `serve_forever`. Включается **только** когда процесс действительно под
  launchd: `os.environ.get("XPC_SERVICE_NAME") == templates.LAUNCHD_LABEL`
  (launchd экспортирует эту переменную; проверено `launchctl print`). В
  терминале SIGHUP сохраняет прежний смысл — завершение процесса.
  Путь берётся **из дескриптора** (macOS `fcntl.F_GETPATH` на fd 1), а не из
  константы: если plist настроен на другой файл, переоткроется именно он. fd 1
  не регулярный файл (терминал, pipe) — обработчик не ставится.
- Обработчик: `flush` → открыть путь (`O_WRONLY|O_APPEND|O_CREAT`, `0600`) →
  `dup2` на 1 и 2 → строка `[SERVICE] log reopened after SIGHUP` в новый файл.
  Ошибка открытия — `[WARN]` в старый поток, процесс не падает.
- На не-macOS (`fcntl.F_GETPATH` отсутствует) — тихий no-op.

Обработчик дополняет, а не заменяет контракт ADR-026: `SIGINT`/`SIGTERM` →
вежливый выход, `SIGHUP` → только переоткрытие лога.

### `--launchd logs-clear` — очистка лога

1. Файла нет — `[WARN]`, код 0 (идемпотентно).
2. Файл есть — удаляется (`os.remove`; `truncate` запрещён, см. контекст п. 1).
3. Если агент **работает**, выполняется `launchctl kickstart -k`: процесс
   перезапускается и создаёт лог заново. Без этого fd живого процесса держал бы
   удалённый inode — место не освобождалось бы до рестарта. Перезапуск
   неизбежен: сигнала, безопасного для старых сборок, нет (`SIGHUP` до v1.0.3
   завершает процесс, см. п. 6), а `truncate` оставляет NUL-дырки.
4. Агент зарегистрирован, но остановлен — файл остаётся удалённым, ничего не
   стартует.

`--systemd logs-clear` не вводится: журнал journald ротируется сам.

### `--launchd log-rotate` — установка ротации (с эскалацией прав)

1. Требуется размеченный дом (`adapter.env`) и установленный plist.
2. Путь pid-файла резолвится как в `daemon._pidfile_path`: `adapter.env`
   читается в отдельный словарь (`env_check.parse_env_text`, окружение CLI
   не мутируется; явный env побеждает файл), затем `ADAPTER_DATA_ROOT`/
   `ADAPTER_PIDFILE`; дефолт — `<root>/var/adapter.pid`.
   Файла нет или PID в нём не жив (`os.kill(pid, 0)`) — `[FATAL]` с подсказкой
   перезапустить сервис; конфиг с заведомо битым pid-путём не ставится
   (см. п. 5).
3. Конфиг рендерится `templates.render_newsyslog_conf(...)` и **сначала**
   проверяется dry-run'ом `newsyslog -r -n -f <временный файл>` без root
   (rc ≠ 0 — `[FATAL]`, в `/etc` ничего не попадает).
4. Установка — только через `sudo install -m 644` из временного файла в
   `/etc/newsyslog.d/backend-adapter.conf`. `sudo` вызывается с наследованием
   терминала (пароль спрашивает он сам); отказ/ошибка — `[FATAL]`.
5. Параметры по умолчанию: `count 5`, `size 1024` КБ, `when *`, флаги `BZ`,
   `mode 600`, `owner:group` — владелец процесса (`getuid():getgid()`).
   Демон newsyslog проверяет размер раз в час в :30.

### `--launchd log-rotate-remove` — снятие ротации

`sudo rm -f /etc/newsyslog.d/backend-adapter.conf`; `-f` делает операцию
идемпотентной (файла нет — код 0, `[OK]`); ошибка `sudo` — `[FATAL]`.
Ротацию, уже случившуюся, команда не откатывает.

### Полное удаление

`--launchd uninstall` дополнительно снимает конфиг ротации (если он есть):
удаление дома без него оставило бы в `/etc` правило на несуществующий файл.
`plist-uninstall` конфиг **не трогает** и sudo не требует — это по-прежнему
операция «только артефакт launchd».

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| `logrotate` | В базовой поставке macOS отсутствует — новая внешняя зависимость (нарушает «только PyYAML», ADR-005/028) |
| Свой поток-уборщик внутри адаптера (в духе ADR-039) | Лог сервиса — fd launchd, а не файл адаптера: без переоткрытия дескриптора уборка ничего не освобождает; плюс политика для лога сервиса живёт вне дома и вне `log/` |
| `os.truncate` для `logs-clear` | Оставляет NUL-дырки: fd launchd без `O_APPEND` (замерено) |
| newsyslog без pid-файла (флаг `N`) | Писатель продолжает писать в переименованный файл — лог теряется |
| Ротация по сигналу от самого адаптера | Требует собственного таймера и прав на переименование чужого файла; дублирует штатный системный механизм |
| Не менять ничего | 21 МБ/сутки; роста нет только у остановленного сервиса |

## Следствия

- Одна установка на машину требует `sudo` (только запись конфига); повседневная
  эксплуатация — без root.
- `SIGHUP` под launchd перестаёт завершать процесс. Скрипты, которые «убивали»
  зависший агент через `kill -HUP`, должны использовать `SIGTERM`.
- `logs-clear` перезапускает работающий агент — прерываются in-flight запросы.
  Это осознанный компромисс: иначе удалённый файл не освобождает место.
- Новая сборка (v1.0.3+) должна быть **перезапущена** после обновления: старый
  процесс не содержит обработчика SIGHUP.
- Появляется новый файл состояния вне дома (`/etc/newsyslog.d/`), который надо
  снимать при полном удалении; путь фиксирован, права — `644 root:wheel`.
- Область ADR-039 (`log/` в доме) не пересекается: у лога сервиса своя
  политика, свой механизм и свой владелец.

## Проверка

- `tests/test_service_log.py`: без `XPC_SERVICE_NAME` или для чужого сервиса
  обработчик не ставится (сигнал остаётся `SIG_DFL`); под launchd — ставится
  обработчик `SIGHUP`, повторный вызов — no-op; `_reopen` на подготовленных
  fd пишет в новый файл (старый inode не трогается); `clear_log` удаляет
  файл, а не обнуляет.
- `tests/test_cli_args.py`: `logs-clear` удаляет файл, при отсутствии —
  `[WARN]` и код 0, при работающем агенте вызывается `kickstart -k`;
  `log-rotate` отказывает без pid-файла и при провале dry-run, генерирует
  ожидаемую строку конфига и зовёт `sudo install`; `log-rotate-remove` —
  идемпотентен; `uninstall` снимает конфиг.
- `tests/test_templates.py`: `render_newsyslog_conf` — формат полей, `BZ`,
  добавление флага `N` при `pid_file=None` (и никогда `0` как сигнал),
  `ValueError` на пути с пробелом, экранирование `#`.
- `pytest tests/test_adr_catalog.py` — каталог.

## Оценка реализации

Реализовано в v1.0.3: новый модуль `backend_adapter/service_log.py`
(~170 строк с docstring), правка `cli_args.py` (делегирующий
`_service_log_path`, три подкоманды, sudo-обвязка, резолвинг pid-пути),
`templates.py` (`render_newsyslog_conf` + экранирование), `backend-adapter.py`
(вызов `install_hup_handler`), тесты (`tests/test_service_log.py`,
`TestServiceLogCommands` в `tests/test_cli_args.py`,
`TestRenderNewsyslogConf`), документация (`docs/install.md` §9/§9.2,
`docs/logging.md`, `docs/architecture.md` §2/§10, `.claude/rules/adr-runtime.md`).

Риски: (а) перезапуск сервиса в `logs-clear` — документировать в help;
(б) `sudo` в неинтерактивном окружении — `[FATAL]` с подсказкой; (в) на
Linux `service_log` — no-op, поведение не меняется.

Вопрос к автору: достаточны ли дефолты `5 × 1 МБ` (≈5 МБ архива) или нужен
размер побольше — параметр вынесен в шаблон и меняется одной строкой.
