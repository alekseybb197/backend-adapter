# Настройка QwenCode для работы через backend-adapter

> Руководство по настройке клиента **QwenCode** на работу через
> backend-adapter. Типовой файл — [`docs/qwen-code/global.settings.json`](qwen-code/global.settings.json)
> (профиль пользователя). Установка и настройка самого адаптера —
> [`docs/install.md`](install.md). Настройка второго клиента, [CC], —
> [`docs/claude_code.md`](claude_code.md); сравнение подходов к моделям —
> раздел 8.

---

## 1. Как QwenCode подключается к адаптеру

Адаптер поднимает локальный HTTP-эндпоинт (по умолчанию
`http://127.0.0.1:9999`), реализующий Anthropic Messages API
(см. `docs/install.md`, раздел 2). QwenCode умеет говорить на двух
протоколах, которые адаптер принимает как **два разных входа**:

| Протокол QwenCode (`modelProviders`) | Куда шлёт | Вход адаптера |
|---|---|---|
| `openai` ([OI]-совместимый) | `POST /v1/chat/completions` | `/v1/chat/completions` |
| `anthropic` | `POST /v1/messages` | `/v1/messages` |

Это даёт полезную возможность: **оба протокола можно направить в один и тот
же адаптер** и переключаться между ними командой `/model`. В типовом файле
так и сделано — объявлены две модели (`local` через `openai`, `remote` через
`anthropic`), и обе ходят в `127.0.0.1:9999`.

> **Важно про `baseUrl`.** У протокола `openai` адрес указывается **с
> суффиксом `/v1`** (`http://127.0.0.1:9999/v1`) — клиент дописывает
> `/chat/completions`. У протокола `anthropic` — **без** `/v1`
> (`http://127.0.0.1:9999`) — клиент дописывает `/v1/messages`. Именно так
> записано в типовом файле; если перепутать, запрос уйдёт на несуществующий
> путь.

В отличие от [CC], который читает адрес адаптера из переменных окружения
(`ANTHROPIC_BASE_URL`), QwenCode задаёт его **в самом `settings.json`**
(поле `baseUrl` записи провайдера). Адаптер, как и прежде, не читает
настройки клиента — ему нужны только собственные `ADAPTER_*`
(см. `docs/environment.md`).

## 2. Что нужно включить в адаптере

Прежде чем настраивать клиент, проверьте входы адаптера: у каждого из трёх
входов есть TARGET-переменная (`ADAPTER_*_TARGET`, см.
[`docs/routing.md`](routing.md)), и **по умолчанию два из трёх выключены**:

| Вход адаптера | Дефолт | Что это значит для QwenCode |
|---|---|---|
| `/v1/messages` | `completions` (включён) | Протокол `anthropic` работает **сразу**, без правок |
| `/v1/chat/completions` | `none` (**выключен**) | Протокол `openai` вернёт **404**, пока не включите |
| `/v1/responses` | `none` (выключен) | QwenCode его не использует |

Чтобы заработал провайдер `openai`, включите соответствующий вход —
например, режимом **passthrough E→E** (тело уходит бэкенду как есть):

```bash
export ADAPTER_COMPLETIONS_TARGET=passthrough
```

Без этого на запрос через `openai`-провайдер придёт
`404 "endpoint is disabled (ADAPTER_COMPLETIONS_TARGET=none)"`. В типовом
файле активен именно `openai` (`security.auth.selectedType: "openai"`),
поэтому эта переменная нужна почти всегда.

## 3. Файлы настроек: расположение и приоритет

QwenCode читает настройки из нескольких файлов `settings.json`:

| Файл | Уровень | Назначение |
|---|---|---|
| `~/.qwen/settings.json` | Пользовательский | Общие настройки для всех проектов (основное место для `modelProviders`) |
| `<project>/.qwen/settings.json` | Проектный | Настройки конкретного проекта |
| `/etc/qwen-code/settings.json` (Linux) / `/Library/Application Support/QwenCode/settings.json` (macOS) | Системный | Администраторские настройки; путь переопределяется `QWEN_CODE_SYSTEM_SETTINGS_PATH` |

Приоритет (позднее перекрывает раннее): системные значения → пользовательские
→ проектные → системные настройки.

Правила:

- в репозиторий backend-adapter каталог `.qwen/` **не коммитится**, поэтому
  типовой файл лежит в `docs/qwen-code/` и копируется вручную (раздел 9);
- по документации клиента файлы настроек **допускают комментарии** (`//`,
  `/* */`) — в отличие от [CC], где это ошибка синтаксиса. В типовом файле
  комментариев всё же нет: так он остаётся строгим JSON и копируется в любой
  инструмент без чистки;
- поле `$version` — служебная версия схемы (используется клиентом для
  миграций); вручную его не правят.

## 4. Типовой профиль — `~/.qwen/settings.json`

Типовой файл — [`docs/qwen-code/global.settings.json`](qwen-code/global.settings.json).
Скопируйте в `~/.qwen/settings.json` и при необходимости поправьте имена
моделей и `baseUrl`:

```json
{
  "outboundCorrelation": {
    "allowDynamicHeaderValues": true
  },
  "modelProviders": {
    "openai": [
      {
        "id": "local",
        "name": "local",
        "baseUrl": "http://127.0.0.1:9999/v1",
        "description": "Local",
        "envKey": "LOCAL_API_KEY",
        "generationConfig": {
          "timeout": 300000,
          "maxRetries": 1,
          "contextWindowSize": "128000",
          "samplingParams": {
            "temperature": 0.6,
            "top_p": 0.9,
            "max_tokens": 8192,
            "presence_penalty": 0,
            "frequency_penalty": 0
          },
          "extra_body": {
            "enable_thinking": true
          },
          "customHeaders": {
            "X-Claude-Code-Session-Id": "${session_id}"
          }
        }
      }
    ],
    "anthropic": [
      {
        "id": "remote",
        "name": "remote",
        "baseUrl": "http://127.0.0.1:9999",
        "description": "Remote",
        "envKey": "LOCAL_API_KEY",
        "generationConfig": {
          "timeout": 300000,
          "maxRetries": 1,
          "contextWindowSize": "262144",
          "samplingParams": {
            "temperature": 0.6,
            "top_p": 0.9,
            "max_tokens": 8192,
            "presence_penalty": 0,
            "frequency_penalty": 0
          },
          "extra_body": {
            "enable_thinking": true
          },
          "customHeaders": {
            "X-Claude-Code-Session-Id": "${session_id}"
          }
        }
      }
    ]
  },
  "env": {
    "LOCAL_API_KEY": "dummy",
    "LOCAL_BASE_URL": "http://127.0.0.1:9999"
  },
  "security": {
    "auth": {
      "selectedType": "openai"
    }
  },
  "model": {
    "name": "local",
    "baseUrl": "http://127.0.0.1:9999/v1"
  },
  "tools": {
    "approvalMode": "default"
  },
  "$version": 4
}
```

## 5. Комментарии по ключам

### 5.1 Верхний уровень

| Ключ | Значение | Назначение |
|---|---|---|
| `outboundCorrelation.allowDynamicHeaderValues` | `true` | **Разрешить подстановку переменных в заголовки.** Без этого флага плейсхолдер `${session_id}` в `customHeaders` не раскрывается — заголовок уходит как есть, и сессия протоколируется как `unknown` (см. раздел 7). Нужен **только** для этого механизма; если id сессии вам не нужен — можно убрать |
| `modelProviders` | объект | **Все модели, доступные клиенту.** Ключи (`openai`, `anthropic`, `gemini`, `vertex-ai`) — это протокол API, а не конкретный вендор. Модель, не объявленная здесь, для клиента не существует (см. раздел 8) |
| `env` | объект | Значения переменных окружения, на которые ссылается `envKey` записей провайдеров. **Низший приоритет** — реальные переменные окружения shell перекрывают эти значения. Здесь лежит заглушка ключа `dummy` |
| `security.auth.selectedType` | `"openai"` | Какой протокол активен при старте. Значение должно совпадать с одним из ключей `modelProviders`; иначе клиент попросит выбрать протокол вручную (`/auth`) |
| `model.name` | `"local"` | Модель, активная при старте; должно совпадать с полем `id` одной из записей провайдеров |
| `model.baseUrl` | `"http://127.0.0.1:9999/v1"` | Адрес по умолчанию для активной модели (дублирует `baseUrl` записи провайдера) |
| `tools.approvalMode` | `"default"` | Режим подтверждения вызовов инструментов: `default` — спрашивать по обычным правилам, без автоодобрения |
| `$version` | `4` | Служебная версия схемы настроек; управляется клиентом |

### 5.2 Записи в `modelProviders`

`modelProviders` — словарь «протокол → список моделей». Поля одной записи:

| Поле | Обяз. | Назначение |
|---|---|---|
| `id` | ✅ | Идентификатор модели — **именно это имя** выбирается в `/model` и указывается в `model.name` |
| `name` | ✅ | Отображаемое имя в интерфейсе |
| `baseUrl` | ✅ | Адрес API. Для `openai` — с `/v1` на конце; для `anthropic` — без (см. раздел 1) |
| `envKey` | ✅ | Имя переменной окружения с API-ключом. Ключ должен быть **непустым**, поэтому в типовом файле стоит заглушка `dummy` — реальную авторизацию на бэкенде выполняет адаптер |
| `description` | ❌ | Описание модели для интерфейса |
| `generationConfig` | ❌ | Параметры генерации и модели (см. 5.3). **Обязателен**, если хотите задать своё контекстное окно или заголовки |

### 5.3 `generationConfig`

| Поле | Значение | Назначение |
|---|---|---|
| `timeout` | `300000` | Таймаут запроса к модели (мс). 5 минут — с запасом на медленный локальный бэкенд и «размышления» |
| `maxRetries` | `1` | Повторы при сбое. Адаптер **сам** делает ретраи (`ADAPTER_RETRY`), поэтому клиентские повторы держат минимальными, чтобы не умножать нагрузку |
| `contextWindowSize` | `"128000"` / `"262144"` | **Размер контекстного окна модели** — главная настраиваемая величина (раздел 6). В типовом файле задан **строкой**; официальный справочник описывает его как число — если ваша сборка значение-строку не принимает, замените на `128000` без кавычек |
| `samplingParams.temperature` | `0.6` | Температура сэмплирования |
| `samplingParams.top_p` | `0.9` | Nucleus sampling |
| `samplingParams.max_tokens` | `8192` | Лимит токенов ответа (клиентский; не путать с окном контекста) |
| `samplingParams.presence_penalty` | `0` | Штраф за повторяемость тем — для «думающих» моделей выключен |
| `samplingParams.frequency_penalty` | `0` | Штраф за повторы токенов — там же |
| `extra_body.enable_thinking` | `true` | Включить режим расширенного мышления (уходит в тело запроса как `enable_thinking`; требует поддержки бэкендом) |
| `customHeaders` | объект | Дополнительные HTTP-заголовки запроса; здесь передаётся id сессии (раздел 7) |

## 6. Модели с разным контекстным окном

**Это главное практическое достоинство конфигурации QwenCode.** Размер
контекстного окна задаётся **отдельно для каждой модели** — полем
`contextWindowSize` в её записи `generationConfig`. В типовом файле это видно
наглядно: модель `local` (протокол `openai`) заявляет `128000` токенов,
модель `remote` (протокол `anthropic`) — `262144`. Переключение `/model`
меняет и модель, и представление клиента о размере её контекста:
компактизация, счётчик заполнения окна и обрезка истории считаются от него.

Отсюда — возможность держать в одном профиле модели разного класса: быструю
с коротким окном и большую с длинным, не переписывая настройки при каждом
переключении. У [CC] такой возможности нет — там окно задаётся одной
переменной на все модели (раздел 8).

Практика:

- **Указывайте реальное окно бэкенда.** Заявленное больше реального — клиент
  переполнит контекст и получит ошибку от бэкенда; меньше реального — будет
  компактизировать раньше времени, теряя историю без нужды.
- **Держите `contextWindowSize` в `generationConfig` нужной модели.**
  Значение в верхнеуровневом `model.generationConfig` игнорируется, если
  модель объявлена в `modelProviders` — это самая частая причина «окно не
  применилось».
- **Проверяйте, что значение подхватилось.** Если после правки размер не
  изменился, проверьте: (а) поле лежит внутри `generationConfig` **той**
  записи `modelProviders`, которой соответствует выбранная модель;
  (б) нет второго `settings.json` (проектного или системного), который
  перекрывает пользовательский; (в) `model.name` действительно указывает на
  ту запись, которую вы правили.

## 7. Передача id сессии

По умолчанию QwenCode **не передаёт id сессии** — ни заголовком, ни полем
тела. Без настройки все обращения агента протоколируются как
`session=unknown`: строки таблицы «Sessions» на статус-странице адаптера
сливаются в одну, и per-session логи тоже (см. [`docs/webui.md`](webui.md),
[`docs/logging.md`](logging.md)).

Механизм включения — `customHeaders` с плейсхолдером `${session_id}` плюс
разрешающий флаг:

```json
"outboundCorrelation": { "allowDynamicHeaderValues": true },
"generationConfig": {
  "customHeaders": { "X-Claude-Code-Session-Id": "${session_id}" }
}
```

`customHeaders` нужно добавить в `generationConfig` **каждой** записи
провайдера, которой вы пользуетесь, — в типовом файле он продублирован и у
`openai`, и у `anthropic`.

Имя заголовка выбираете вы. В типовом файле взято
`X-Claude-Code-Session-Id` — то же, что шлёт [CC] CLI; оно уже входит в
дефолтный список `ADAPTER_SESSION_HEADER`
(`X-Claude-Code-Session-Id,x-opencode-session`), поэтому адаптер подхватит id
без правок. Если хотите своё имя (например, `x-opencode-session`), задайте
его и в `customHeaders`, и в `ADAPTER_SESSION_HEADER`
(см. [`docs/environment.md`](environment.md) §5).

После настройки адаптер запишет честный id — тот же, что печатает
`qwen --resume <uuid>` и что стоит в имени `session-*.jsonl` / `session-*.log`.
Оговорка: id ротируется на `/new` и `/resume` — после смены сессии в логах
появится новый идентификатор (это поведение клиента, не адаптера).

## 8. Отличия от [CC]

Оба клиента работают через один и тот же адаптер, но по-разному
распоряжаются моделями. Это не «лучше/хуже», а разные компромиссы.

| Аспект | [CC] ([`docs/claude_code.md`](claude_code.md)) | QwenCode |
|---|---|---|
| **Список моделей** | Не фиксирован: имя модели приходит в запросе и проверяется адаптером (строгая проверка + маппинг `ADAPTER_MODELS_MAPPING`) | **Фиксирован заранее**: каждая модель должна быть описана записью в `modelProviders` — чего в файле нет, того для клиента не существует |
| **Смена модели** | Сразу доступна любая модель, поддержанная адаптером и попавшая в таблицы; правка конфига не нужна | Сначала описать модель в `modelProviders`, затем выбирать `/model` |
| **Размер контекста** | **Одно значение на все модели** (`CLAUDE_CODE_AUTO_COMPACT_WINDOW`) | **Своё значение у каждой модели** (`contextWindowSize`) — модели с разным окном сосуществуют в одном профиле |
| **Модели для ролей и субагентов** | Отдельные переменные на роли (`ANTHROPIC_DEFAULT_OPUS_MODEL`, `..._SONNET_...`, `..._HAIKU_...`) и на субагентов (`CLAUDE_CODE_SUBAGENT_MODEL`) — **при смене модели про них легко забыть** | Ролевых переменных нет: активная модель выбирается целиком через `/model`, отдельные модели для субагентов не задаются |
| **Комментарии в JSON** | Строгий JSON: комментарии и хвостовые запятые — ошибка (`[Settings Error]` при старте) | Допускаются `//` и `/* */` |

**Практический вывод.** [CC] выигрывает в гибкости: подключили новую модель
на бэкенде — она сразу доступна, без правок клиента. Обратная сторона —
единое жёстко заданное окно контекста для всех моделей и необходимость
**помнить про ролевые модели**, в том числе про модель субагентов: иначе
часть запросов уйдёт на имя, которого бэкенд не знает. QwenCode требует
описать все модели заранее, зато позволяет каждой задать своё контекстное
окно и не имеет «забытых» ролевых переменных.

## 9. Установка типового файла

```bash
# Пользовательский профиль (каталог создаётся при необходимости)
mkdir -p ~/.qwen
cp docs/qwen-code/global.settings.json ~/.qwen/settings.json
#    поправьте baseUrl, имена моделей и contextWindowSize (раздел 6)

# И не забудьте разрешить вход, которым пользуется выбранный протокол
# (раздел 2): для провайдера openai — ADAPTER_COMPLETIONS_TARGET=passthrough
# в окружении адаптера; для anthropic правок не требуется.
```

## 10. Проверка

```bash
# 1. Адаптер слушает и отвечает
curl -s http://127.0.0.1:9999/v1/models | head

# 2. Клиент запускается
qwen --version

# 3. В интерфейсе /model видны обе объявленные модели (local, remote);
#    ответы на запросы приходят от бэкенда через адаптер

# 4. Сессия протоколируется честным id: в консоли адаптера
#    [REQ] ... session=<uuid>, а не session=unknown
```

Если при запросе через `openai`-провайдер приходит
`404 "endpoint is disabled (ADAPTER_COMPLETIONS_TARGET=none)"` — не включён
вход `/v1/chat/completions` (раздел 2).
