# Environment Variables — backend-adapter

> Параметры настройки режимов работы адаптера `backend-adapter.py`.
> Все переменные читаются из окружения перед стартом (модуль `backend_adapter/config.py`).
> Если не заданы — используются значения по умолчанию, указанные в столбце *Default*.

> **Не путать с переменными установщика.** Префикс `ADAPTER_SERVICE_*`
> (`ADAPTER_SERVICE_BACKEND_BASE`, `ADAPTER_SERVICE_BACKEND_KEY`,
> `ADAPTER_SERVICE_ROOT`, `ADAPTER_SERVICE_USER`) читает **`install.sh --service`**,
> а не сам адаптер: это параметры установки сервиса (см. `docs/install.md`
> §4.2). Режим удаления читает `DELETE_INSTALL` (эквивалент `--delete`) и
> `ADAPTER_DELETE_YES` (эквивалент `--yes`). Адаптер эти переменные
> игнорирует.

---

## Ноль-конфиг (zero-config) против полной настройки

Все переменные делятся на две группы:

1. **Обязательные при старте** — без них адаптер не запускается.
   Сейчас это одна переменная: `ADAPTER_BACKEND_CONFIG` (внешние LLM-бэкенды).
2. **Дефолтные (можно не задавать)** — всё остальное. Дефолты выбраны так,
   чтобы адаптер работал с **минимальными запросами к ресурсам**:
   - **не пишет логов на диск** (`ADAPTER_DEBUG_ENABLE=0` — файловая запись
     выключена; консольные debug-логи безусловны и всегда видны, с обрезкой
     `ADAPTER_DEBUG_TRIM`). Одним этим флагом включаются и логи, и per-session
     дампы частей протокола (`.json`/`.yaml`) — отдельного выключателя дампов
     больше нет (v0.9.10),
   - **показывает статус на дефолтном порту** (WEBUI поднимается **всегда** —
     флага отключения нет; статус-страница `/` на `127.0.0.1:8765`, корень —
     `ADAPTER_DATA_ROOT`, по умолчанию `./tmp/adapter`; вкладка сессий пуста,
     пока файловая запись не включена `ADAPTER_DEBUG_ENABLE=1`).

Минимальный запуск:

```bash
# Примеры — docs/samples/sample.adapter.yaml и sample.adapter.env
export ADAPTER_BACKEND_CONFIG="./adapter.yaml"           # внешний LLM-бэкенд
# ... + переменная токена, на которую ссылается поле key в YAML
python3 backend-adapter.py
```

## Домашняя папка и `--root` (v0.9.11)

Вместо перечисления `export`-переменных настройки можно сложить в **домашнюю
папку** и указать её ключом `--root <путь>` (по умолчанию `~/.ba`). Раскладка:

```
<root>/
├── adapter.env     # переменные окружения (генерирует --install)
├── adapter.yaml    # конфигурация бэкендов (копия sample.adapter.yaml)
├── tariffs.yaml    # тарифы моделей (копия sample.tariffs.yaml)
└── tmp/adapter/    # ADAPTER_DATA_ROOT: внутри log/ и var/
```

Из дома подставляются ровно те настройки, которых нет в окружении:

| Что | Откуда | Если переменная уже задана |
|---|---|---|
| `ADAPTER_DATA_ROOT` | `<root>/tmp/adapter` (или значение из `adapter.env`) | не перетирается |
| все переменные из `adapter.env` | файл `<root>/adapter.env` | не перетираются |
| `ADAPTER_BACKEND_CONFIG` | `<root>/adapter.yaml` | не перетирается |
| `ADAPTER_MODELS_TARIFFS` | `<root>/tariffs.yaml` (если файл есть) | не перетирается |

**Приоритет: явное окружение всегда побеждает.** Каждая подстановка — это
`os.environ.setdefault`, то есть значение, экспортированное в оболочке, сильнее
и файла `adapter.env`, и пути по умолчанию от `root`. Порядок: сначала
читается `adapter.env` (файл дома — тоже пользовательская настройка и вправе
задать `ADAPTER_DATA_ROOT` сам, как это делает реальный `~/.ba`), потом
подставляются оставшиеся пути.

**Активность только по флагу.** Без `--root` и `--install` дом не читается
вовсе: дефолт `ADAPTER_DATA_ROOT=./tmp/adapter` и обязательный
`ADAPTER_BACKEND_CONFIG` в окружении сохраняются (см. «Ноль-конфиг» выше).

**Разметка дома.** Ключ `--install` создаёт папку со всеми конфигами и
заглушкой токена (`ADAPTER_BACKEND_KEY_LLM_SERVICE='*****'`, файл `0600`),
затем завершает работу. Повторный запуск идемпотентен — существующие файлы не
перезаписываются, о каждом пропуске печатается `[WARN]`. Образцы берутся из
`docs/samples/`, поэтому из standalone-бинарника `--install` недоступен.
Подробнее — `docs/install.md` §4.5.

```bash
backend-adapter --install              # разметить ~/.ba
backend-adapter --root ~/.ba           # запуск с настройками из дома
```

## 1. Обязательные при старте: подключение к бэкенду

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_BACKEND_CONFIG` | *(пусто)* | **Обязательна при старте. Единственный способ конфигурации бэкенда.** Путь к YAML-файлу со структурой `backend:` (список записей `name`/`base`/`key`). Пример — `docs/samples/sample.adapter.yaml`. Не задан — старт невозможен: адаптер завершается с `[FATAL]` и подсказкой. |

> **Стартовая проверка не настраивается:** при `ADAPTER_STRICT_MODELS=1`
> (дефолт) адаптер при старте опрашивает каждый бэкенд (`GET /v1/models`) —
> это не env-рубильник, а факт работы: список доступных моделей нужен для
> валидации. Если бэкенд недоступен, адаптер продолжает старт
> (с предупреждением в консоль) — на проксирование это не влияет.
> Дымовых проб эндпойнтов больше нет (сняты в v0.9.9): единственная
> проверка бэкенда — опрос списка моделей.

### Пример YAML-конфига бэкендов (пример файла — `docs/samples/sample.adapter.yaml`)

```yaml
backend:
  - name: home
    base: "http://127.0.0.1:8002"
    key: ADAPTER_HOME_KEY          # имя переменной окружения → подставляется реальное значение
  - name: litellm
    base: "https://llm.service.example.com"
    key: ADAPTER_LITELLM_KEY
  - name: local
    base: "http://127.0.0.1:8000"
    key: ADAPTER_HOME_KEY
```

Поля каждого элемента:

- **`name`** — произвольный идентификатор бэкенда. Используется для префикса модели (при коллизиях) и для маршрутизации запросов (`&lt;backend_name&gt;.&lt;model&gt;`).
- **`base`** — базовый URL бэкенда (без `/v1/`).
- **`key`** — либо прямой токен, либо **имя переменной окружения**. Адаптер сначала подставляет значение переменной, затем использует его как Bearer-токен.
- **`probe`** *(устаревшее, v0.9.9)* — ключ больше **не поддерживается**:
  дымовые пробы эндпойнтов сняты, ключ молча игнорируется. Проверка бэкенда —
  только опрос списка моделей (`GET /v1/models`). Неверный выбор эндпойнта
  агентом фиксируется по факту ошибки (ответ бэкенда отдаётся клиенту как
  есть, инцидент попадает в `.err`), а не предугадывается пробой. Прежние
  значения ключа (`completions`/`messages`/`responses`/`embeddings`) ни на
  что не влияют.

### Маршрутизация по бэкендам

1. Если в запросе модель содержит префикс `&lt;имя_бэкенда&gt;.` (например `litellm.qwen3.6-35b-a3b`), запрос отправляется на соответствующий бэкенд, а префикс обрезается.
2. Если модель встречается на нескольких бэкендах (коллизия), к её ID автоматически добавляется префикс `&lt;backend_name&gt;.model_id`.
3. Уникальные модели передаются как есть — адаптер сам найдёт подходящий бэкенд по списку.
4. Fallback — первый бэкенд в конфигурации (`_DEFAULT_BACKEND`).

## 1а. Входные эндпоинты (TARGET)

> **Что это.** Адаптер принимает **три** POST-эндпоинта входных запросов —
> `/v1/messages` (Anthropic Messages API), `/v1/chat/completions`
> ([OI] Chat Completions), `/v1/responses` ([OI] Responses API). Что делает
> адаптер с запросом на каждом входе (какой формат отдаёт бэкенду) — решает
> соответствующая TARGET-переменная: **префикс имени переменной = входной
> эндпоинт**. Входы, целевой формат которых `none`, не принимаются вовсе
> (404). **Полное описание принципов, реализованных маршрутов и перспектив —
> [`docs/routing.md`](routing.md).**

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_MESSAGES_TARGET` | `completions` | Куда направлять запросы с **`/v1/messages`** (Anthropic-формат). |
| `ADAPTER_COMPLETIONS_TARGET` | `none` | Куда направлять запросы с **`/v1/chat/completions`** ([OI]-формат). |
| `ADAPTER_RESPONSES_TARGET` | `none` | Куда направлять запросы с **`/v1/responses`** (Responses-формат). |

Допустимые значения всех трёх — одно из: **`completions`**, **`messages`**,
**`responses`** (целевой формат: **прямое преобразование** входа в него),
**`passthrough`** (передать на эндпойнт входного формата **без
преобразования** — тело и SSE дословно), **`none`** (вход выключен: HTTP 404).
Значение `auto` прежних версий удалено в v0.9.4: в env оно невалидно — консоль
`[WARN]`, вход трактуется как `none`. Детали и примеры — `docs/routing.md`.

> **Дефолты — это нулевая настройка (100% прежнее поведение):** принимается
> только `/v1/messages`, который конвертируется в `chat.completions`
> (`ADAPTER_MESSAGES_TARGET=completions`); входы
> `/v1/chat/completions` и `/v1/responses` закрыты (`none`). Пример из
> задачи «принимать только messages, конвертировать в chat completions» —
> ровно эти дефолты: `ADAPTER_COMPLETIONS_TARGET=none,
> ADAPTER_MESSAGES_TARGET=completions, ADAPTER_RESPONSES_TARGET=none`.

**Входят в runtime-пул `/config`** (см. §6): значения TARGET-переменных
меняются на лету через WEBUI — на странице `/config` для каждой переменной —
выпадающий список допустимых значений. Смена влияет только на новые запросы
(маршрут выбирается на каждый запрос) и не рвёт активные соединения.

> **Пер-сессионное переопределение (v0.9.5).** Общая настройка приложения —
> дефолт для всех сессий; для отдельного `session_id` TARGET (как и Log)
> переопределяется прямо в таблице `/sessions` (WEBUI §4) или через
> `POST /api/sessions/settings`, не затрагивая остальных. Вернуться к общей
> настройке — снять переопределение (`clear`): домен TARGET совпадает с общим,
> состояния `inherit` нет (v0.9.9), а WEBUI снимает запись, когда выбрано
> значение, равное текущему общему. Переопределения живут в памяти процесса
> (не переживают перезапуск) — см. [`docs/routing.md`](routing.md) §2.4 и
> `backend_adapter/session_settings.py`.

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_PROXY_PORT` | `9999` | Порт, на котором адаптер слушает входящие подключения от Claude Code. |
| `ADAPTER_ENDPOINT_HOST` | `127.0.0.1` | Адрес (host), на котором слушает HTTP-эндпоинт адаптера. Пусто/не задано — дефолт `127.0.0.1` (localhost, только локально). `0.0.0.0` — слушать на всех интерфейсах (доступ из сети). |
| `ADAPTER_TIMEOUT` | `300` | Таймаут ожидания ответа от бэкенда (в секундах). Однопоточный запрос может ждать до этого значения. |
| `ADAPTER_RETRY_COUNT` | `3` | Количество повторных попыток при ошибке соединения с бэкендом. |
| `ADAPTER_REASONING_RETRY` | `2` | **Подъём `max_tokens` при `reasoning_budget_exhausted`** (v0.9.9). Reasoning-модель потратила весь бюджет на внутренние рассуждения — бэкенд отвечает HTTP 502 с этим `type` и рецептом «Увеличьте max_tokens». Адаптер поднимает `max_tokens` и немедленно повторяет запрос **без sleep** (тело изменилось, а не сеть подвела). Значение — сколько подъёмов разрешено за запрос; `0` — механизм выключен (прежнее поведение: 502 уходит клиенту как есть). |
| `ADAPTER_REASONING_MIN_TOKENS` | `8192` | Нижняя граница (пол) при подъёме `max_tokens`: новое значение — `max(текущее × 4, ADAPTER_REASONING_MIN_TOKENS)`. Потолок `sanitize_max_tokens` (16384) здесь **не** применяется: причина ошибки — «слишком мало», а не «слишком много». |

> **Бюджеты попыток.** Повтор при `reasoning_budget_exhausted` идёт в том же цикле попыток, что и обычный ретрай, поэтому **общее число HTTP-запросов к бэкенду ≤ `ADAPTER_RETRY_COUNT`**, а счётчик `ADAPTER_REASONING_RETRY` лишь ограничивает, сколько из этих попыток могут поднимать `max_tokens`. При `ADAPTER_RETRY_COUNT=1` подъём отправить уже некуда — механизм фактически выключен.

> Адаптер использует `ThreadingHTTPServer` — каждый запрос обрабатывается в отдельном потоке, поэтому параллельные запросы Claude Code (конкурентные tool calls) не блокируют друг друга.

## 3. Дефолтные: режимы стриминга

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_STREAMING_ENABLE` | `1` (включён) | **Рубильник стриминга.**<br>• `1` — если клиент просит `stream=true`, адаптер пробрасывает это бэкенду и стримит SSE-чанки построчно в реальном времени.<br>• `0` — полный откат к старому поведению: адаптер ВСЕГДА шлёт бэкенду `stream=False` и ждёт ответ целиком. Аварийный режим, если конкретный backend криво стримит. |
| `ADAPTER_STREAM_INCLUDE_USAGE` | `1` (включён) | **Передача токенов usage в стриме.**<br>• `1` — адаптер просит бэкенд прислать usage-статистику через `stream_options.include_usage=true`. Backend возвращает `prompt_tokens` и `completion_tokens` в последнем SSE-чанке, и адаптер передаёт их клиенту.<br>• `0` — не запрашивать usage. Используется, если backend падает на неизвестном поле `stream_options` (старые версии OpenAI-совместимых серверов). |

> **Баг-факт:** без `stream_options.include_usage` (и без флага `ADAPTER_STREAM_INCLUDE_USAGE=1`) клиент Claude Code видел `input_tokens=0` на протяжении всей сессии и не мог оценивать заполнение контекстного окна. В стримах, где backend не вернул usage, адаптер подставляет эвристику `chars / 4` и помечает значение как оценочное.

## 4. Дефолтные: маппинг моделей

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_MODELS_MAPPING` | *(пусто)* | Строка маппинга моделей формата `agent_model:backend_model,agent_model2:backend_model2`. **Входит в runtime-пул `/config`** (v0.9.3, §6): строку можно править на лету текстовым полем страницы `/config` — `set_runtime_config` перестраивает словарь `config._MAP` на месте, следующий запрос резолвит модель по новому маппингу, перезапуск не нужен. Указывает, какая модель бэкенда используется для каждой модели агента (Claude Code). |

### Зачем нужен маппинг: организация рабочего окружения субагентов

Каждый субагент (Explore, Plan, general-purpose и т.д.) работает в собственном
экземпляре агента и запрашивает ту модель, что указана в его конфигурации
(например ``). Без маппинга адаптер передал бы это имя
бэкенду как есть — а бэкенд (например [OI]-совместимый шлюз к Qwen) такого
имени не знает и отвечает ошибкой. Маппинг `agent_model:backend_model` приводит
имя модели агента к реально существующей на бэкенде — и тогда несколько
субагентов с разными моделями могут работать одновременно через один адаптер,
не конфликтуя за имя модели.

### Пример

```bash
export ADAPTER_MODELS_MAPPING="claude-sonnet-4-20250514:k2-05,claude-opus-4-20250514:k2-05-opus"
```

Здесь `claude-sonnet-4-20250514` от агента будет заменён на `k2-05` для бэкенда. Формат строки — пары через двоеточие, разделённые запятыми. Пустая строка — маппинг отключён.

> Маппинг применяется **до** проверки `ADAPTER_STRICT_MODELS` — то есть модель, преобразованная маппингом, проходит валидацию по списку доступных бэкенда под своим новым именем (`backend_model`), а не по имени агента.

## 5. Дефолтные: валидация моделей

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_STRICT_MODELS` | `1` (строгий) | **Режим валидации моделей.**<br>• `1` (строгий) — адаптер при запуске опрашивает бэкенд (`GET /v1/models`) и принимает **только** модели, перечисленные в ответе. Любая другая модель будет отвергнута.<br>• `0` (разрешающий) — валидация по списку отключена, любые модели принимаются. |
| `ADAPTER_MODEL_USAGE_ENABLE` | `1` (включён) | **Учёт использованных моделей** (секция «Models in use» статус-страницы `/` — см. WEBUI §3; модуль `backend_adapter/model_usage.py`). Каждый запрос агента после strict-проверки модели (имя из BODY, до маппинга) заносит модель в таблицу: счётчик обращений, имя бэкенда, время первого обращения, а также **токены usage ответов бэкенда** — колонки «Input» (`usage.prompt_tokens`) и «Output» (`usage.completion_tokens`) по всем успешным попыткам; ответы без usage (ошибки, обрывы, бэкенд без usage) в учёт не попадают (колонки — «0»). Колонка **Cost** — стоимость накопленных токенов по тарифу модели (`ADAPTER_MODELS_TARIFFS`, считается на лету при отображении). Сетевых проверок при учёте нет: запись строки не ходит в бэкенд и не задерживает запрос (дымовые пробы эндпойнтов сняты в v0.9.9). Колонки «Вызовов/Input/Output» обновляются на открытой странице сами (JS каждые ~5 с, `/api/model-usage/snapshot`).<br>• Таблица **персистентна**: сохраняется в YAML-файл `model-usage.yaml` в папке состояния `ADAPTER_DATA_ROOT/var` (см. §6) и загружается при старте — счётчики переживают перезапуски адаптера.<br>• `1` (дефолт) — учёт обращений и накопление токенов;<br>• `0` — накопление токенов отключено, учёт обращений (счётчик «Вызовов») остаётся (колонки Input/Output — «0»); персистентность работает независимо от мастер-флага. В runtime-пул `/config` не входит. |

В runtime-пул `/config` не входит — смена требует перезапуска. |

### Формат файла тарифов (`ADAPTER_MODELS_TARIFFS`)

Стоимость строки считается **на лету** из токенов и тарифа на момент
отображения страницы: `cost = input_tokens×input_price/price_per +
output_tokens×output_price/price_per` (колонки Input/Output — из
usage-блоков ответов; тарифы — из этого файла). Структура YAML:

```yaml
tariffs:
  - name: qwen2.5-coder-32b    # имя клиентской модели (как в BODY запроса)
    backend: pvapi             # опционально; при задании тариф матчится
                               #   только для этого бэкенда, без поля — для
                               #   любого бэкенда (wildcard)
    input_price: 10            # цена за price_per входных токенов
    output_price: 20           # цена за price_per выходных токенов
    currency: RUB              # 3-буквенный код валюты (USD, RUB, …)
    price_per: 1000000         # база — на сколько токенов дана цена
                               #   (дефолт 1; 0/None трактуется как 1)
```

- **Запятая — десятичный разделитель** цен: `input_price: 0,02` (PyYAML
  читает такое как строку — парсер нормализует в `0.02`).
- Модель не в тарифах / **нулевая цена** (бесплатная модель — не ошибка) /
  токены ещё не накоплены (после «Сбросить», 0/0) — колонка Cost
  показывает «--».
- Формат вывода — «N,NN CUR»: `0,25 USD`, `133,00 RUB`; сумма ≥ 10 000 —
  компактно как токены (`12k3 USD`), колонка остаётся узкой.
- Файл **перечитывается с диска** при загрузке накопленных счётчиков
  (model-usage.yaml) и при добавлении новой модели в таблицу; каждый
  полноценный рендер страницы (GET `/`) тоже перечитывает его — правка
  тарифа видна после перезагрузки страницы без рестарта адаптера.
- Битый/недоступный файл — колонка Cost показывает «--», адаптер работает
  дальше (ошибка — в консольный лог).

### Настройка агента (QwenCode) — передача id сессии

QwenCode (проверено на 0.23.2) **не передаёт id сессии ни заголовком, ни полем
тела** — в запросе есть только `user-agent` и `x-stainless-*`. Поэтому без
настройки клиента все обращения протоколируются как `session=unknown` (в
консоли `[REQ] POST /v1/chat/completions session=unknown`, а per-session логи
и строки страницы `/sessions` сливаются в одну).

Штатный механизм — `customHeaders` провайдера с плейсхолдером `${session_id}`
плюс глобальный флаг, разрешающий подстановку в заголовки. В
`~/.qwen/settings.json` — флаг на верхнем уровне, а `customHeaders` внутри
`generationConfig` **каждого** провайдера:

```json
{
  "outboundCorrelation": { "allowDynamicHeaderValues": true },
  "modelProviders": {
    "openai": [
      {
        "id": "lfm2",
        "baseUrl": "http://127.0.0.1:9999/v1",
        "generationConfig": {
          "customHeaders": { "X-Claude-Code-Session-Id": "${session_id}" }
        }
      }
    ]
  }
}
```

Имя заголовка выбираете вы; штатно указывают `X-Claude-Code-Session-Id` —
то же, что шлёт [CC] CLI, и оно уже есть в дефолтном `ADAPTER_SESSION_HEADER`.
Альтернатива — своё имя (например, `x-opencode-session`): тогда задайте его и
в `customHeaders`, и в `ADAPTER_SESSION_HEADER`.

После настройки адаптер запишет честный id — тот же, что печатает
`qwen --resume <uuid>` и что стоит в имени `session-*.jsonl`/`session-*.log`.
Оговорка: id ротируется на `/new` и `/resume` — после смены сессии в логах
появится новый идентификатор.

## 7. Дефолтные: трассировка (trace) — лимиты обрезки

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_TRACE_REASONING_MAX_CHARS` | `0` (без ограничения) | Максимальная длина поля `reasoning` в trace-записях. `0` — без обрезки. |
| `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS` | `0` (без ограничения) | Максимальная длина JSON-поля `input` в tool_call записях trace. `0` — без обрезки. |

Формат trace-записи — JSONL, каждая строка содержит:

- `ts` — метка времени
- `session_id` — ID сессии
- `req_id` — ID запроса
- `seq` — монотонно возрастающий номер
- `event` — тип события (`response_content`, `tool_call`, `usage_report` и др.)
- `...fields` — дополнительные поля в зависимости от события

Записи проходят через `redact` — чувствительные данные (токены, ключи) автоматически заменяются на `***`.

### Runtime-пул: переключение на лету без перезапуска

Часть переменных debug-записи и рубильников поведения НОВЫХ запросов можно
менять на **работающем** адаптере через веб-интерфейс — страница
`http://127.0.0.1:<ADAPTER_WEBUI_PORT>/config` (эндпойнт `/config`,
`webui_config_api.py`). На странице — форма с текущими значениями пула; POST
применяет их через `config.set_runtime_config()` (неверные типы и неизвестные
ключи молча игнорируются) и сообщает **только об ошибках** — плашки
«Применено» нет (v0.9.3): успешное применение видно по колонке «текущее».

В **runtime-пул** (`RUNTIME_CONFIG_POOL` в `config.py`) входят переменные,
чьё значение безопасно применить на следующем же вызове/запросе — их чтение
кодом переведено на живые обращения `config.ADAPTER_X` (не снимок на
импорте):

- **bool** — объём записи: `ADAPTER_DEBUG` (файловая запись: логи, трейсы,
  `*.parts`-дампы — v0.9.10, одним флагом);
- **bool** — рубильники поведения новых запросов и логов:
  `ADAPTER_SENSITIVE_LOGGING_ENABLE` (отключение санитайзера — секреты
  выводятся в открытом виде), `ADAPTER_STREAMING_ENABLE`,
  `ADAPTER_STREAM_INCLUDE_USAGE`, `ADAPTER_STRICT_MODELS`;
- **int**: `ADAPTER_DEBUG_TRIM`, `ADAPTER_TRACE_REASONING_MAX_CHARS`,
  `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS`;
- **enum (3)** — TARGET-маршрутизация входов (v0.9.1, выбираются выпадающими
  списками): `ADAPTER_MESSAGES_TARGET`, `ADAPTER_COMPLETIONS_TARGET`,
  `ADAPTER_RESPONSES_TARGET` (см. §1а). Допустимые значения — домен
  `TARGET_ALLOWED_VALUES` в `config.py`; значение применяется на следующем же
  запросе (маршрутизатор читает `config.ADAPTER_*_TARGET` на каждый вызов) и
  влияет только на новые запросы, не рвя активные соединения;
- **str (1)** — `ADAPTER_MODELS_MAPPING` (v0.9.3, текстовое поле): строка
  маппинга моделей agent→backend в формате env (§4). Применяется на лету —
  `set_runtime_config` перестраивает словарь `config._MAP` **на месте**
  (модули держат ссылку на словарь, а не снимок), поэтому следующий запрос
  резолвит модель по новому маппингу без перезапуска. Пустая строка валидна —
  маппинг отключается. Формат парсера остаётся лояльным (как у env): битые
  пары молча пропускаются.

Строковые переменные в пуле — enum-поля TARGET (домен значений фиксирован) и
свободная строка `ADAPTER_MODELS_MAPPING` (домен не фиксирован); прочих
строковых переменных нет (v0.8.6: прежние селекторы подробности удалены —
консоль всегда с обрезкой `ADAPTER_DEBUG_TRIM`, файл всегда полный).

Переменные, менять которые на лету **нельзя** (влияют на активные соединения,
раскладку файлов или структуру конфигурации, в пул не входят): сеть и адреса
прослушивания (`ADAPTER_PROXY_PORT`, `ADAPTER_ENDPOINT_HOST`,
`ADAPTER_WEBUI_PORT`, `ADAPTER_WEBUI_HOST`), таймауты/ретраи
(`ADAPTER_TIMEOUT`, `ADAPTER_RETRY_COUNT`, `ADAPTER_REASONING_RETRY`,
`ADAPTER_REASONING_MIN_TOKENS`), бэкенды
(`ADAPTER_BACKEND_CONFIG`), стартовые режимы и служебные пути
(`ADAPTER_DETACH_ENABLE`, `ADAPTER_PIDFILE`), `ADAPTER_DATA_ROOT`
(идентичность корня данных не должна меняться посреди сессии).

Вне пула (смена — с рестартом) также лимиты, не влияющие на отдельный
запрос: `ADAPTER_ARTIFACT_DEBOUNCE`, `ADAPTER_MODEL_USAGE_SAVE_INTERVAL`,
`ADAPTER_SESSIONS_TABLE`.

**Персистентность пула (v0.9.6).** Значения пула сохраняются в файле
состояния (`ADAPTER_STATE`, дефолт `state.yaml` в `ADAPTER_DATA_ROOT/var`) и
применяются при старте **поверх env** — подробности в таблице §6, строка
`ADAPTER_STATE`. Каждое изменение через `POST /config` перезаписывает файл
атомарно. Пер-сессионные переопределения (`session_settings`) в файл **не**
попадают.

### Валидация env при старте (v0.9.6)

Старт предваряется строгой проверкой env (модуль `backend_adapter/env_validate.py`,
вызывается из `backend-adapter.py` **до** импорта `config`):

- **int-переменные** (`ADAPTER_PROXY_PORT`, `ADAPTER_TIMEOUT`, `ADAPTER_RETRY_COUNT`,
  `ADAPTER_REASONING_RETRY`, `ADAPTER_REASONING_MIN_TOKENS`,
  `ADAPTER_DEBUG_TRIM`, `ADAPTER_TRACE_*`, порты WEBUI/EXPORTER,
  `ADAPTER_MODEL_USAGE_SAVE_INTERVAL`, `ADAPTER_SESSIONS_TABLE`) — значение
  обязано парситься в целое;
- **bool-переменные** (`ADAPTER_DEBUG_ENABLE`,
  `ADAPTER_DETACH_ENABLE`, `ADAPTER_STRICT_MODELS`, `ADAPTER_STREAMING_ENABLE`,
  `ADAPTER_STREAM_INCLUDE_USAGE`, `ADAPTER_SENSITIVE_LOGGING_ENABLE`,
  `ADAPTER_EXPORTER_ENABLE`, `ADAPTER_MODEL_USAGE_ENABLE`)
  — только `1/0/true/false/yes/no/on/off` (регистр и пробелы не важны; пусто —
  выключено). Опечатка (`off` в старом коде молча трактовалось как включено)
  больше не даёт противоположного поведения;
- невалидное значение → `[FATAL] <имя>=<знач>: ожидается <тип>` и `sys.exit(1)` —
  адаптер не стартует (как и при непустом `ADAPTER_BACKEND_CONFIG` / корне-файле).

YAML-файлы проверяются **мягко** (принцип «битый файл — работаем дальше»):
`adapter.yaml` — записи без `name`/`base`/`key` или с `base` не-http(s)
пропускаются с `[WARN]`; `tariffs.yaml` — битые записи пропускаются с
`[WARN]` (причина в сообщении); `state.yaml` — невалидный ключ/тип
пропускается с `[WARN]`, остальное применяется.
