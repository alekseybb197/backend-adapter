# Environment Variables — backend-adapter

> Параметры настройки режимов работы адаптера `backend-adapter.py`.
> Все переменные читаются из окружения перед стартом (модуль `backend_adapter/config.py`).
> Если не заданы — используются значения по умолчанию, указанные в столбце *Default*.

---

## Ноль-конфиг (zero-config) против полной настройки

Все переменные делятся на две группы:

1. **Обязательные при старте** — без них адаптер не запускается.
   Сейчас это одна переменная: `ADAPTER_BACKEND_CONFIG` (внешние LLM-бэкенды).
2. **Дефолтные (можно не задавать)** — всё остальное. Дефолты выбраны так,
   чтобы адаптер работал с **минимальными запросами к ресурсам**:
   - **не пишет логов на диск** (`ADAPTER_DEBUG_ENABLE=0` — файловая запись
     выключена; консольные debug-логи безусловны и всегда видны, с обрезкой
     `ADAPTER_DEBUG_TRIM`),
   - **не пишет per-session дампы** (`ADAPTER_DEBUG_PARTS=0` — JSON/YAML
     дампы частей протокола выключены),
   - **показывает статус на дефолтном порту** (WEBUI поднимается **всегда** —
     флага отключения нет; статус-страница `/` на `127.0.0.1:8765`, корень —
     `ADAPTER_DEBUG_LOGPATH`, по умолчанию `./tmp/logs`; вкладка сессий пуста,
     пока файловая запись не включена `ADAPTER_DEBUG_ENABLE=1`).

Минимальный запуск:

```bash
# Примеры — docs/samples/sample.adapter.yaml и sample.adapter.env
export ADAPTER_BACKEND_CONFIG="./adapter.yaml"           # внешний LLM-бэкенд
# ... + переменная токена, на которую ссылается поле key в YAML
python3 backend-adapter.py
```

## 1. Обязательные при старте: подключение к бэкенду

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_BACKEND_CONFIG` | *(пусто)* | **Обязательна при старте. Единственный способ конфигурации бэкенда.** Путь к YAML-файлу со структурой `backend:` (список записей `name`/`base`/`key`). Пример — `docs/samples/sample.adapter.yaml`. Не задан — старт невозможен: адаптер завершается с `[FATAL]` и подсказкой. |

> **Стартовый probe не настраивается:** при `ADAPTER_STRICT_MODELS=1` (дефолт)
> адаптер при старте опрашивает каждый бэкенд (`GET /v1/models`) — это не
> env-рубильник, а факт работы: список доступных моделей нужен для
> валидации. Если бэкенд недоступен, адаптер продолжает старт
> (с предупреждением в консоль) — на проксирование это не влияет.

### Пример YAML-конфига бэкендов (пример файла — `docs/samples/sample.adapter.yaml`)

```yaml
backend:
  - name: home
    base: "http://127.0.0.1:8002"
    key: ADAPTER_HOME_KEY          # имя переменной окружения → подставляется реальное значение
  - name: litellm
    base: "https://llm.service.example.com"
    key: ADAPTER_LITELLM_KEY
    probe:                         # необязательно: модель на каждый API-эндпоинт пробы
      - completions: qwen3.6       #   /v1/chat/completions — этой моделью
      - responses: gpt-5-sol       #   /v1/responses — этой моделью
      - embeddings: text-embedding-3-small  #   /v1/embeddings — этой моделью
  - name: local
    base: "http://127.0.0.1:8000"
    key: ADAPTER_HOME_KEY
```

Поля каждого элемента:

- **`name`** — произвольный идентификатор бэкенда. Используется для префикса модели (при коллизиях) и для маршрутизации запросов (`&lt;backend_name&gt;.&lt;model&gt;`).
- **`base`** — базовый URL бэкенда (без `/v1/`).
- **`key`** — либо прямой токен, либо **имя переменной окружения**. Адаптер сначала подставляет значение переменной, затем использует его как Bearer-токен.
- **`probe`** *(необязательно)* — модель для дымовой пробы каждого API-эндпоинта
  (см. `ADAPTER_ENDPOINT_PROBE`, §5). Список пар `эндпоинт: модель` по коротким
  именам: `completions` (`/v1/chat/completions`), `messages` (`/v1/messages`),
  `responses` (`/v1/responses`), `embeddings` (`/v1/embeddings`). У разных
  эндпоинтов бэкенда могут быть свои модели (chat / responses / embeddings).
  **Политика «только явно указанные пробы»** (v0.8.5): пробуется ТОЛЬКО
  эндпоинт, перечисленный в `probe` с НЕПУСТОЙ моделью (модель сверяется со
  списком `/v1/models` бэкенда; не найдена — пропускается только этот
  эндпоинт с текстом в errors):
  - ключа `probe` нет / эндпоинт не перечислен / значение пустое
    (`messages:`) — эндпоинт **НЕ пробуется** (штатно, молча; у бэкенда без
    перечисленных проб колонка «Доступные API» пуста);
  - найденные пробой МОДЕЛИ эндпоинты (первое обращение, «Перепроверить»
    строки, загрузка model-usage.yaml) синхронизируются в общий кэш
    `_ENDPOINT_STATE` бэкенда (см. §6).

### Маршрутизация по бэкендам

1. Если в запросе модель содержит префикс `&lt;имя_бэкенда&gt;.` (например `litellm.qwen3.6-35b-a3b`), запрос отправляется на соответствующий бэкенд, а префикс обрезается.
2. Если модель встречается на нескольких бэкендах (коллизия), к её ID автоматически добавляется префикс `&lt;backend_name&gt;.model_id`.
3. Уникальные модели передаются как есть — адаптер сам найдёт подходящий бэкенд по списку.
4. Fallback — первый бэкенд в конфигурации (`_DEFAULT_BACKEND`).

## 1а. Входные эндпоинты (TARGET)

> **Что это.** Адаптер принимает **три** POST-эндпоинта входных запросов —
> `/v1/messages` (Anthropic Messages API), `/v1/chat/completions`
> ([OI] Chat Completions), `/v1/responses` ([OI] Responses API). Что делает
> адаптер с запросом на каждом входе (какой формат отдаёт бэкенду) — решает
> соответствующая TARGET-переменная: **префикс имени переменной = входной
> эндпоинт**. Входы, целевой формат которых `none`, не принимаются вовсе
> (404). **Полное описание принципов, реализованных маршрутов и перспектив —
> [`docs/routing.md`](routing.md).**

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_MESSAGES_TARGET` | `completions` | Куда направлять запросы с **`/v1/messages`** (Anthropic-формат). |
| `ADAPTER_COMPLETIONS_TARGET` | `none` | Куда направлять запросы с **`/v1/chat/completions`** ([OI]-формат). |
| `ADAPTER_RESPONSES_TARGET` | `none` | Куда направлять запросы с **`/v1/responses`** (Responses-формат). |

Допустимые значения всех трёх — одно из: **`completions`**, **`messages`**,
**`responses`** (целевой формат), **`auto`** (адаптер сам выбирает целевой
формат **только по кэшу результатов проб** — без сети в запросе; детали и
примеры — `docs/routing.md`), **`none`** (вход выключен: HTTP 404).

> **Дефолты — это нулевая настройка (100% прежнее поведение):** принимается
> только `/v1/messages`, который конвертируется в `chat.completions`
> (`ADAPTER_MESSAGES_TARGET=completions`); входы
> `/v1/chat/completions` и `/v1/responses` закрыты (`none`). Пример из
> задачи «принимать только messages, конвертировать в chat completions» —
> ровно эти дефолты: `ADAPTER_COMPLETIONS_TARGET=none,
> ADAPTER_MESSAGES_TARGET=completions, ADAPTER_RESPONSES_TARGET=none`.

**В runtime-пул `/config` не входят** (см. §6): TARGET-переменные меняют
топологию восприятия входных эндпоинтов и читаются на импорте, как
бэкенды/порты.

---

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_PROXY_PORT` | `9999` | Порт, на котором адаптер слушает входящие подключения от Claude Code. |
| `ADAPTER_ENDPOINT_HOST` | `127.0.0.1` | Адрес (host), на котором слушает HTTP-эндпоинт адаптера. Пусто/не задано — дефолт `127.0.0.1` (localhost, только локально). `0.0.0.0` — слушать на всех интерфейсах (доступ из сети). |
| `ADAPTER_TIMEOUT` | `300` | Таймаут ожидания ответа от бэкенда (в секундах). Однопоточный запрос может ждать до этого значения. |
| `ADAPTER_RETRY_COUNT` | `3` | Количество повторных попыток при ошибке соединения с бэкендом. |

> Адаптер использует `ThreadingHTTPServer` — каждый запрос обрабатывается в отдельном потоке, поэтому параллельные запросы Claude Code (конкурентные tool calls) не блокируют друг друга.

## 3. Дефолтные: режимы стриминга

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_STREAMING_ENABLE` | `1` (включён) | **Рубильник стриминга.**<br>• `1` — если клиент просит `stream=true`, адаптер пробрасывает это бэкенду и стримит SSE-чанки построчно в реальном времени.<br>• `0` — полный откат к старому поведению: адаптер ВСЕГДА шлёт бэкенду `stream=False` и ждёт ответ целиком. Аварийный режим, если конкретный backend криво стримит. |
| `ADAPTER_STREAM_INCLUDE_USAGE` | `1` (включён) | **Передача токенов usage в стриме.**<br>• `1` — адаптер просит бэкенд прислать usage-статистику через `stream_options.include_usage=true`. Backend возвращает `prompt_tokens` и `completion_tokens` в последнем SSE-чанке, и адаптер передаёт их клиенту.<br>• `0` — не запрашивать usage. Используется, если backend падает на неизвестном поле `stream_options` (старые версии OpenAI-совместимых серверов). |

> **Баг-факт:** без `stream_options.include_usage` (и без флага `ADAPTER_STREAM_INCLUDE_USAGE=1`) клиент Claude Code видел `input_tokens=0` на протяжении всей сессии и не мог оценивать заполнение контекстного окна. В стримах, где backend не вернул usage, адаптер подставляет эвристику `chars / 4` и помечает значение как оценочное.

## 4. Дефолтные: маппинг моделей

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_MODELS_MAPPING` | *(пусто)* | Строка маппинга моделей формата `agent_model:backend_model,agent_model2:backend_model2`. Указывает, какая модель бэкенда используется для каждой модели агента (Claude Code). |

### Зачем нужен маппинг: организация рабочего окружения субагентов

Каждый субагент (Explore, Plan, general-purpose и т.д.) работает в собственном
экземпляре агента и запрашивает ту модель, что указана в его конфигурации
(например ``). Без маппинга адаптер передал бы это имя
бэкенду как есть — а бэкенд (например [OI]-совместимый шлюз к Qwen) такого
имени не знает и отвечает ошибкой. Маппинг `agent_model:backend_model` приводит
имя модели агента к реально существующей на бэкенде — и тогда несколько
субагентов с разными моделями могут работать одновременно через один адаптер,
не конфликтуя за имя модели.

### Пример

```bash
export ADAPTER_MODELS_MAPPING="claude-sonnet-4-20250514:k2-05,claude-opus-4-20250514:k2-05-opus"
```

Здесь `claude-sonnet-4-20250514` от агента будет заменён на `k2-05` для бэкенда. Формат строки — пары через двоеточие, разделённые запятыми. Пустая строка — маппинг отключён.

> Маппинг применяется **до** проверки `ADAPTER_STRICT_MODELS` — то есть модель, преобразованная маппингом, проходит валидацию по списку доступных бэкенда под своим новым именем (`backend_model`), а не по имени агента.

## 5. Дефолтные: валидация моделей

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_STRICT_MODELS` | `1` (строгий) | **Режим валидации моделей.**<br>• `1` (строгий) — адаптер при запуске опрашивает бэкенд (`GET /v1/models`) и принимает **только** модели, перечисленные в ответе. Любая другая модель будет отвергнута.<br>• `0` (разрешающий) — валидация по списку отключена, любые модели принимаются. |
| `ADAPTER_ENDPOINT_PROBE` | `1` (включён) | **Дымовая проба API-эндпоинтов бэкендов** (что реально обслуживает бэкенд: `/v1/chat/completions`, `/v1/messages`, `/v1/responses`, `/v1/embeddings`).<br>• `1` (дефолт) — при каждой фоновой проверке бэкендов (старт адаптера, первый GET `/`, кнопка-иконка 🔃 «Перепроверить бэкенды» — см. WEBUI §6) шлётся короткий POST с `max_tokens:1` **только на перечисленные в `probe` эндпоинты с непустой моделью** (политика «только явно указанные», см. §1; неперечисленные/пустые/без ключа `probe` не пробуются). Кнопка 🔃 дополнительно **перечитывает** `ADAPTER_BACKEND_CONFIG` — бэкенды добавляются/удаляются без рестарта (битый YAML — прежние остаются, `[WARN]`). Результат кэшируется ~60 с (`ENDPOINT_PROBE_TTL`) и показывается в колонке «Доступные API» статус-страницы; фактическая проба пишется в консоль блоком `[ENDPOINT_PROBE]` (безусловно, v0.8.6).<br>• `0` — автопроба выключена: колонка показывает «не опрошено», сетевых POST-проб нет. Классификация по HTTP-коду: `200` — работает (показывается зелёным ✓); любой не-200 (`400/401/405/429`, `404`, прочие 4xx/5xx) — не работает (на странице не показывается); сеть/таймаут — ошибка бэкенда. |
| `ADAPTER_MODEL_USAGE_ENABLE` | `1` (включён) | **Учёт использованных моделей** (секция «Models in use» статус-страницы `/` — см. WEBUI §6; модуль `backend_adapter/model_usage.py`). Каждый запрос агента после strict-проверки модели (имя из BODY, до маппинга) заносит модель в таблицу: счётчик обращений, имя бэкенда, время первого обращения, а также **токены usage ответов бэкенда** — колонки «Input» (`usage.prompt_tokens`) и «Output» (`usage.completion_tokens`) по всем успешным попыткам; ответы без usage (ошибки, обрывы, бэкенд без usage) в учёт не попадают (колонки — «0»). Колонка **Cost** — стоимость накопленных токенов по тарифу модели (`ADAPTER_MODELS_TARIFFS`, считается на лету при отображении). При ПЕРВОМ обращении к новой модели выполняется синхронная дымовая проба **по probe-перечню бэкенда** (политика «только явно указанные», см. §1: пробуются только эндпоинты, перечисленные в `probe` с непустой моделью; модель пробы — фактическое имя запроса; до 4×10 с — первый запрос модели ждёт); доступные (HTTP 200) показываются в колонке Endpoints строки. Повторные обращения к внесённой модели не перепроверяют никогда (только инкремент счётчика и токенов); обновить результаты проб строки — кнопка «Перепроверить» (POST `/api/model-usage/reprobe`, фоновая перепроба без сброса счётчиков). Колонки «Вызовов/Input/Output» обновляются на открытой странице сами (JS каждые ~5 с, `/api/model-usage/snapshot`). **Найденные пробой модели эндпоинты синхронизируются в общий кэш `config._ENDPOINT_STATE` бэкенда** (первое обращение, перепроверка строки, загрузка файла) — колонка «Доступные API» бэкенда и Prometheus-экспортёр их видят.<br>• Таблица **персистентна**: сохраняется в YAML-файл `model-usage.yaml` в корне WEBUI (= `ADAPTER_DEBUG_LOGPATH`, см. §6) и загружается при старте — счётчики переживают перезапуски адаптера.<br>• `1` (дефолт) — проба при первом обращении выполняется **всегда**, независимо от `ADAPTER_ENDPOINT_PROBE` (тот управляет только фоновой проверкой бэкендов); токены накапливаются;<br>• `0` — пробы и накопление токенов отключены, учёт обращений остаётся (колонка Endpoints — «—», Input/Output — «0»); персистентность работает независимо от мастер-флага. В runtime-пул `/config` не входит. |
| `ADAPTER_MODEL_USAGE_SAVE_INTERVAL` | `300` | **Период персистентного сохранения таблицы использованных моделей в YAML-файл** (сек; файл — `model-usage.yaml` в корне WEBUI = `ADAPTER_DEBUG_LOGPATH`, см. §6). «Грязная» таблица (инкременты счётчиков/токенов) сохраняется не чаще раза в период; создание новой строки модели, обнуление счётчиков строки (кнопка «Сбросить» / `POST /api/model-usage/reset`), удаление строки (кнопка «Удалить» ✕ / `POST /api/model-usage/delete`) и завершение работы адаптера (в т.ч. Ctrl-C) сохраняют сразу. Дефолт 300 — при жёстком kill (kill -9) теряется хвост ≤ 300 с (5 мин); при штатном завершении таблица сохраняется всегда. |
| `ADAPTER_MODELS_TARIFFS` | *(пусто)* | **Путь к YAML-файлу с тарифами моделей** — для колонки **Cost** секции «Models in use» статус-страницы `/` (стоимость накопленных токенов строки по тарифу на момент отображения; см. `ADAPTER_MODEL_USAGE_ENABLE` выше). Формат и перечитывание — см. примечание под таблицей. Пусто / файл не читается — колонка Cost показывает «--». В runtime-пул `/config` не входит (см. §6). |

### Формат файла тарифов (`ADAPTER_MODELS_TARIFFS`)

Стоимость строки считается **на лету** из токенов и тарифа на момент
отображения страницы: `cost = input_tokens×input_price/price_per +
output_tokens×output_price/price_per` (колонки Input/Output — из
usage-блоков ответов; тарифы — из этого файла). Структура YAML:

```yaml
tariffs:
  - name: qwen2.5-coder-32b    # имя клиентской модели (как в BODY запроса)
    backend: pvapi             # опционально; при задании тариф матчится
                               #   только для этого бэкенда, без поля — для
                               #   любого бэкенда (wildcard)
    input_price: 10            # цена за price_per входных токенов
    output_price: 20           # цена за price_per выходных токенов
    currency: RUB              # 3-буквенный код валюты (USD, RUB, …)
    price_per: 1000000         # база — на сколько токенов дана цена
                               #   (дефолт 1; 0/None трактуется как 1)
```

- **Запятая — десятичный разделитель** цен: `input_price: 0,02` (PyYAML
  читает такое как строку — парсер нормализует в `0.02`).
- Модель не в тарифах / **нулевая цена** (бесплатная модель — не ошибка) /
  токены ещё не накоплены (после «Сбросить», 0/0) — колонка Cost
  показывает «--».
- Формат вывода — «N,NN CUR»: `0,25 USD`, `133,00 RUB`; сумма ≥ 10 000 —
  компактно как токены (`12k3 USD`), колонка остаётся узкой.
- Файл **перечитывается с диска** при загрузке накопленных счётчиков
  (model-usage.yaml) и при добавлении новой модели в таблицу; каждый
  полноценный рендер страницы (GET `/`) тоже перечитывает его — правка
  тарифа видна после перезагрузки страницы без рестарта адаптера.
- Битый/недоступный файл — колонка Cost показывает «--», адаптер работает
  дальше (ошибка — в консольный лог).

## 7. Дефолтные: трассировка (trace) — лимиты обрезки

| Переменная | Default | Описание |
|---|---|---|
| `ADAPTER_TRACE_REASONING_MAX_CHARS` | `0` (без ограничения) | Максимальная длина поля `reasoning` в trace-записях. `0` — без обрезки. |
| `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS` | `0` (без ограничения) | Максимальная длина JSON-поля `input` в tool_call записях trace. `0` — без обрезки. |

Формат trace-записи — JSONL, каждая строка содержит:

- `ts` — метка времени
- `session_id` — ID сессии
- `req_id` — ID запроса
- `seq` — монотонно возрастающий номер
- `event` — тип события (`response_content`, `tool_call`, `usage_report` и др.)
- `...fields` — дополнительные поля в зависимости от события

Записи проходят через `redact` — чувствительные данные (токены, ключи) автоматически заменяются на `***`.

### Runtime-пул: переключение на лету без перезапуска

Часть переменных debug-записи и рубильников поведения НОВЫХ запросов можно
менять на **работающем** адаптере через веб-интерфейс — страница
`http://127.0.0.1:<ADAPTER_WEBUI_PORT>/config` (эндпойнт `/config`,
`webui_config_api.py`). На странице — форма с текущими значениями пула; POST
применяет их через `config.set_runtime_config()` (неверные типы и неизвестные
ключи молча игнорируются) и показывает, что применилось.

В **runtime-пул** (`RUNTIME_CONFIG_POOL` в `config.py`) входят переменные,
чьё значение безопасно применить на следующем же вызове/запросе — их чтение
кодом переведено на живые обращения `config.ADAPTER_X` (не снимок на
импорте):

- **bool** — объём записи: `ADAPTER_DEBUG` (файловая запись),
  `ADAPTER_DEBUG_PARTS` (per-session дампы `.json`+`.yaml`);
- **bool** — рубильники поведения новых запросов и логов:
  `ADAPTER_SENSITIVE_LOGGING_ENABLE` (отключение санитайзера — секреты
  выводятся в открытом виде), `ADAPTER_STREAMING_ENABLE`,
  `ADAPTER_STREAM_INCLUDE_USAGE`, `ADAPTER_STRICT_MODELS`;
- **int**: `ADAPTER_DEBUG_TRIM`, `ADAPTER_TRACE_REASONING_MAX_CHARS`,
  `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS`.

Строковых переменных в пуле нет (v0.8.6: прежние селекторы подробности
удалены — консоль всегда с обрезкой `ADAPTER_DEBUG_TRIM`, файл всегда
полный).

Переменные, менять которые на лету **нельзя** (влияют на активные соединения,
раскладку файлов или структуру конфигурации, в пул не входят): сеть и адреса
прослушивания (`ADAPTER_PROXY_PORT`, `ADAPTER_ENDPOINT_HOST`,
`ADAPTER_WEBUI_PORT`, `ADAPTER_WEBUI_HOST`), таймауты/ретраи
(`ADAPTER_TIMEOUT`, `ADAPTER_RETRY_COUNT`), бэкенды
(`ADAPTER_BACKEND_CONFIG`, `ADAPTER_MODELS_MAPPING`), стартовые режимы
(`ADAPTER_DETACH_ENABLE`, `ADAPTER_PIDFILE`), `ADAPTER_DEBUG_LOGPATH`
(идентичность директории логов не должна меняться посреди сессии).
