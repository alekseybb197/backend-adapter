### 2026-09-08 Группа: CI к набору проверок, JSON-файлы результатов проверок в LOGPATH, [EXIT] Bye, PID-файл в LOGPATH (v0.9.0)

**Цель:** (1) CI должен отвечать набору проверок проекта; (2) результаты
проверок бэкендов на доступные модели и эндпоинты — в LOGPATH как плоские
JSON-файлы фиксированных имён (безусловный канал, каждый раз перезапись);
(3) вернуть «[EXIT] Bye» как консольное сообщение завершения; (4) PID-файл —
в единую директорию артефактов.

**Решение:**
- **CI к набору проверок** — `.github/workflows/ci.yml`: mypy
  `--strict --ignore-missing-imports` (как локальная проверка CLAUDE.md),
  оба job'а ставят `requirements-dev.txt` вместо инлайн-пакетов;
  `pyproject.toml` version синхронизирована с `__version__`;
- **JSON-файлы результатов проверок (новый модуль `probe_json.py`)** —
  `<имя_бэкенда>.models.json` и `<имя_бэкенда>.<конверт.модель>.
  <pname>.json` в корне `ADAPTER_DEBUG_LOGPATH`, каждый раз перезапись
  (tmp + os.replace); канал БЕЗУСЛОВНЫЙ (вне ENABLE/PARTS/TRIM; гейт —
  наличие LOGPATH), провал записи молча глотается; охват — все события
  (`.models.json`: стартовый init/фоновый refresh/reload; эндпоинт-файлы:
  фоновая probe_endpoints и пер-модельные пробы usage-таблицы — единая
  точка `_probe_model_endpoints`); конвертация имени модели — `/` и `:` →
  `_`; имя эндпоинта — короткое из ENDPOINT_PROBES; санитайзер: секретные
  ключи маскируются структурно (рекурсивно, маской redact._mask) + redact()
  текстом, при SENSITIVE=1 — полные данные;
- **`[EXIT] Bye`** — печать перенесена из finally backend-adapter.py внутрь
  `shutdown.graceful_shutdown` (после успешного завершения процедуры) —
  контракт модуля покрывается unit-тестами;
- **PID-файл в LOGPATH** — `daemon._write_pidfile()`: `ADAPTER_PIDFILE`
  задаёт ИМЯ (basename), файл кладётся ВСЕГДА в LOGPATH (дефолт
  `adapter.pid`), директория создаётся при записи.

**Следствия:** результаты проверок читаются из LOGPATH плоскими JSON без
включения файловой записи (модели — даже при ENABLE=0, как .err); конец
работы маркируется «[EXIT] Bye» из модуля завершения; PID — в единой
директории. Breaking change: `ADAPTER_PIDFILE` = имя (в LOGPATH), не путь.
Поведение проксирования не меняется. Покрыто unit-тестами (probe_json,
точки записи config/model_usage, shutdown, daemon) и интеграционным
прогоном (test_manual_check: JSON-файлы в logs_dir при ENABLE=0).

### 2026-09-08 Фикс Cost-ячейки live-поллинга — setHtml/innerHTML вместо textContent (v0.9.0)

**Цель:** убрать буквальную разметку `<span style="color:#aaa">—</span>` в
колонке Cost при live-поллинге счётчиков.

**Решение:** `usage_poll` ставил ячейку Cost через `set()` → `textContent`,
а снимок `/api/model-usage/snapshot` несёт `cost_html` — готовый HTML
(`_cost_cell_html`: серая «—» для нулевых токенов/модели без тарифа, суммы —
plain text). Для «—»-кейсов textContent показывал разметку буквально при
каждом поллинге/рендере. Введён отдельный сеттер `setHtml` (innerHTML-
сравнение + присваивание) для ячейки Cost (индекс 5): серверный HTML
ставится как HTML; счётчики Вызовов/Input/Output остаются на `textContent`;
innerHTML-сравнение не трогает DOM, если значение не изменилось. Единый
источник HTML — `_cost_cell_html` (рендер и снимок); контракты снимка не
меняются.

**Следствия:** «—» в колонке Cost отображается серой разметкой, а не
текстом; реальные суммы (plain text) не ломались и не ломаются. Поведение
проксирования не меняется. Покрыто тестами (наличие `setHtml`/
`setHtml(5, row["cost_html"])` в usage_poll-скрипте). Ветка feature/v0.9.0
в WIP.

### 2026-09-08 .err-протокол инцидентов взаимодействия с бэкендом (v0.9.0)

**Цель:** протокол «записываем взаимодействие с бэкендом до ответа»: при
ФИНАЛЬНОМ ответе клиенту **4xx/5xx** реального прокси-запроса агента
(`POST /v1/messages` → `server.do_POST`) — после ретраев/таймаутов/исчерпания
попыток — в директорию логов пишется **специальный файл ошибок** `.err`
(имя как у session-лога, расширение `.err`), с полным запросом к бэкенду и
полным сообщением об ошибке последней попытки — **без обрезки** по
`ADAPTER_DEBUG_TRIM` и **вне** `ADAPTER_DEBUG_ENABLE` (безусловный канал).

**Решение:**
- **`session_log.write_error_file(session_id, req_id, *, final_status,
  backend_url, model, out_body, err_body)`** — новый безусловный канал
  записи. Гейтится ТОЛЬКО наличием лог-директории `ADAPTER_DEBUG_LOGPATH`
  (всегда непуста, дефолт `./tmp/logs`): НЕ зависит от `ADAPTER_DEBUG_ENABLE`
  (при `0` тоже пишется), НЕ от `ADAPTER_DEBUG_PARTS`, НЕ обрезается по
  `ADAPTER_DEBUG_TRIM` (полные запрос и ошибка). Санитайзер уважает
  `ADAPTER_SENSITIVE_LOGGING_ENABLE`: по умолчанию секреты redact'ятся,
  при `=1` — полные данные (живое чтение config, как logger._write).
  Никогда не бросает исключений (наблюдательный канал);
- **файл** — `session-<ts>-<safe8>.err` через `_open_session_file("err",
  ...)`: живёт в той же директории debug-логов и **делит с `.log` общий
  `_session_file_ts` сессии** (тот же ts — имя отличается только
  расширением); общий FIFO-пул `_session_logs`. Формат — в духе session-
  лога, timestamp-строки с `[req_id]`: шапка-метаданные (`session_id`,
  `final_status`, `model`, `backend_url`), `[REQUEST]` — полное тело
  запроса к бэкенду, `[BACKEND_ERROR]` — полное сообщение об ошибке
  последней попытки;
- **server.py — вызов из финальных точек ошибки** обеих веток (стрим и
  не-стрим): `final_status` = код HTTPError последней попытки (не-retry
  4xx; исчерпанные 429/502/503/504), `504` после таймаутов, `502` после
  прочих ошибок. **Один `.err` на запрос**, не на попытку. Scope — только
  реальные прокси-запросы `do_POST`; 400-пути ДО бэкенда (нет `/v1/messages`,
  Invalid JSON, нет `model`, strict-400) `.err` НЕ пишут — бэкенд не
  участвовал; дымовые пробы (config/webui_status) — свои консольные логи.

**Следствия:** любой финальный сбой взаимодействия с бэкендом оставляет
файл-инцидент с полными данными для разбора (причины + ошибки), независимо
от настроек подробности файловой записи; поведение проксирования не
меняется. Покрыто: unit-тестами `session_log` (безусловность при ENABLE=0,
полнота при малом TRIM, redact по умолчанию / полные при SENSITIVE=1,
общий ts с `.log`) и серверными тестами (400 не-стрим/стрим → `.err`;
502 после ретраев → один `.err`; 200-успех → нет файла; локальные 400 ДО
бэкенда → нет файла; redact/полные данные). Ветка feature/v0.9.0 в WIP.

### 2026-09-08 Реформа логирования: консоль с TRIM / файл полный; удалены TAGS_FULL·TOOLS·TOOLS_ERROR; TAGS_OUT → ADAPTER_DEBUG_PARTS; иконки строк 🔄/⏪/🗑

**Цель:** после того как консольные debug-логи стали безусловными, убрать
устаревшие «селекторы подробности» и зафиксировать простую модель: консоль
всегда печатается с обрезкой `ADAPTER_DEBUG_TRIM`, файловый канал при
`ADAPTER_DEBUG_ENABLE=1` несёт ПОЛНЫЕ строки без обрезки, per-session дампы
`.json+.yaml` одним флагом покрывают все логгируемые части. Заодно сменить
иконки действий строк таблицы «Models in use»: ⟳/↺/✕ → 🔄/⏪/🗑.

**Решение:**
- **`logger._write(msg)`** — единая точка вывода `_d`/`_dr`: в консоль
  печатается строка, обрезанная до `config.trim_limit()` (живое чтение
  `ADAPTER_DEBUG_TRIM`; `0`/None — без обрезки), с redact; при
  `ADAPTER_DEBUG_ENABLE=1` в сессионный файл пишется та же строка ПОЛНОЙ
  (без обрезки). Trim применяется к строке с префиксами `[ts]`/`[req_id]`;
- **удалены** `ADAPTER_DEBUG_TAGS_FULL` (env-парсинг `_parse_tags_full`,
  `_SET`/`_RAW`-представления, `_trim_limit(tag)`), `ADAPTER_DEBUG_TOOLS`,
  `ADAPTER_DEBUG_TOOLS_ERROR`, `ADAPTER_DEBUG_TAGS_OUT_ALL`; вместо
  тегового трима — публичный `config.trim_limit()` (без тега);
- **`ADAPTER_DEBUG_TAGS_OUT` → `ADAPTER_DEBUG_PARTS`** — тот же флаг, но
  дампы пишутся для ВСЕХ логгируемых частей (фиксированного списка тегов
  больше нет): `BODY`, `TOOL_RESULT`, `OPENAI_BODY`, `FETCH_RAW`, `RESPONSE`;
- **`[TOOL_RESULT]` content-блок безусловен** — на каждый результат единым
  блоком с полным content (консоль с TRIM, файл полный); `[TOOL_RESULT_ERROR]`
  удалён из кода и *.parts-дампов полностью; точечные trim-вызовы в
  server.py/streaming.py упрощены до «слать полное» (консоль обрежет сама);
- **runtime-пул `/config`** — строковых полей нет: 6 bool (`ADAPTER_DEBUG`,
  `ADAPTER_DEBUG_PARTS`, `ADAPTER_SENSITIVE_LOGGING_ENABLE`,
  `ADAPTER_STREAMING_ENABLE`, `ADAPTER_STREAM_INCLUDE_USAGE`,
  `ADAPTER_STRICT_MODELS`) + 3 int (`ADAPTER_DEBUG_TRIM`,
  `ADAPTER_TRACE_REASONING_MAX_CHARS`, `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS`);
- **иконки строк** — `_ACTIONS` в `webui_status.py`: 🔄 (U+1F504, reprobe),
  ⏪ (U+23EA, reset), 🗑 (U+1F5D1, delete — красный #c0392b); фразы —
  в `title`/`aria-label`. Текстовая кнопка «⟳ Перепроверить» (POST `/`) не
  меняется.

**Следствия:** канал «консоль» всегда читается с обрезкой TRIM, канал
«файл» при ENABLE=1 несёт полные части — отдельных рубильников
подробности не нужно; `.parts`-дампы по одному флагу покрывают все части;
один content-блок на каждый tool result (ошибки не выделяются отдельным
тегом). Breaking change: удалены `ADAPTER_DEBUG_TAGS_FULL`,
`ADAPTER_DEBUG_TOOLS`, `ADAPTER_DEBUG_TOOLS_ERROR`; `ADAPTER_DEBUG_TAGS_OUT`
переименован в `ADAPTER_DEBUG_PARTS`. Поведение проксирования не меняется.
Покрыто: unit — test_logger.py (консоль с TRIM / файл полный / TRIM=0 /
runtime-live), test_server.py (content-блок безусловен), test_config.py,
test_webui_config_api.py, test_session_log.py, test_webui_status.py (новые
глифы 🔄/⏪/🗑); интеграция — test_manual_check.py (реальный процесс:
консоль обрезана при малом TRIM, `session-*.log` несёт полную строку).

### 2026-09-08 Колонка Actions, иконки-действия строки, удаление модели из таблицы и файла

**Цель:** переименовать колонку «Действия» таблицы «Models in use» в Actions,
дать действие «Удалить» для выбранной модели (строка уходит из рабочей
таблицы и из файла `model-usage.yaml` на диске — запись обновлённой таблицы
без неё) и заменить фразы кнопок «Перепроверить»/«Сбросить»/«Удалить»
символьными иконками.

**Решение:**
- **`model_usage.delete_model(model)`** — по образцу `reset_model`: под
  `_TABLE_LOCK` `_ensure_loaded_locked()` + `del _TABLE[model]` + `_DIRTY=True`,
  вне лока `_save_table(force=True)` — файл перезаписывается сразу без
  строки (в отличие от reset строка уходит и из памяти, и с диска; повторный
  delete → False). Безопасно при идущей reprobe строки (`reprobe_model` в
  finally видит `row is None`); чистка `config._ENDPOINT_STATE` не нужна
  (кэш доступности эндпоинтов — общий на бэкенд);
- **колонка Actions** — `<th>Действия</th>` → `<th>Actions</th>`; 8 колонок
  и их позиции не меняются (Cost=5, Actions=7) — JS usage_poll и
  позиционный парсинг Cost интеграционного теста валидны; текстовая кнопка
  «⟳ Перепроверить» (проверка бэкендов, POST `/`) не трогается;
- **иконки-кнопки строки** — `_actions_cell_html` по константе `_ACTIONS`
  собирает три POST-формы с юникод-кнопками: ⟳ (U+27F3 — reprobe), ↺
  (U+21BA — reset), ✕ (U+2715 — delete, красный #c0392b); фразы-подписи
  ушли в `title`/`aria-label`. Reprobing-ветка ячейки прежняя: серый
  «проверяется…», кнопок нет;
- **`POST /api/model-usage/delete?model=<имя>`** — `ModelUsageDeleteEndpoint`
  по образцу reset: JSON — 200 `{"ok": true}` / 404 (строки нет — повторный
  delete не идемпотентен, в отличие от reset) / 400 (нет model); кнопка ✕
  (HTML-форма) — 303 See Other на GET `/` (PRG); GET на префикс → 404.

**Следствия:** строка модели удаляется из рабочей таблицы и YAML-файла
кнопкой ✕ или curl-ом; действия строки читаются по иконке (подпись — в

**Цель:** закрыть замечания после фикса корректного завершения: (1)

### 2026-09-08 Корректное завершение по Ctrl-C/SIGTERM

**Цель:** убрать падение процесса при повторном Ctrl-C во время завершения.
Дефолтный SIGINT кидает KeyboardInterrupt в главный поток; первый Ctrl-C
ловился в serve_forever, finally звал flush_table() (запись model-usage.yaml),
а ПОВТОРНЫЙ Ctrl-C (пользователь жмёт сразу) прерывал YAML-запись посреди
_atomic_write_yaml — «unhandled exception» с traceback-хвостом [PYI-...]
(в бинаре PyInstaller — KeyboardInterrupt в <string>), оставался мусорный
model-usage.yaml.tmp. SIGTERM (systemd/launchd/kill) по умолчанию убивал
процесс МГНОВЕННО, без finally — usage-хвост терялся.

**Решение:**
- **переключение сигналов в finally** (backend-adapter.py): как только началось
  вежливое завершение, SIGINT/SIGTERM переключаются на немедленный
  os._exit(130) — повторный сигнал больше не может прервать flush_table(),
  процесс тихо умирает без дампа стека;
- **SIGTERM → вежливое завершение**: хэндлер _graceful_signal кидает
  KeyboardInterrupt в главный поток (PEP 475), как Ctrl-C — штатное завершение
  (shutdown слушателей, flush) работает и для systemctl stop / launchctl / kill;
- **вежливая остановка фоновых слушателей** в finally: shutdown() +
  server_close() WEBUI и Prometheus-экспортёра (активные обработчики успевают
  дочитать ответ); config.stop_refresh(timeout=2) дожидается текущего цикла
  фоновой проверки бэкендов (снимок состояния консистентен);
- **flush_table() устойчив к прерыванию** (model_usage.py): глотает
  KeyboardInterrupt из _save_table — завершение адаптера не падает;
- **_save_table снимает _DIRTY только после успешного os.replace** — прерванная
  запись оставляет флаг взведённым, следующее сохранение допишет хвост;
  осиротевший model-usage.yaml.tmp затирается следующим атомарным сохранением.

**Следствия:** Ctrl-C завершает адаптер вежливо и предсказуемо: первый —
[EXIT] Bye после сохранения usage-хвоста; повторный во время завершения —
немедленный выход с rc=130, без traceback и [PYI-...] unhandled exception.
SIGTERM больше не «рубит» процесс, а проходит то же штатное завершение.
Поведение проксирования не меняется.

### 2026-09-07 Live-счётчики секции Models in use (автообновление без перезагрузки)

**Цель:** для обновления счётчиков Вызовов/Input/Output статус-страницы
приходилось обновлять страницу вручную. Сделать так, чтобы счётчики менялись
сами (с каждым запросом), без оверхеда: push браузеру недоступен, способ —
лёгкий периодический GET (как уже принято в проекте: status_poll /
reprobe_poll); цена — один маленький JSON-ответ раз в 5 с на открытую вкладку
(локальный сервер), при скрытой вкладке браузер сам троттлит таймеры.

**Решение:**
- **эндпоинт `GET /api/model-usage/snapshot`** — новый класс
  `UsageSnapshotEndpoint` в `webui_status.py`: `json.dumps(model_usage.
  usage_snapshot())` — копии строк таблицы в порядке первого обращения
  (примитивы, JSON-safe). GET ничего не мутирует (кроме ленивой загрузки
  таблицы при первом обращении) и **не ходит в сеть к бэкендам** — безопасно
  опрашивать каждые 5 с;
- **JS `usage_poll`** (безусловный, в <head> страницы — в отличие от
  status_poll/reprobe_poll, которые вставляются только при running): каждые
  ~5 с fetch снимка и обновление **только ячеек** счётчиков
  (data-calls/data-input/data-output на `<td>`; textContent — сырое число для
  Вызовов и `_fmt_tokens`-формат с U+202F для Input/Output, JS `usage_fmt`);
- **позиционный матчинг** — и рендер, и снимок идут в порядке первого
  обращения (`usage_snapshot`), поэтому строки сопоставляются по индексу
  (`id="usage-row-<i>"` на `<tr>`), экранирование имён не мешает. Число строк
  изменилось (строка сброшена/добавлена) — `location.reload()` перерисует
  таблицу целиком (редкое событие; reprobe и так перерисовывает страницу
  своим поллингом). Без `location.reload()` в обычном тике — диалогов и
  зацикливания нет.

**Следствия:** счётчики на открытой странице меняются сами в течение ~5 с
после запроса, страница не перезагружается; оверхед — один JSON-ответ раз
в 5 с на вкладку, сеть к бэкендам не гоняется; свёрнутая вкладка трафика
почти не создаёт; поведение проксирования не меняется.

### 2026-09-06 Персистентная таблица использованных моделей (ядро)

**Цель:** таблица использованных моделей (`model_usage.py`) жила только в
памяти процесса и терялась при рестарте адаптера — счётчики вызовов и
трафика, накопленные от запуска к запуску, обнулялись. Сделать учёт
перманентным: хранить таблицу в YAML-файле в корне WEBUI (там же, где
`ADAPTER_DEBUG_LOGPATH` / `./tmp/webui`), чтобы счётчики переживали
перезапуски.

**Решение:**
- **персистентность** — таблица сохраняется в `model-usage.yaml` в корне
  WEBUI (формула `ADAPTER_DEBUG_LOGPATH or "./tmp/webui"`; файл несёт версию
  формата — `version: 1`, строки — под ключом `models`). При старте файл
  загружается лениво (при первом обращении к таблице), строки нормализуются
  (`probing` всегда False, счётчики — неотрицательные int, незнакомые
  pname/ключи отбрасываются); повреждённый файл игнорируется (таблица
  стартует пустой, файл перезапишется первым сохранением). Загруженные
  строки не перепроверяются — повторное обращение идёт по fast-path
  (устаревшие результаты проб эндпоинтов освежаются кнопкой
  «Перепроверить» — запись 2026-09-06 «Кнопка „Перепроверить"»);
- **период сохранения** — новый env-параметр `ADAPTER_MODEL_USAGE_SAVE_INTERVAL`
  (сек, дефолт **300**): «грязная» таблица сохраняется не чаще раза в период;
  создание новой строки модели и завершение работы адаптера (в т.ч. Ctrl-C —
  `flush_table` в финальном блоке backend-adapter.py) сохраняют сразу. Строки
  с `probing: True` (идёт первая проба новой модели) на диск не попадают;
- **сброс строки** — новая функция `model_usage.reset_model(model)`: обнуляет
  счётчики строки (calls/input_tokens/output_tokens → 0), строку из таблицы
  и из YAML-файла НЕ удаляет (см. запись 2026-09-07 «Сбросить очищает
  счётчики…»; полный сброс таблицы НЕ добавлялся);
- **точка включения** — `webserver.serve()` (после создания контекста)
  синхронизирует persist-путь с `root_dir` WEBUI — файл лежит в корне и при
  встроенном запуске, и в standalone (`python -m backend_adapter.webserver
  [ROOT]`). Тесты: персистентность выключена изолирующей фикстурой
  (`set_persist_path("")`), unit-тесты включают её на `tmp_path`.

**Следствия:** счётчики переживают рестарты (страница `/` после рестарта
сразу показывает прошлые строки без новых запросов); потеря хвоста ≤
`ADAPTER_MODEL_USAGE_SAVE_INTERVAL` при жёстком kill, при штатном завершении
таблица сохраняется всегда; поведение проксирования не меняется. API сброса
счётчиков и руководство WEBUI — следующими коммитами группы.

### 2026-09-06 Использованные модели: счётчики трафика (ядро)

**Цель:** в таблице использованных моделей, кроме счётчика вызовов, видеть
объёмы данных, которыми адаптер обменивается с бэкендом по каждой модели:
сколько байт тел запросов отправлено и сколько байт тел ответов получено.

**Решение:**
- **два новых поля строки** `model_usage._TABLE` — `bytes_sent` (байты тел
  запросов → бэкенду) и `bytes_recv` (байты тел ответов ← бэкенда);
  инициализируются 0 при создании строки, растут только накоплением;
- **новая точка учёта** — `model_usage.add_usage_bytes(client_model, sent,
  recv)`; вызывается ОДИН раз на запрос из `finally` в `do_POST` (срабатывает
  на любой исход: успех, ошибка бэкенда, исчерпание ретраев, исключение).
  Учитываются только запросы, прошедшие strict-проверку (`usage_active`
  ставится сразу после `record_model_usage`); 400-пути в счётчики не
  попадают. Гейт — тот же `ADAPTER_MODEL_USAGE_ENABLE` (живое чтение);
  новых флагов нет;
- **что считается** — только обмен с бэкендом: тело [OI]-запроса
  (`out_body`, сериализуется один раз в переменную и переиспользуется
  ретраями) + тело ответа бэкенда. **Включая повторные попытки**: `sent`
  накапливается на каждой попытке (перед `urlopen`), `recv` — на каждом
  полученном теле (в т.ч. тела ответов ошибок 4xx/5xx в HTTPError-ветках);
- **стриминг**: `stream_openai_to_anthropic` получил необязательный параметр
  `bytes_sink` (список-ячейка `[int]`) — в нём накапливается сумма длин ВСЕХ
  сырых SSE-строк ответа бэкенда (включая пустые разделители и не-data
  строки), до конвертации в Anthropic-события. Распаковка пары
  `(stop_reason, usage)` не изменилась — параметр опционален, существующие
  тесты стрима не тронуты;
- **не учитывается**: запрос агента и ответ агенту (только обмен адаптер ↔
  бэкенд), служебные дымовые пробы эндпоинтов (другой путь кода).

**Следствия:** по каждой модели видны фактические объёмы трафика к бэкенду
(включая повторные попытки при сбоях); `add_usage_bytes` не бросает
исключений (учёт не влияет на запрос); python-int не переполняется —
«крышки» не нужны. Колонки «Отправлено/Получено» на странице статуса —
следующим коммитом группы.

### 2026-09-06 Статус-страница: автопроверка бэкендов при старте и на первом GET

**Цель:** проверки не вызывались при первом старте: стартовая инициализация
делала только модельный опрос (`_init_multi_backends`), а GET «/» по
контракту v0.8.2 проверку сознательно не запускал — колонка Endpoints была
пустой («не опрошено»), и результат появлялся только после клика по кнопке.

**Решение:**
- **старт адаптера** (`backend-adapter.py`, блок WEBUI): сразу после поднятия
  веб-сервера запускается фоновая проверка `config.start_refresh(timeout=
  PROBE_TIMEOUT)` — первый GET «/» показывает свежие модели и колонку
  Endpoints без клика. Дублирование стартового опроса `/v1/models`

  вторую проверку не дёргает. Локальные импорты (скрипт не импортирует

- **первый GET «/»** (`webui_status.py`, `_autostart_first_check`): чистая
  функция запускает проверку, если есть что проверять (`_collect_endpoints()`
  непуст — в т.ч. standalone с YAML в `ADAPTER_BACKEND_CONFIG`), проверка
  не идёт (`running` ложен) и ещё ни разу не завершалась (`done_at is None`).
  Вызывается в `StatusEndpoint.GET` перед рендером; после запуска страница
  отдаётся с баннером «Проверка выполняется…»;
- критерий «проверок ещё не было» — `done_at is None` (воркер всегда
  публикует `done_at`, даже при исключении): повторные загрузки страницы

**Следствия:** при первом старте адаптера и при первом заходе в standalone
(с YAML) колонки заполняются автоматически; повторные проверки — только по

нет. Контракт v0.8.2 «GET проверку не запускает» заменён на «первый GET

### 2026-09-06 Статус-страница: POST «⟳ Проверить сейчас» — PRG (303 See Other)

**Цель:** по завершении фоновой проверки страница перезагружается
`location.reload()`, который повторял исходный POST «/» (кнопка отвечала
200 + HTML) — Chrome/Firefox показывали диалог «Чтобы отобразить эту
страницу, браузер должен отправить сведения для повторения ранее
произведённого действия…», закрывающийся только отменой, а при отмене
зависал баннер «Проверка выполняется…» (его снимал только тот же reload).

**Решение:**
- **PRG-паттерн (Post/Redirect/Get)**: `StatusEndpoint.POST` теперь не
  отдаёт HTML, а отвечает **303 See Other** с `Location: /` — браузер
  переходит на страницу GET-навигацией (новый сервисный метод
  `Handler._redirect(location, status=303)` в `webserver.py`, без тела);
- фоновую проверку POST по-прежнему запускает до редиректа;
  `start_refresh` синхронно публикует `running=True` → следующий GET видит
  идущую проверку (баннер + поллинг), авто-релоад по завершении происходит
  на GET-документе — повторного POST нет.

**Следствия:** диалог «повторить действие» исчезает; баннер корректно
снимается авто-релоадом. GET-загрузка и все остальные эндпойнты
(session_viewer, config_api) не затронуты — `_redirect` отдельный метод,
`_write` не менялся. `webui_config_api.py` (комментарий обещает 303,
отдаёт 200+HTML) вне этой задачи.

### 2026-09-06 Статус-страница: зелёный ✓ в колонке Endpoints — только для HTTP 200

**Цель:** колонка «Доступные API» помечала зелёным ✓ и комментарием `(501)`
эндпоинты, не прошедшие проверку: классификация дымовой пробы считала
«найденным» любой HTTP-код, кроме 404 (`400/401/405/429`, все 5xx — в т.ч.
`501 Not Implemented` — рисовались как работающие), что вводило в заблуждение.

**Решение:**
- **классификация в `config.py` (`_probe_backend_endpoints`)**: `found=True`
  теперь только для HTTP 200; любой другой код (включая 404 и все 4xx/5xx) —
  `found=False`. Единое место правды — рендер не дублирует семантику кода;
- **рендер колонки (`webui_status.py`, `_api_html`)**: зелёный `✓` показывается
  только для реально работающих эндпоинтов (`found` ⇔ 200); непрошедшие и
  пропущенные (нет probe-модели) на странице **не показываются вовсе** (ранее —
  серым `—`/`(код)`); если проба была, но ни один эндпоинт не ответил 200 —
  ячейка показывает один серый `—` с пояснением вместо пустого места.

**Следствия:** колонка Endpoints = «что реально работает», а не «что ответило
не 404»; комментарий `(501)` и прочих кодов на странице больше нет. Данные
`_ENDPOINT_STATE` и лог-блок `[ENDPOINT_PROBE]` (сырые коды) не менялись;
ломающих изменений нет.

### 2026-09-05 Дымовая проба API-эндпойнтов LLM-бэкендов

**Цель:** статус-страница WEBUI (`/`) показывает модели каждого бэкенда
(опрос `GET /v1/models`), но не говорит, какие известные API-эндпойнты бэкенд
реально обслуживает. Бэкенды бывают разными: один реализует [OI] Chat
Completions и Responses, другой — ещё и [AN]-совместимый `/v1/messages` или
embeddings. Задача — показывать это рядом со списком моделей, определяя
короткими «дымовыми» POST-запросами.

**Решение:**
- **проба эндпойнтов** (`config.py`): при каждом обновлении списка моделей
  (`refresh_models`) на фиксированный список `ENDPOINT_PROBES`
  (`/v1/chat/completions`, `/v1/messages`, `/v1/responses`, `/v1/embeddings`)
  шлются короткие POST с `max_tokens:1` (у `/v1/messages` — обязательный
  заголовок `anthropic-version: 2023-06-01`, иначе живой [AN]-эндпоинт
  отвечает 400). HTTP-классификация: `200` — работает; `400/401/405` —
  эндпоинт есть, но тело/ключ не подошли; `404` — не реализован; сеть/таймаут —
  ошибка бэкенда. Новый помощник `_http_json` (по образцу `_fetch_models`,
  тот же `SSL_CTX`), поведение `_fetch_models` не тронуто;
- **модель на эндпоинт — ключ `probe` YAML-записи бэкенда** (необязательный):
  список пар `эндпоинт: модель` (у разных эндпоинтов бэкенда свои модели —
  chat / responses / embeddings). Семантика: перечислен с моделью — пробуется
  ею (модель сверяется со свежим `/v1/models`; не найдена — пропускается
  только этот эндпоинт, `[WARN]` + текст в `errors`); пустое значение или
  неперечисленный эндпоинт — моделью по умолчанию (первая из `/v1/models`
  бэкенда); ключа нет — все 4 эндпоинта моделью по умолчанию (старые конфиги
  работают как раньше);
- **кэш ~60 с** (`ENDPOINT_PROBE_TTL`, `_ENDPOINT_STATE`): повторный заход на
  страницу в пределах TTL сеть не трогает; мастер-флаг `ADAPTER_ENDPOINT_PROBE=0`
  отключает автопробу;
- **лог** — консольный блок `[ENDPOINT_PROBE]` (print, гейт
  `ADAPTER_DEBUG_ENABLE`, как `_d()` в `logger.py` — `config.py` не может
  импортировать logger, цикл): одна строка на фактическую пробу бэкенда —
  `backend '<имя>' (<base>): completions=200 messages=404 responses=…
  embeddings=…` (сырые коды); сетевая ошибка — `failed: <текст>`. Кэш-хиты не
  логируются: страница показывает последний результат, лог — историю проб;
- **WEBUI** (`webui_status.py`): в таблицу добавлена колонка «Доступные API» —
  найденные пути зелёным с ✓, ненайденные (404) и пропущенные — серым «—»,
  непробованный бэкенд — «не опрошено»; футер про автообновление уточнён

- **Версия:** `__version__` и `pyproject.toml` подняты до 0.8.2 в первом
  коммите группы (вместе с WIP-шапкой changelog).

**Следствия:** на статус-странице видно, какие API реально обслуживает каждый
бэкенд (и чем — моделью по умолчанию или заданной в `probe`); повторные
проверки не дублируют дымовые запросы к бэкенду (кэш 60 с); у

### 2026-09-05 Фоновая проверка бэкендов по кнопке: баннер, авто-обновление, `/api/refresh-state`

**Цель:** каждый GET/POST статус-страницы `/` синхронно перечитывал модели
всех бэкендов (`refresh_models`) и гонял дымовую пробу эндпойнтов — при
недоступном/медленном бэкенде HTTP-ответ висел (N бэкендов × 5 с), а
повторная загрузка страницы давала лишнюю пачку сетевых запросов даже при
живом бэкенде. Проверку нужно было сделать фоновой, а о незавершённой
операции — сообщать на странице.

**Решение:**
- **фоновый воркер проверки в `config.py`** (рядом с `refresh_models`):
  состояние — иммутабельный снимок-словарь `_REFRESH_JOB` (`running`,
  `started_at`/`done_at`, `ok`/`count`/`errors`, `checked_at`), заменяемый
  целиком; запуск сериализуется `_REFRESH_LOCK`. Публичный API:
  `start_refresh(timeout) -> bool` (False, если проверка уже идёт — второй
  поток не создаётся) и `refresh_state() -> dict` (копия снимка). Воркер
  `_refresh_worker` зовёт `refresh_models(timeout)` в daemon-потоке и в
  `finally` публикует финальный снимок — `running=False` гарантирован даже
  при исключении (текст — в `errors["__worker__"]`);
- **статус-страница `webui_status.py`**: GET `/` проверку **не запускает** —
  рендерит состояние из `config.refresh_state()` (модели/статусы из конфиг-
  глобалов — результат стартового опроса или последней проверки; до первой
  проверки — футер-подсказка «нажмите Проверить сейчас»); POST `/` (кнопка
  «⟳ Проверить сейчас») вызывает `config.start_refresh(timeout=PROBE_TIMEOUT)`
  и отвечает сразу;
- **баннер + авто-обновление**: пока проверка идёт, страница показывает
  жёлтый баннер «⟳ Проверка выполняется (запущена в HH:MM:SS)… страница
  обновится автоматически по завершении»; JS `status_poll` каждые ~2 с
  опрашивает лёгкий JSON-эндпоинт `/api/refresh-state` и при завершении сам
  делает `location.reload()` (GET проверку не запускает — зацикливания нет);
  на странице без баннера поллинга нет;
- **эндпоинт `/api/refresh-state`** (`RefreshStateEndpoint` в `webui_status.py`,
  регистрируется тем же `@webserver.register`): JSON-снимок состояния
  (`running`/`ok`/`count`/`errors`/`checked_at`/…), отдаётся мгновенно без
  сети;
- футер «Список моделей обновляется при каждой загрузке страницы»
  переформулирован: обновление — по кнопке (GET больше не проверяет);
  docstring и комментарии (`config.refresh_models`, секция ENDPOINT PROBE)
  приведены к фактическому поведению.

**Следствия:** статус-страница отвечает мгновенно при любом состоянии
бэкендов (проверка — в фоне); повторные GET не порождают сетевых запросов;
результат проверки виден без ручного обновления (авто-релоад по завершении);
повторный POST во время идущей проверки не создаёт второй поток (баннер
«уже выполняется»). Поведение проксирования не меняется. Breaking-изменений
нет: контракт чистых функций рендера (`_render_status_page`) и читатели
результата `refresh_models` сохранены; тесты переведены с синхронного мока
`refresh_models` на seed-состояния `_REFRESH_JOB` (+ новые — воркер,
баннер/поллинг, JSON-эндпоинт).

### 2026-09-04 Фикс: init/refresh моделей мутируют кэш-словари на месте (живые ссылки server.py)

**Проблема:** при старте против живого бэкенда адаптер после успешного probe

сети/контейнере на нужном адресе, а дефолт «все интерфейсы» небезопасен
по умолчанию (доступ из сети без явного запроса).

**Решение:**
- `ADAPTER_ENDPOINT_HOST` — адрес, на котором слушает HTTP-эндпоинт
  адаптера; `ADAPTER_WEBUI_HOST` — адрес веб-интерфейса; дефолт обеих —
  `127.0.0.1` (localhost);
- идиом `os.environ.get(name, "") or "127.0.0.1"`: пустая env-переменная
  в bind-кортеже socketserver означала бы INADDR_ANY — с `or` и незаданная,
  и пустая дают безопасный localhost;
- `0.0.0.0` — осознанный выбор «слушать на всех интерфейсах» (прежнее
  поведение адаптера); баннер при старте показывает реальный адрес.

**Изменения:** backend_adapter/config.py (две константы + комментарии),

## v0.5.0 (multi-backend config)

### Множественные бэкенды через YAML-конфиг

**Новая переменная:** `ADAPTER_BACKEND_CONFIG` — путь к YAML-файлу, описывающему несколько бэкендов.
Если переменная не задана — адаптер работает в старом single-backend режиме (`BACKEND_BASE` / `BACKEND_KEY`).

**Формат конфига:**
```yaml
backend:
  - name: AAA
    base: https://llm.service.example.com
    key: ADAPTER_BACKEND_KEY_AAA
  - name: BBB
    base: https://llm.service.another.com
    key: ADAPTER_BACKEND_KEY_BBB
```

| Поле | Описание |
|---|---|
| `name` | Короткое имя бэкенда, используется как префикс для коллизирующих моделей |
| `base` | URL бэкенда (без `/v1/…`) |
| `key` | ИМЯ переменной окружения, содержащей токен доступа |

**Автоматические префиксы моделей:**
- При старте адаптер запрашивает `GET /v1/models` с каждого бэкенда.
- Если модель с одинаковым `id` встречается на нескольких бэкендах — к её имени добавляется префикс `<backend_name>.` (например `AAA.qwen3.6-35b-a3b`).
- Модели без коллизий доступны под своим оригинальным именем.
- `ADAPTER_MODELS_MAPPING` не учитывает префиксы — маппинг составляется независимо.

**Маршрутизация запросов:**
- Явный префикс в имени модели (`AAA.qwen3.6-35b-a3b`) → routing к бэкенду AAA, на бэкенд уходит имя без префикса.
- Префикса нет → lookup в общем списке моделей (`_MODEL_TO_BACKEND`), fallback к первому бэкенду в конфиге.

### Прочее

- Заведён самописный мини-парсер YAML (`_parse_backend_yaml`) — без зависимости от PyYAML.
- Вывод при старте показывает количество конфигурированных бэкендов.

### Исправление именования сессионных логов

**Проблема:** в `_make_session_file()` весь `session_id` подставлялся в безопасное имя файла через `re.sub(r'[^A-Za-z0-9._-]', '_', session_id)`. Длинные session IDs (UUID-подобные) порождали слишком длинные и неуклюжие имена файлов сессий.

**Решение:** обрезка `session_id` до первых 8 символов перед безопасным преобразованием: `re.sub(r'[^A-Za-z0-9._-]', '_', session_id[:8])`.

### Прочее

- Удалён неиспользуемый `import socketserver`.
- Убран хардкод fallback модели `"qwen3.6-35b-a3b"` — теперь при отсутствии `model` в запросе возвращается 400 "Missing required field: model".
- Заведены `__version__` и `__comment__` для единого управления версией и комментариями в заголовке запуска.

## v0.4.0 (streaming SSE passthrough + HTTP/1.0 keep-alive fix)

### Стриминг (SSE passthrough)

**Проблема:** адаптер принудительно шлёл бэкенду `stream: False` и ждал ответ целиком. Пока backend "думал" (иногда десятки секунд), клиент (Claude Code) не видел ни одного байта и рвал соединение по своему таймауту — на выходе `BrokenPipeError` при попытке записать уже готовый ответ.

**Решение:**

- Убран жёсткий `"stream": False`. Клиентский флаг `stream` пробрасывается бэкенду "как есть".
- Новая функция `stream_openai_to_anthropic()` — читает SSE-ответ backend'а построчно (`data: {...}` / `data: [DONE]`) и на лету транслирует каждый чанк в Anthropic streaming-события: `message_start` → чередующиеся `content_block_start/delta/stop` (текст как `text_delta`, tool-calls как `tool_use` + `input_json_delta`, фрагменты `arguments` конкатенируются клиентом по-OpenAI-совски) → `message_delta` → `message_stop`.
- `do_POST` разделён на две ветки:
  - **Потоковая:** retry работает только пока не ушёл ни один байт (этап `urlopen`/заголовков). Если обрыв во время самого стрима — шлём SSE-событие `error` вместо retry (второй `message_start` сломал бы протокол). `BrokenPipeError` во время стрима → `[CLIENT_GONE]` без падения.
  - **Нестриминговая:** без изменений, на случай если бэкенд стриминг не поддерживает.
- Логика ретраев, редактирования секретов, per-session логов и causality (`_register_tool_use`) сохранена и в стриминговом пути.

### Флаг `ADAPTER_STREAMING_ENABLE`

Переключатель "рубильник" в едином стиле с остальными `ADAPTER_*_ENABLE`:

- `ADAPTER_STREAMING_ENABLE=1` (по умолчанию) — новое стримящее поведение: если клиент просит `stream=true`, адаптер честно стримит.
- `ADAPTER_STREAMING_ENABLE=0` (или `false`/`no`) — полный откат к старому поведению: `stream=False` принудительно, даже если клиент просил стриминг. Удобен как аварийный рубильник.
- Режим виден при старте: `Streaming: enabled (SSE passthrough)` / `disabled (legacy stream=False, старое поведение)`.

### HTTP/1.0 keep-alive lie fix

**Проблема:** в `_start_sse()` стоял заголовок `Connection: keep-alive`, хотя `protocol_version` адаптера остаётся дефолтным `"HTTP/1.0"` — при таком protocol_version `http.server` **всегда** закрывает TCP-соединение после ответа. Клиент верил заголовку, клал сокет в пул на переиспользование, а при следующей попытке отправить по нему запрос получал `ECONNRESET` на уже мёртвый сокет — отсюда `"API Error: The operation timed out"` и `"will retry in Xm Ys"` в терминале **уже после** того, как адаптер успешно отдал предыдущий ответ.

**Решение:** `_start_sse()` теперь шлёт `Connection: close` и явно выставляет `self.close_connection = True` — честно информирует клиент, что соединение будет закрыто. Ложные таймауты устранены.

> Примечание: это чинит симптом, но не убирает накладные расходы на TCP+TLS handshake на каждый запрос (агентный цикл шлёт их последовательно). Настоящий keep-alive (переиспользование TCP-соединений) потребует отдельной правки: `protocol_version = "HTTP/1.1"` + chunked-фрейминг.

## v0.3.4 (unbuffered I/O for debug/trace logs)

Отключена буферизация ОС/Python при записи в debug- и trace-логи. До этого `fd.write()` уже вызывал `fd.flush()`, но Python внутри файловых потоков мог держать байты в своём буфере и не сбрасывать их на диск мгновенно — в режиме пер-session логов это приводило к задержкам между моментом события и появлением записи в файле.

**Что изменено:** добавлен явный `fd.flush()` / `f.flush()` после каждого `write()` в:
- `_d()` — дескриптор сессионного debug-файла
- `_trace()` — дескриптор сессионного trace-файла
- `_trace()` — mode «один файл» (через `with open(...)`)

Это гарантирует, что каждое событие попадает в log-file сразу, без задержек на заполнение внутреннего буфера Python.

## v0.3.3 (model probe + validation)

## v0.3.0 (timeout+retry+trace+causality)

### Отличия от v0.2.0:
- **reasoning_content больше НЕ обрезается** в trace-логе (раньше писалось только `reasoning[:500]`). Теперь пишется полная строка в поле `"reasoning"` (с опциональным потолком `ADAPTER_TRACE_REASONING_MAX_CHARS`, по умолчанию без ограничения). Это единственное место, где видно, ПОЧЕМУ модель выбрала тот или иной инструмент — обрезка убивала именно ту часть рассуждения, где принимается решение.
- **Аргументы tool_call (tool_input)** теперь пишутся в trace целиком (поле `"input"` внутри `tool_uses` события `response_content`), а не только `name`. Без них нельзя было отличить содержательно разные вызовы одного и того же инструмента.
- **Добавлена трассировка ИСПОЛНЕНИЯ инструмента**: когда в очередном входящем запросе обнаруживается `tool_result`-блок, эмитится отдельное событие `"tool_result"` с полным содержимым результата и признаком ошибки (`is_error`), а не только сам факт вызова инструмента без исхода.
- **Добавлена явная связь родитель → потомок** между запросами одной сессии: каждый `tool_use`, который модель вернула в ответе на запрос `req_id=P`, регистрируется в session-scoped индексе по его `tool_use_id`. Когда в ПОСЛЕДУЮЩЕМ запросе `req_id=C` приходит `tool_result` с тем же `tool_use_id`, адаптер находит `P` в индексе и пишет событие `"tool_result"` с полями `tool_use_id` и `parent_req_id=P`. Это даёт точную причинно-следственную связь между конкретным вызовом инструмента и запросом, в котором пришёл его результат — надёжно даже при параллельных ветвях (см. `request_kind` ниже), потому что `tool_use_id` уникален для каждого вызова, в отличие от сортировки по времени/msg_count.
- **`request_start` теперь содержит поле `request_kind`** — структурный (не эвристический по содержимому промпта) признак того, к какому "потоку" относится запрос в рамках сессии: `"agent_turn"` (обычный ход агента, `tool_count > 0`), `"structured_output"` (побочный вызов со structured-output схемой в `output_config` — например, генерация заголовка сессии, идёт параллельно основному циклу и НЕ является его веткой) или `"plain"` (ни тулов, ни structured output). Это отделяет параллельные сайдкар-вызовы харнесса от реальных ветвлений основного агентного цикла ещё до какого-либо анализа контента.
- **Событие `"harness_branch"` убрано целиком** — оно смешивало под одним именем два разных по природе явления: собственные инвариант-проверки адаптера (`harness_branch/system_first`, `harness_branch/finish_reason_map`) и реальную деградацию поведения (`harness_branch/text_tool_call_fallback`). Заменено тремя явными событиями:
  - `"adapter_invariant_check"` — только диагностика конвертации Anthropic→OpenAI внутри самого адаптера (сейчас: позиция system-сообщения). Явно НЕ ветвление модели/харнесса.
  - `"tool_call_fallback"` — реальная деградация: backend не отдал нативный `tool_calls`, адаптеру пришлось парсить JSON из текста. Повышает риск некорректного вызова инструмента.
  - маппинг `finish_reason → stop_reason` больше не отдельное событие, а поля (`finish_reason_raw`/`stop_reason_mapped`) внутри и так существующего `response_content` — это чистая функция одного в другое, отдельное событие под неё было избыточным.
- **Человекочитаемый debug-лог (ADAPTER_DEBUG_LOGFILE) ТОЛЬКО дополнен**, ничего не сокращалось и не удалялось:
  - каждая строка теперь начинается с `[req_id]` (или `[-]` вне контекста конкретного запроса) — раньше при параллельных запросах строки разных `req_id` перемежались без возможности их различить, не сверяясь с trace JSON;
  - добавлена отдельная строка `[TOOL_RESULT]` в момент разбора входящего `tool_result`-блока — раньше результат тула был виден только внутри большого дампа `[BODY]`/`[OPENAI_BODY]`;
  - добавлена строка `[STREAM_REQUESTED]` — фиксирует, просил ли исходный запрос Claude Code потоковую выдачу (`anthropic_req["stream"]`), тогда как адаптер к бэкенду всегда шлёт `stream=False`; раньше это расхождение нигде не логировалось.

Аналитика по-прежнему должна строиться по JSONL trace-логу — debug-лог остаётся вспомогательным для ручной отладки конкретной сессии.

### Новая конфигурация (в дополнение к переменным v0.2.0):

| Переменная | Описание |
|---|---|
| `ADAPTER_TRACE_LOGFILE` | Путь к JSONL trace-логу (если не задан — трассировка событий не пишется, но redaction всё равно применяется к debug-логу) |
| `ADAPTER_TRACE_REASONING_MAX_CHARS` | Опциональный потолок длины поля `"reasoning"` в trace (0 или не задано — без ограничения, пишется полностью) |
| `ADAPTER_TRACE_TOOL_FIELD_MAX_CHARS` | Опциональный потолок длины полей `"input"` (аргументы tool_call) и `"content"` (tool_result) в trace (0 или не задано — без ограничения). Предохранитель на случай очень больших результатов (вывод команды на десятки МБ), а не дефолтное поведение |
